MotoRacer PC Reverse Engineering                           Analysis Note


                    THE SOFTWARE RASTERIZER PIPELINE


Abstract

   With the four primitive setup functions finally defined, the software
   rasterizer can be read end to end, from a primitive in a display list
   to a pixel in the framebuffer.

   None of the setup functions existed as functions until the orphan-
   code sweep in ghidra-db-repairs.txt section 6. They are the layer
   everything else in subsystems/pixel-format.txt sits underneath.

1.  The chain

   Screen3D_DispatchPrimitive  0x004aef20
       |
       +-- walker table at 0x004f1ee0, indexed by kind
       |
       v
   maybe_Screen3D_SetupPrimN   one of five
       |   average depth, resolve colour and texture page,
       |   near-plane clip, trivial reject, split quads
       |
       +-- maybe_Screen3D_ClipEdgeNear  0x0049d8f0
       |
       v
   the matching emitter        sets g_spanPatchDirty, texture base
       |
       +-- edge walker, installed in maybe_g_spanClipper
       |
       v
   span function, installed in DAT_00655d08
       |
       v
   self-patching inner loop    SpanBlend1/2, SpanCopyTexels

2.  Five parallel pipelines

   Each walker table slot pairs a setup function with two edge walkers,
   and each setup function drives its own emitter [verified]. Slots are
   the RUN-TIME indices after the scatter described in section 3, not
   the order the records appear in the binary:

   +------+------------+------------+---------------+---------------+
   | Slot | Setup      | Emitter    | Edge walker A | Edge walker B |
   +======+============+============+===============+===============+
   | 2    | 0x004a4820 | -          | -             | -             |
   +------+------------+------------+---------------+---------------+
   | 4    | 0x0049e510 | 0x0049dde0 | 0x0049d9e0    | 0x0049dbf0    |
   +------+------------+------------+---------------+---------------+
   | 5    | 0x0049fa10 | 0x0049f1e0 | 0x0049ed50    | 0x0049efb0    |
   +------+------------+------------+---------------+---------------+
   | 6    | 0x004a0f90 | 0x004a0700 | 0x004a0260    | 0x004a04d0    |
   +------+------------+------------+---------------+---------------+
   | 7    | 0x004a2630 | 0x004a1cb0 | 0x004a1770    | 0x004a1a30    |
   +------+------------+------------+---------------+---------------+

   Walker A is used when the span table's flag field is zero and walker
   B otherwise; the dispatcher copies that flag into DAT_0068b010 and
   picks accordingly.

   Slot 7's walker A is maybe_Screen3D_Walk7Now (0x004a1770), which was
   already read while repairing a split function. It walks a linked list
   of spans, clips each against the current interval, and calls through
   DAT_00655d08 per clipped segment. The other seven walkers are unread
   but are presumably variants of the same shape.

   Every one of the four emitters is a writer of g_spanPatchDirty, which
   closes a loop left open in subsystems/pixel-format.txt section 1.3.2:
   the fourteen functions that raise the span patch flag are the
   emitters and their relatives, and they raise it because they have
   just changed the texture base.

   Slot 2 is reached only when the span table names index 2, which no
   shipped record does; the indices in use are 0, 4, 5, 6 and 7, and 0
   is short-circuited. So maybe_Screen3D_SetupPrim0 may be unreachable
   in the shipped game [inferred].

3.  The tables are scattered by key at startup

   The indexing looked broken on a first pass and it is not. Both
   dispatch tables are rearranged at run time, so the bytes in the
   binary are NOT the table the dispatcher reads [verified].

   Screen3D_InitDispatchTables (0x004a2ea0) does nothing but call
   Screen3D_ScatterTableByKey (0x004a2e00) twice:

       Screen3D_ScatterTableByKey(g_spanTable,  0x10, 0x47);
       Screen3D_ScatterTableByKey(0x004f1ee0,   0x10, 0x0c);

   and that routine is a scatter:

       tmp = malloc(recSize * count);
       memcpy(tmp, table, recSize * count);   // packed source
       memset(table, 0xff, recSize * count);  // all slots -> -1
       for (src = tmp; i < count; i++, src += recSize) {
           if (*(int *)src == -1) break;      // -1 ends the source
           memcpy(table + *(int *)src * recSize, src, recSize);
       }
       free(tmp);

   Each record's first dword is its key. On disk the records are a
   dense, arbitrarily ordered list terminated by -1. At startup each is
   moved to table[key] and every unused slot is left as -1.

3.1.  What the tables actually look like at run time

   The walker table's source list carries keys 2, 4, 5, 6 and 7, so
   after the scatter:

   +------------+------------+---------------+---------------+
   | Slot       | Setup      | Edge walker A | Edge walker B |
   +============+============+===============+===============+
   | 2          | 0x004a4820 | -             | -             |
   +------------+------------+---------------+---------------+
   | 4          | 0x0049e510 | 0x0049d9e0    | 0x0049dbf0    |
   +------------+------------+---------------+---------------+
   | 5          | 0x0049fa10 | 0x0049ed50    | 0x0049efb0    |
   +------------+------------+---------------+---------------+
   | 6          | 0x004a0f90 | 0x004a0260    | 0x004a04d0    |
   +------------+------------+---------------+---------------+
   | 7          | 0x004a2630 | 0x004a1770    | 0x004a1a30    |
   +------------+------------+---------------+---------------+
   | all others | -1         | -1            | -1            |
   +------------+------------+---------------+---------------+

   The dispatcher's index values are 0, 4, 5, 6 and 7, where 0 is short-
   circuited and calls the span function directly. So 4 through 7 land
   exactly on the four setup functions. There is no off-by-anything and
   no null call.

   The span table is the same story at larger scale: 0x47 slots keyed by
   primitive kind. Its static record order says nothing about which kind
   a record serves; only the key field does. A table read of the raw
   bytes, which is what section 2 of an earlier draft did, gives a
   plausible but wrong mapping.

   The -1 fill is also what the consumers test.
   Screen3D_DispatchPrimitive begins with an equivalent of if
   (spanTable[kind].key < 0) return, which is the empty-slot check for a
   primitive kind with no entry.

3.2.  The general lesson

   This is the second mechanism in this binary where the static image
   does not show what the code actually runs against. The first was the
   self-modifying span loops in subsystems/pixel-format.txt section 1.3.

   Both have the same tell: an apparent inconsistency between clean-
   looking code and nonsensical data. When indexing arithmetic seems off
   by a fixed amount, or immediates look like placeholders, suspect run-
   time construction before suspecting the disassembly.


4.  What a setup function does

   Read from maybe_Screen3D_SetupPrim1 (0x0049e510) [verified]. All five
   share this skeleton, confirmed by each calling
   maybe_Screen3D_ClipEdgeNear exactly four times.

   Step 3 is NOT universal. Only slots 4 and 6 resolve a flat colour;
   slots 5 and 7 skip it and pass colour per vertex instead. See section
   5.

   1. Average the three vertices' depth at +0x0c into DAT_006d1f80, and
      a second per-vertex field into DAT_0068b00c.

   2. Fetch the texture page with maybe_Bankw_LockPageBits(page, 1).
      NOT a table lookup - it LOCKS the page's DirectDraw surface
      and the 1 asks it to release the lock again immediately.
      See sections 46 and 47.

   3. Resolve the flat colour:

   c = face[+0x02];
   maybe_g_spanFlatColor = Color_Convert555ToSurface(
                      (c & 0xffffffc1) >> 1 | (c & 0x1f));

   That is the same expression Load3dfAndMap uses in its flat-colour
   path, which is a useful cross-check on both.

   4. Near-plane clip. Each vertex's field at +0x08 is compared against
      DAT_00625774. The eight sign combinations are handled explicitly:
      all in front emits directly, one or two behind calls
      maybe_Screen3D_ClipEdgeNear to intersect the offending edges and
      interpolates new vertices before emitting.

   5. Trivial reject, with a neat trick. A tally starts at 2 and, per
      vertex, adds 1 when the coordinate is outside the limit and
      subtracts 2 more when it is outside on the negative side. A final
      value of 6 means all three vertices are off the same edge, and the
      primitive is dropped. X is tested against DAT_0062e448 and Y
      against DAT_00625784.

   6. Quads. The function body is a do-while that runs twice when
      face[+0x34] is not -1, the second pass shifting the vertex indices
      by one to emit the second triangle. That is exactly the triangle
      and quad marker documented in formats/trk.txt and
      formats/mesh-3df-map.txt, consumed here.

5.  What distinguishes the four pipelines

   Two independent axes, and the emitter argument counts confirm them
   arithmetically [verified].

   +------+------------+-------------+--------------------+--------------+
   | Slot | Setup      | Flat colour | Reads vertex +0x18 | Emitter args |
   +======+============+=============+====================+==============+
   | 4    | 0x0049e510 | yes         | no                 | 13           |
   +------+------------+-------------+--------------------+--------------+
   | 5    | 0x0049fa10 | no          | no                 | 16           |
   +------+------------+-------------+--------------------+--------------+
   | 6    | 0x004a0f90 | yes         | yes                | 16           |
   +------+------------+-------------+--------------------+--------------+
   | 7    | 0x004a2630 | no          | yes                | 19           |
   +------+------------+-------------+--------------------+--------------+

   Flat colour means the setup calls Color_Convert555ToSurface once for
   the whole primitive and leaves the result in maybe_g_spanFlatColor. Slots 4
   and 6 do; slots 5 and 7 do not. Vertex +0x18 is loaded six times as a
   float and three times as an integer, once per vertex, by slots 6 and
   7 only.

   The arithmetic ties it together. Slot 4 passes 13 dwords: two triples
   of per-vertex values plus the texture page. Dropping the flat colour
   costs three further arguments, one per vertex. Adding the +0x18
   interpolant costs another three. And 13 + 3 + 3 is 19, exactly what
   slot 7 passes. Which triple is which is settled in section 6.2.

   So the two axes are independent and the four slots are the full 2 x 2
   matrix. The natural reading is per-primitive versus per-vertex
   colour, which is flat versus Gouraud shading, crossed with one
   optional extra interpolant [inferred]. What +0x18 actually holds is
   not yet identified; the vertex record is 0x1c bytes and +0x18 is its
   last field.

   STALE. +0x18 has since been identified as invZ, 1/z, with the UVs
   premultiplied by it - see structs/MR_Vertex.txt section 1. The
   hardware path corroborates it independently: D3D_WriteVertex copies
   vertex +0x18 straight into the D3DTLVERTEX rhw field, and rhw is by
   definition the reciprocal homogeneous w. So slots 6 and 7 are the
   perspective-correct pair, which is what detail-levels.txt section 2.3
   concluded from the other direction.

   WHAT SELECTS THE SLOT IS NOW KNOWN. g_spanTable maps kind to slot,
   and cross-referencing its 32 records against the primitive-kind
   feature table at DAT_006d1f88 gives an exact, exceptionless rule over
   all 24 kinds that use a real slot [verified]:

       slot = 4 + (featureBits & 0x02 ? 1 : 0) + (featureBits & 0x20 ? 2 : 0)

   So feature bit 1 is this section's flat-versus-Gouraud axis and
   feature bit 5 is its +0x18 axis. That confirms the 2 x 2 reading
   above from a completely independent direction - the table was built
   in Screen3D_Open without reference to any of these functions.

   It also names the second axis by use rather than by content: bit 5
   is set by Screen3D_QueuePrimitive for primitives NEAR the camera, so
   slots 6 and 7 are the near path and slots 4 and 5 the far one. Which
   is exactly what an optional perspective-correction interpolant would
   be used for, and is consistent with section 6.1. See
   subsystems/detail-levels.txt section 9.

   All five setups, including slot 2, call maybe_Screen3D_ClipEdgeNear
   exactly four times, which confirms they share one skeleton and differ
   only in what they interpolate [verified].

   Slot 2 is the odd one: it calls Color_Convert555ToSurface TWICE and
   has no emitter or walkers in its table slot. Still unread.


6.  The vertex record, and what +0x18 holds

   maybe_Screen3D_ClipEdgeNear (0x0049d8f0) settles it. To clip an edge
   against the near plane it must write every per-vertex attribute, so
   it names the whole record [verified]:

       out[0] = lerp(a.x, b.x, t);        // +0x00  view x
       out[1] = lerp(a.y, b.y, t);        // +0x04  view y
       out[2] = NEAR;                     // +0x08  view z
       out[6] = 1.0f / NEAR;              // +0x18  1/z
       out[4] = originX + ftol(...);      // +0x10  screen X
       out[5] = originY - ftol(...);      // +0x14  screen Y, flipped
       out[3] = ftol(...);                // +0x0c

   +--------+---------------------------------------------+------------+
   | Offset | Meaning                                     | Confidence |
   +========+=============================================+============+
   | +0x00  | view space x, float                         | verified   |
   +--------+---------------------------------------------+------------+
   | +0x04  | view space y, float                         | verified   |
   +--------+---------------------------------------------+------------+
   | +0x08  | view space z; tested against the near plane | verified   |
   +--------+---------------------------------------------+------------+
   | +0x0c  | light intensity, shade; see section 8       | verified   |
   +--------+---------------------------------------------+------------+
   | +0x10  | screen X, float, plus a viewport origin     | verified   |
   +--------+---------------------------------------------+------------+
   | +0x14  | screen Y, float, subtracted so Y runs down  | verified   |
   +--------+---------------------------------------------+------------+
   | +0x18  | 1/z                                         | verified   |
   +--------+---------------------------------------------+------------+

   The reciprocal is literal. The constant divided by z is
   _DAT_004d1f4c, which reads 0x3f800000, exactly 1.0f. So +0x18 is 1/z
   and nothing else. The near plane itself, DAT_00625774, is BSS and set
   at run time.

6.1.  So the second axis is perspective correction

   Slots 6 and 7 read 1/z per vertex and pass it to their emitters.
   Slots 4 and 5 do not. That makes the second axis affine versus
   PERSPECTIVE-CORRECT texture mapping [inferred, though a reciprocal
   depth leaves little else it could be].

   It is exactly the trade a 1997 software rasterizer makes. Affine
   interpolation is cheap and visibly wrong on large or steeply-angled
   polygons; perspective correction costs a divide. Having both,
   selected per primitive kind through the span table, lets the engine
   spend the divide only where it shows.

   Combined with the first axis, the four live pipelines are:

   +------+------------+---------------------+
   | Slot | Colour     | Texture mapping     |
   +======+============+=====================+
   | 4    | flat       | affine              |
   +------+------------+---------------------+
   | 5    | per vertex | affine              |
   +------+------------+---------------------+
   | 6    | flat       | perspective correct |
   +------+------------+---------------------+
   | 7    | per vertex | perspective correct |
   +------+------------+---------------------+

6.2.  A correction

   An earlier version of section 5 called the emitter's first six
   arguments three uv pairs. That was wrong. Fields +0x10 and +0x14 are
   screen X and Y, as ClipEdgeNear shows by writing a viewport origin
   into them.

   The argument COUNTS in section 5 are unaffected, since they were
   measured from each emitter's RET, and so is the 13 + 3 + 3 = 19
   arithmetic. Only the labelling of which triple was which was wrong.

   The trivial reject in section 4 reads differently with this in mind.
   It compares +0x10 and +0x14 as UNSIGNED INTEGERS against bounds,
   which works because for non-negative IEEE floats the bit pattern
   order matches the numeric order; the separate sign test catches
   negatives. A neat period trick, and independent confirmation that
   those fields are floats.


7.  Inside an emitter

   maybe_Screen3D_EmitTriFlatAffine (0x0049dde0), slot 4's emitter,
   settles the last question about the argument list and closes the loop
   back to the batch queue [verified].

       void emit(int x0, int y0, int x1, int y1, int x2, int y2,
                 void *texPage,
                 int u0, int v0, int u1, int v1, int u2, int v2)

   Its opening loop sorts the vertices by params 2, 4 and 6 while
   carrying params 1, 3 and 5 along. Sorting by Y with X in tow is what
   an edge walker does, so the first six arguments are screen
   coordinates. The remaining six are then interpolated down each edge
   into DAT_0068b018 and DAT_0068b01c, which makes them U and V.

7.1.  Texture coordinates are per face, not per vertex

   That raises an obvious question, because the vertex record in section
   6 has no UV field. The answer is that it does not need one. The setup
   reads UVs from the FACE, at face+0x14, and passes them in.

   This agrees exactly with the on-disk format. formats/mesh-3df-map.txt
   records the .map file as carrying four u and four v values per face
   record, not per vertex. The runtime layout mirrors the file layout,
   which is a satisfying cross-check between two independently derived
   documents.

7.2.  The batch record, from the producing end

   Having walked the triangle, the emitter appends a batch record for
   Screen3D_FlushSpans to drain later. The record is 0x24 bytes at
   DAT_00625790 and the count is DAT_006d1f78 [verified]:

   +--------+---------------------------+----------------------------------+
   | Offset | Field                     | Source                           |
   +========+===========================+==================================+
   | +0x00  | primitive kind            | a literal, per emitter           |
   +--------+---------------------------+----------------------------------+
   | +0x04  | span count                | spans emitted this triangle HALF |
   +--------+---------------------------+----------------------------------+
   | +0x08  | texture base              | g_texBase                        |
   +--------+---------------------------+----------------------------------+
   | +0x0c  | flat colour               | maybe_g_spanFlatColor            |
   +--------+---------------------------+----------------------------------+
   | +0x10  | texture palette           | maybe_g_texPalette               |
   +--------+---------------------------+----------------------------------+
   | +0x14  | UV step u, or persp u     | g_texStepU                       |
   +--------+---------------------------+----------------------------------+
   | +0x18  | UV step v, or persp v     | g_texStepV                       |
   +--------+---------------------------+----------------------------------+
   | +0x1c  | persp step w              | maybe_g_perspStepW               |
   +--------+---------------------------+----------------------------------+
   | +0x20  | flat shade, or shade STEP | maybe_g_edgeShade / shadeStep    |
   +--------+---------------------------+----------------------------------+

   Corrected in section 42. An earlier version of this table gave +0x04
   as the spans emitted for a TRIANGLE, omitted +0x10 and +0x1c, and
   named +0x00's source as a global. All three are wrong: the count is
   per triangle half, the two missing fields are restored by
   Screen3D_FlushSpans for the paletted and perspective kinds, and the
   kind is a literal each emitter stamps.

   The queue holds 1000 batches; reaching that count clears
   g_spanAccepting (0x006d20c0). CONFIRMED as the accepting flag, no
   longer inferred: maybe_Screen3D_EmitTriBlend both clears it at the
   cap and TESTS it before walking a triangle, and Screen3D_BeginFrame
   resets it every frame. See section 14 [verified].

   Section 1.3.2 of subsystems/pixel-format.txt derived this same record
   by reading Screen3D_FlushSpans, the consuming end. Every field this
   emitter writes is read back at the same offset, which is the
   strongest confirmation available without running the game.

   The flusher also reads two fields at +0x10 and +0x1c that this
   emitter never writes. Those belong to other primitive kinds, and the
   switch in Screen3D_FlushSpans selects which fields are meaningful per
   kind, so the record is a union rather than a fixed struct [inferred].

7.3.  Two details it confirms

   g_spanPatchDirty is raised immediately after DAT_00655d20 and
   DAT_00655d24 are computed, which is precisely the invariant claimed
   in subsystems/pixel-format.txt section 1.3.2: the flag goes up
   because a patched value has just changed.

   The emitter reads the FLAT colour maybe_g_spanFlatColor and never
   interpolates a colour, which confirms the first pipeline axis in
   section 5. A slot 5 or 7 emitter should interpolate three per-vertex
   colours instead; that remains unread.

   Edge X positions are carried as x * 0x2000, thirteen fractional bits,
   and each scanline sets maybe_g_spanRowPtr to the framebuffer row before
   calling through maybe_g_spanClipper.


8.  Gouraud confirmed, and what +0x0c really is

   Slot 5's emitter, maybe_Screen3D_EmitTriGouraudAffine (0x0049f1e0),
   takes 16 dwords: the same six screen coordinates, the texture page,
   six U and V values, and THREE more, one per vertex.

   Those three are interpolated exactly as U and V are. The opening sort
   swaps them alongside the others, a per-scanline step is computed, and
   the running value is advanced down each edge [verified]:

       DAT_0068b00c  = v0.extra;
       step          = (v2.extra - v0.extra) / dy;
       ... per scanline: DAT_0068b00c += step;

   Linear interpolation of a per-vertex value across the primitive. That
   is Gouraud, not per-vertex selection, and it is now verified rather
   than inferred.

8.1.  Following the value to its consumer

   The edge walker copies DAT_0068b00c into DAT_006d1f80 and clips it
   along x with its own step DAT_00655d30, in step with U and V.
   DAT_006d1f80 has many writers and exactly ONE reader:
   maybe_Screen3D_SpanShadedTex (0x004adbf0), the span function for
   primitive kind 0x14.

       texel = palette[ page[ ((v & 0xffffe01f) >> 5)
                              + (u >> 13) ] ];
       if (texel == 0)
           *dst = (*dst >> 1) & mask;         // darken
       else
           *dst = g_shadeLut[ ((t & 0x3e7ff) >> 11)
                            + ((texel & 0xf80f) >> 4) ]
                | (texel & 0x7ff);

   The interpolant indexes a shade lookup table at 0x004f62f0, labelled
   g_shadeLut, together with the texel's own colour bits. So it is a
   LIGHT INTENSITY.

8.2.  A correction to section 6

   Section 6 listed vertex +0x0c as an integer depth, averaged per
   primitive, marked [inferred]. That was wrong. It is a per-vertex
   SHADE, and the shade LUT is what proves it [verified]. The vertex
   record carries no depth at all beyond view z at +0x08 and 1/z at
   +0x18.

   This also sharpens the first pipeline axis. It is not flat versus
   per-vertex colour in the abstract; it is FLAT versus GOURAUD SHADING.
   Slot 4's setup averages +0x0c across the three vertices and the whole
   triangle gets one intensity. Slot 5's passes all three and the
   intensity varies per pixel.

8.3.  Two details in passing

   The transparent path in that span function does not skip the pixel. A
   texel of zero HALVES the destination instead, so kind 0x14 darkens
   what is already there. That reads as a shadow or dimming pass
   [inferred], and it is a different treatment of the transparent index
   from the hardware path in subsystems/d3d-textures.txt section 3,
   which discards it.

   Texture addressing uses thirteen fractional bits in u, which matches
   the 0x2000 fixed point the emitters carry for edge x. The v term is
   masked and shifted by five, so the page is 32 texels wide in the
   addressing arithmetic.


9.  Slot 2 is not dead: the untextured blend path

   maybe_Screen3D_SetupPrim0 (0x004a4820) sits in walker slot 2 with
   both edge walkers null, and the span table records read so far used
   only indices 0, 4, 5, 6 and 7. It looked like dead code. It is not.

   Reading the span table's source list to its -1 terminator gives 32
   records, and the last three include one that had been missed
   [verified]:

       key 0x0c   index 2   flag 0   span fn 0x004a4110

   So primitive kind 0x0c selects slot 2. A full census of the source
   list:

   +--------------------------+--------------------------+
   | Pipeline index           | Primitive kinds using it |
   +==========================+==========================+
   | 0, called directly       | 7                        |
   +--------------------------+--------------------------+
   | 2, SetupPrim0            | 1                        |
   +--------------------------+--------------------------+
   | 4, flat + affine         | 11                       |
   +--------------------------+--------------------------+
   | 5, Gouraud + affine      | 4                        |
   +--------------------------+--------------------------+
   | 6, flat + perspective    | 8                        |
   +--------------------------+--------------------------+
   | 7, Gouraud + perspective | 1                        |
   +--------------------------+--------------------------+

   Slot 2 is the rarest live path, one kind out of 32, which is why it
   looked absent.

9.1.  What kind 0x0c draws

   Its span function, maybe_Screen3D_SpanBlendFlat (0x004a4110), has no
   texture lookup at all [verified]:

       *dst = ((*dst >> 1) & g_halveMask) + maybe_g_spanFlatColor;

   Halve the destination and add a constant. That is a 50 per cent blend
   with a flat colour, written as dst/2 + src/2 with the source pre-
   halved. g_halveMask (0x0050270c) is the precomputed mask that clears
   the bits which bleed between channels on a right shift, the same
   correction maybe_Screen3D_FadeRect computes inline from g_shlR and
   g_shlG.

   That explains the oddity noted earlier, that SetupPrim0 calls
   Color_Convert555ToSurface twice where the other setups call it once:
   it needs both the colour and its halved form [inferred].

   So kind 0x0c is an UNTEXTURED TRANSLUCENT POLYGON. It also explains
   the null walkers. Its emitter chain, maybe_Screen3D_EmitTriBlend
   (0x004a4350) into maybe_Screen3D_SpanBlendOrQueue (0x004a4190), calls
   its span filler directly instead of going through maybe_g_spanClipper, so it
   has no use for the walker indirection.

9.2.  The span buffer, from the producing end

   maybe_Screen3D_SpanBlendOrQueue has two modes. When DAT_0062e444 is
   zero it fills immediately. Otherwise it walks the span list and
   RECORDS each span into a buffer rather than drawing [verified]:

   +--------+--------------------------------------------------+
   | Offset | Field                                            |
   +========+==================================================+
   | +0x04  | framebuffer row pointer, from maybe_g_spanRowPtr |
   +--------+--------------------------------------------------+
   | +0x08  | x start, u16                                     |
   +--------+--------------------------------------------------+
   | +0x0a  | x end, u16                                       |
   +--------+--------------------------------------------------+

   Records are 0x1c bytes at g_spanBuffer (0x0068b040), the count is
   DAT_006d1048, and the capacity is 0x2800, which is 10240 spans.
   Reaching it clears DAT_006d20c0, the same stop-accepting flag the
   batch queue uses at 1000 batches.

   Those are exactly the fields Screen3D_FlushSpans reads back at
   DAT_0068b044, DAT_0068b048 and DAT_0068b04a. As with the batch record
   in section 7.2, producer and consumer agree offset for offset,
   derived independently from opposite ends.


10.  The eight span clippers

   CORRECTION. An earlier version of this section called these edge
   walkers and described them only by the interpolants they carry. That
   was wrong about what they do. They do not walk polygon edges.
   Applying a struct to the pointer they iterate made the algorithm
   legible and it is a span buffer [verified].

   Each is called with one scanline's x range already computed, in
   DAT_00624b0c and DAT_00624b44 as 19.13 fixed point. It clips that
   range against a per-scanline list of ranges that are still FREE, and
   emits only the parts that survive.

10.1.  The free list

   The node is eight bytes, applied in the database as MR_ClipSpan
   [verified]:

   +--------+-------+------+----------------------------------+
   | Offset | Type  | Name | Meaning                          |
   +========+=======+======+==================================+
   | +0x00  | short | x0   | left edge                        |
   +--------+-------+------+----------------------------------+
   | +0x02  | short | x1   | right edge                       |
   +--------+-------+------+----------------------------------+
   | +0x04  | ptr   | next | next free range, NULL at the end |
   +--------+-------+------+----------------------------------+

   Nodes come from g_spanFreePool at 0x0060d3d0 by bump allocation,
   counted by g_spanFreeCount. Heads live in g_spanScanlineHead at
   0x00623bd8, one per scanline. Screen3D_BeginFrame seeds each scanline
   with a single node covering x = 0 to width, so every scanline starts
   wholly free.

   That is hidden-surface removal by span buffer, with the scene drawn
   front to back: whatever is drawn first claims the pixels and later
   polygons are clipped out of them. It also explains why there is no
   z-buffer in the software path.

   CORRECTION - an earlier version cited 'the depth field in the batch
   record' as further evidence here. There is no depth field: batch
   +0x20 carries a SHADE term, per section 18. The front-to-back
   conclusion is unaffected, since it rests on the free-list algorithm
   itself, but that supporting clause was wrong.

   The pool's declared length is not established. The next referenced
   global sits 0x16808 bytes above it, which is 11521 nodes, but that is
   an upper bound and not a size read from the code.

10.2.  Now versus defer

   Both variants clip against the same list. They differ in what they do
   with the result [verified]:

   +---------+--------------------------------------------------+--------------------------------------------------+
   | Variant | Emits                                            | Free list                                        |
   +=========+==================================================+==================================================+
   | Now     | draws each visible sub-range at once through     | CONSUMED: nodes are shrunk, unlinked, or split   |
   |         | DAT_00655d08                                     | by allocating from the pool                      |
   +---------+--------------------------------------------------+--------------------------------------------------+
   | Defer   | writes a 0x1c-byte record into g_spanBuffer      | left unchanged                                   |
   +---------+--------------------------------------------------+--------------------------------------------------+

   A second correction. The earlier version said the immediate variant
   was identified by testing DAT_0062e444. Both variants test it, so it
   is not the discriminator. It is g_spanBufferEnabled: when it is 0 the
   free list is bypassed altogether and the span is only clamped to the
   screen.

   The deferred record is 0x1c bytes and the buffer holds 0x2800 of
   them, 10240. Reaching the cap clears g_spanAccepting. The clipper
   writes x0 at +0x08, x1 at +0x0a, and the u and v start values at
   +0x0c and +0x10.

10.3.  What each pair carries

   The interpolant table from the earlier version still holds; it was
   the description of the mechanism that was wrong, not the measurement
   [verified].

   +------+------------+------------+------------------------+
   | Slot | Immediate  | Deferred   | Interpolants carried   |
   +======+============+============+========================+
   | 4    | 0x0049d9e0 | 0x0049dbf0 | U, V                   |
   +------+------------+------------+------------------------+
   | 5    | 0x0049ed50 | 0x0049efb0 | U, V, shade            |
   +------+------------+------------+------------------------+
   | 6    | 0x004a0260 | 0x004a04d0 | U, V, 1/z terms        |
   +------+------------+------------+------------------------+
   | 7    | 0x004a1770 | 0x004a1a30 | U, V, shade, 1/z terms |
   +------+------------+------------+------------------------+

10.4.  The specialised path: three layers, eight kinds

   Screen3D_DispatchPrimitive has two paths. One is the table-driven one
   described above. The other is a switch on the primitive kind that
   calls a specialised chain, and those chains account for the sixteen
   extra clippers that walk the same free list [verified].

   Each chain is three layers deep, and naming them made the shape
   plain:

       Screen3D_DispatchPrimitive   switch on kind
         Screen3D_DrawPrimKn        one primitive; calls Tri twice
           Screen3D_TriKn           ONE triangle; the real edge walker
             Screen3D_ClipSpanKn    ONE scanline; clips the free list

   +--------+------------+------------+------------+------------+
   | Kind   | DrawPrim   | Tri        | ClipSpan   | Span loop  |
   +========+============+============+============+============+
   | 1 Full | 0x004a7b70 | 0x004a74e0 | 0x004a72d0 | 0x004a7240 |
   +--------+------------+------------+------------+------------+
   | 1 Half | 0x004a8c70 | 0x004a85e0 | 0x004a83d0 | 0x004a8340 |
   +--------+------------+------------+------------+------------+
   | 2 Full | 0x004ab070 | 0x004aa940 | 0x004aa750 | 0x004aa6c0 |
   +--------+------------+------------+------------+------------+
   | 2 Half | 0x004ac1f0 | 0x004abac0 | 0x004ab8d0 | 0x004ab840 |
   +--------+------------+------------+------------+------------+
   | 3      | 0x004a6a50 | 0x004a62d0 | 0x004a6080 | -          |
   +--------+------------+------------+------------+------------+
   | 4      | 0x004ad410 | 0x004acc00 | 0x004ac9d0 | -          |
   +--------+------------+------------+------------+------------+
   | 9      | 0x004ae730 | 0x004adf10 | 0x004adce0 | -          |
   +--------+------------+------------+------------+------------+
   | 42     | 0x004a9df0 | 0x004a96c0 | 0x004a94d0 | -          |
   +--------+------------+------------+------------+------------+

   The middle layer is where the edge walking actually happens, and that
   corrects the terminology once more. Screen3D_TriKn takes sixteen
   arguments, three vertices' worth of screen position and interpolants;
   sorts them by y with a swap loop; computes edge gradients in 19.13
   fixed point; handles the upper and lower halves; and for each
   scanline leaves the x range in DAT_00624b0c and DAT_00624b44 before
   calling its clipper. So section 10 was right that something walks
   edges, and wrong about which layer does it [verified].

   Each DrawPrim calls its Tri exactly twice, so a primitive is two
   triangles [inferred].

   Kinds 1 and 2 have two variants each, chosen on *(int *)(vertexBase +
   0xc) > 0x3dfff - the first vertex's +0x0c, its light intensity,
   against 31.0 in the same 19.13 fixed point. An earlier version of
   this note could not say what that selected. It selects BRIGHTNESS,
   and nothing else [verified].

   Diffing the pair settles it. Screen3D_TriK1Full and
   Screen3D_TriK1Half are 463 instructions each, instruction for
   instruction identical, differing only in which clipper they call. The
   clippers differ only in which span routine they call. The span
   routines differ in one operation:

       Full:  *dst = palette[texel]
       Half:  *dst = palette[texel] >> 1 & g_halveMask

   g_halveMask clears the low bit of each packed colour channel, so the
   shift is a correct 50 percent darken - the same primitive
   maybe_Screen3D_SpanBlendFlat uses.

   So this is a two-level lighting approximation. Kinds that carry no
   per-pixel shade get one bright and one dim rendering, chosen once per
   primitive from a single vertex's intensity. The engine implements it
   by duplicating the entire three-layer chain rather than branching
   inside the per-pixel loop, which on a 1997 CPU is the cheaper trade
   [inferred].

   Every kind on this path can be named the same way, by reading the
   innermost span routine [verified]:

   +------+-----------------------------------------+------------------------------+
   | Kind | What it is                              | Span routine                 |
   +======+=========================================+==============================+
   | 1    | opaque textured; every texel written    | 0x004a7240 / 0x004a8340      |
   +------+-----------------------------------------+------------------------------+
   | 2    | colour-keyed; palette entry 0 skipped   | 0x004aa6c0 / 0x004ab840      |
   +------+-----------------------------------------+------------------------------+
   | 3    | OCCLUDER; writes no pixels at all       | 0x004a6070, a RET            |
   +------+-----------------------------------------+------------------------------+
   | 4    | deferred shaded; immediate path stubbed | 0x004ac9c0, a RET            |
   +------+-----------------------------------------+------------------------------+
   | 9    | Gouraud shaded textured                 | maybe_Screen3D_SpanShadedTex |
   +------+-----------------------------------------+------------------------------+
   | 42   | textured stencil, filled flat           | 0x004a9440                   |
   +------+-----------------------------------------+------------------------------+

   Kind 3 is the interesting one. Its span routine is a single 0xc3, a
   bare RET, yet Screen3D_ClipSpanK3 is a full Now clipper: it walks the
   free list and CONSUMES coverage exactly as the drawing kinds do,
   shrinking, unlinking and splitting nodes, then calls a routine that
   writes nothing.

   So kind 3 claims pixels in the span buffer without painting them.
   That is an occluder - invisible geometry whose only job is to hide
   what is behind it. With a span buffer it costs almost nothing, which
   is why the technique is worth having [inferred, though a coverage-
   consuming primitive with a RET for a pixel loop leaves little else it
   could be].

   Kind 4's RET is a different case. Its clipper is a Defer variant, so
   the stub is reached only on the bypass path taken when
   g_spanBufferEnabled is 0. Normally it queues span records carrying
   the shade term at record +0x18 and the flusher paints them. The
   consequence is still worth noting: with the span buffer disabled,
   kind 4 renders nothing.

   Kind 42 uses its texture purely as a mask. The texel value decides
   WHETHER to write, never WHAT to write; every covered pixel gets the
   flat colour from maybe_g_spanFlatColor. A textured stencil, which is how a
   1997 engine draws a shadow [inferred].

   Every clipper in these chains differs from the tabled ones in one way
   only: it calls its span routine DIRECTLY rather than indirectly
   through DAT_00655d08. Duplicating the clipper per kind buys one fewer
   indirect call per scanline, and it is why the walker table holds only
   five records while twenty-four clippers exist.

10.5.  There is no screen clear

   Screen3D_EndFrame at 0x0049b0e0 closes the loop the free list opened
   [verified]. Before unlocking the surface it walks each scanline's
   remaining free ranges - the pixels no polygon ever covered - and
   fills them in the frame buffer with g_backgroundColor (0x0065f0d8),
   then clears the head.

   So the engine never clears the screen at the start of a frame.
   Screen3D_BeginFrame marks every scanline wholly free, the clippers
   carve out what gets drawn, and Screen3D_EndFrame paints only what is
   left. The span buffer pays for itself twice: hidden-surface removal
   on the way in, and no full-screen clear on the way out.

11.  Where the viewport comes from

   Screen3D_SetViewport at 0x00499ba0 establishes everything the
   rasterizer measures itself against. Its five callers include
   Menu_SetPage, which is why entering the menus resizes the world
   [verified].

   +------------------+--------------------------+-----------------------------------------+
   | Global           | Value                    | Used by                                 |
   +==================+==========================+=========================================+
   | g_viewWidth      | width                    | batch and clip arithmetic               |
   +------------------+--------------------------+-----------------------------------------+
   | g_viewHeight     | height                   | Screen3D_BeginFrame, one free list each |
   +------------------+--------------------------+-----------------------------------------+
   | g_viewMaxX       | width - 1                | every span clipper's right bound        |
   +------------------+--------------------------+-----------------------------------------+
   | g_viewMaxY       | topMargin + height - 1   | vertical clip                           |
   +------------------+--------------------------+-----------------------------------------+
   | g_viewCentreX    | width / 2                | projection centre                       |
   +------------------+--------------------------+-----------------------------------------+
   | g_viewCentreY    | topMargin + height / 2   | projection centre                       |
   +------------------+--------------------------+-----------------------------------------+
   | g_scanlineOffset | per-scanline byte offset | Screen3D_EndFrame                       |
   +------------------+--------------------------+-----------------------------------------+

   g_scanlineOffset is the interesting one. It is filled as
   (letterboxSkip + i) * g_frameStridePx for each scanline, so consumers
   address rows through the table rather than by multiplying. That is
   what lets the letterbox exist without the span buffer or the clippers
   knowing about it: they work in view coordinates and the table maps
   those onto the frame buffer.

11.1.  Widescreen is letterboxing

   With the widescreen flag set the height is scaled down and the
   difference is split into equal top and bottom margins [verified].
   There is no change of projection and no change of field of view, so
   16:9 here means the same picture with black bars rather than more of
   the world.

   The port widens instead of cropping; see subsystems/projection.txt
   7.1.  [OPTIONS] Wide169Crop=1 asks for this behaviour.

11.2.  A hang on a failed mode set

   The mode-setting path is a do-while(true). If the mode set fails the
   code overwrites the requested size with 640x480 and loops to retry
   [verified]:

       do {
           if (!g_ownsDisplayMode) { ...viewport...; return 1; }
           if (SetDisplayMode(w, h, bpp)) { ...viewport...; return 1; }
           w = 0x280; h = 0x1e0;          /* 640x480, then retry */
       } while (true);

   There is no attempt counter and no other exit. A machine that can set
   neither the requested mode nor 640x480 at the configured depth spins
   here forever instead of reporting an error.

   Given the engine is pinned to 16-bit colour, and that
   subsystems/d3d-execute-buffers.txt section 6.1 shows the same depth
   demanded of the Direct3D device, this is a plausible failure on
   modern hardware where 16-bit modes are often unavailable. The symptom
   would be a hang, not a message.

12.  What this means for the port

   This layer is ordinary geometry code: depth averaging, near-plane
   clipping, trivial rejection, quad splitting. It contains no self-
   modifying code, and its only colour work is one call to
   Color_Convert555ToSurface, which is tier 1 and needs no change.

   So the rewrite boundary is clean. Everything above the emitter is
   portable arithmetic that a modern renderer would keep or replace with
   equivalent logic; everything from the emitter down is the self-
   patching, five-bit-locked machinery described in subsystems/pixel-
   format.txt.

11.  The flat span filler, and how much MMX really matters

   maybe_Screen3D_ClipSpanFlatMMX at 0x004a31d0 is the flat-colour member
   of the clipper family. It was found only after a boundary repair -
   its recorded entry was 11 bytes late, because it is reached through a
   function pointer and so has no call reference. See ghidra-db-
   repairs.txt [verified].

   It is installed into maybe_g_spanClipper by FUN_004a3950 and
   FUN_004a3cf0, each of which writes maybe_g_spanFlatColor immediately
   before. It carries no interpolants, which is why it does not appear
   in the slot table of section 10.3.

   Its two modes match section 10.2 exactly, confirming that structure
   from a third function:

   o g_spanBufferEnabled == 0: clamp the range to [0, g_viewMaxX + 1]
     and fill. The free list is not consulted.

   o otherwise: walk the MR_ClipSpan list for the scanline and fill only
     free parts, shrinking, unlinking or SPLITTING nodes as it goes. A
     split bump-allocates from g_spanFreePool, which is the allocation
     site section 10.1 describes.

11.1.  The fill is MMX

   The inner loop writes four pixels per store [verified]:



       MOVD      MM0, EAX      ; colour, already duplicated to 32 bits

       PUNPCKLWD MM0, MM0      ; broadcast into four 16-bit lanes

       MOVQ      [EDI], MM0    ; 8 bytes = 4 pixels



   preceded by a scalar prologue that writes up to three pixels to reach
   8-byte alignment, and followed by a scalar tail for the remainder.
   That is the classic aligned-bulk-fill shape.

11.2.  How much MMX is actually format-dependent

   Worth measuring, because the command-line flag list advertises an MMX
   switch and it would be easy to assume the rasterizer is full of
   format-specific vector code. It is not. Every MMX instruction in
   .text [verified]:

   +-----------------------------+-----+------------------------------------+
   | Function                    | MMX | What it is                         |
   +=============================+=====+====================================+
   | FUN_0043f0f0                | 175 | bulk MOVQ copy, in menu/bitmap.cpp |
   +-----------------------------+-----+------------------------------------+
   | maybe_Screen3D_ClipSpanFlatMMX | 15  | the flat fill above             |
   +-----------------------------+-----+------------------------------------+
   | FUN_004a3180                | 3   | a small fill, unread               |
   +-----------------------------+-----+------------------------------------+
   | FUN_004a34f0                | 1   | unread                             |
   +-----------------------------+-----+------------------------------------+
   | maybe_Screen3D_EmitTriBlend | 1   | unread                             |
   +-----------------------------+-----+------------------------------------+

   195 instructions in five functions, and the mnemonic breakdown is
   MOVQ 180, MOVD 6, PUNPCKLWD 6, EMMS 3.

   So 180 of 195 are plain 8-byte MOVQ copies, which are FORMAT-AGNOSTIC
   - copying eight bytes does not care how many pixels they are. The
   only format-dependent idiom is the MOVD + PUNPCKLWD colour broadcast,
   and there are just six of those. The MMX exposure of a 32-bit port is
   therefore six sites, not a rewrite of the vector code [verified].

   ANSWERED, and the suspicion was wrong. EMMS appears 3 times for 5
   MMX-using functions because the LEAF fillers deliberately leave MMX
   state set and the DRIVER clears it once per triangle.
   maybe_Screen3D_TriFlat issues EMMS after its whole scanline loop, not
   inside it. See section 11.5 - the pairing is correct and there is no
   missing-EMMS defect [verified].

11.3.  What is hardcoded to 16 bpp here

   +----------------------------+---------+------------------------------+
   | Construct                  | Count   | Why it breaks at 32 bpp      |
   +============================+=========+==============================+
   | x * 2 + maybe_g_spanRowPtr | many    | pixel stride is 2 bytes      |
   +----------------------------+---------+------------------------------+
   | MOV word ptr [..], reg     | 5       | scalar store is 16-bit       |
   +----------------------------+---------+------------------------------+
   | PUNPCKLWD broadcast        | 1       | assumes 4 pixels per 8 bytes |
   +----------------------------+---------+------------------------------+
   | MOVQ [EDI], MM0            | several | writes exactly 4 pixels      |
   +----------------------------+---------+------------------------------+

   The colour VALUE is not a problem: maybe_g_spanFlatColor is produced
   by Color_Convert555ToSurface and is already correct for whatever the
   surface format is. It is the pixel SIZE that is baked in. That
   distinction is the useful one for the port - the palette and
   conversion layer generalises, the addressing and store width do not.


11.4.  The flat chain, all three layers

   maybe_Screen3D_TriFlat at 0x004a34f0 is the middle layer, and with it
   the flat path matches the three-layer shape of section 10.4 exactly
   [verified]:



       FUN_004a3950 / FUN_004a3cf0     set colour, install filler

         maybe_Screen3D_TriFlat        ONE triangle, called TWICE

           maybe_g_spanClipper()        ONE scanline, via pointer

             = maybe_Screen3D_ClipSpanFlat



   Both DrawPrim-layer functions call the Tri layer exactly twice,
   confirming from a second family that a primitive is two triangles.
   The difference from the Kn chains is that the flat path reaches its
   filler through a POINTER, maybe_g_spanClipper, rather than calling it
   directly - which is what section 9.1 meant about the walker
   indirection.

   The signature is six integers, three screen positions, and no
   interpolants at all. That is the cleanest confirmation yet of the
   first pipeline axis: flat primitives carry colour in a global, not
   per vertex.

11.4.1.  How it walks

   Worth recording because the clipping is neater than expected
   [verified]:

   o The vertex sort is a ROTATION, not a sort. It rotates the three
     vertices until y0 is smallest; which of y1 and y2 is then the
     middle selects the long edge. Two code paths follow, one per case.

   o Gradients are (dx * 0x2000) / dy - 19.13 fixed point, the same
     format section 10 records for the x range.

   o Top clipping PRE-STEPS the DDA: if y0 < 0 the accumulators are
     advanced by -y0 * gradient before the loop, rather than the loop
     testing each scanline. Bottom clipping just shortens the count.
     There is no per-pixel clip test.

   o Each scanline sets g_spanCurScanline to the free-list head and
     maybe_g_spanRowPtr to the row, then calls the filler ONLY IF the
     head is non-null. A scanline whose spans are all claimed costs one
     pointer test - that is the span buffer paying for itself.

11.5.  The MMX contract

   maybe_g_useMMX at 0x004dbcf4 gates both halves of the MMX usage, and
   that is what makes the EMMS count correct [verified]:

   +------------------------+-------------------------------------+
   | Site                   | Gated action                        |
   +========================+=====================================+
   | 0x004a399a, 0x004a3dd1 | install the MMX filler              |
   +------------------------+-------------------------------------+
   | 0x004a3879             | EMMS after the scanline loop        |
   +------------------------+-------------------------------------+
   | 0x004a46ef             | EMMS in maybe_Screen3D_EmitTriBlend |
   +------------------------+-------------------------------------+
   | 0x0043f139             | the bulk MOVQ copier                |
   +------------------------+-------------------------------------+

   It is written twice by Main_InitAndParseCommandLine, at 0x00414fc5
   and 0x00414fd7, and read by MenuPage13_Diagnostics_Tick, so it is a
   command-line switch that the diagnostics page reports - almost
   certainly the -mmx flag from the block at 0x004dc664 [verified that
   the parser writes it; inferred as to which flag].

   The design is: when MMX is off, the MMX filler is never installed and
   EMMS is never issued. When it is on, the leaf filler uses MMX freely
   and the driver clears the state ONCE PER TRIANGLE rather than once
   per scanline. So maybe_Screen3D_ClipSpanFlatMMX containing MMX but no
   EMMS is correct by construction.

   FOUND - see section 11.7. The non-MMX default is
   maybe_Screen3D_ClipSpanFlatScalar at 0x004a2f10, installed
   UNCONDITIONALLY a few instructions before the MMX override. It was
   0x25 bytes above the window examined at the time. FUN_004a3180 is
   unrelated [verified].

11.6.  16 bpp in the walker

   +-------------------------+-------------+-------------------+
   | Construct               | Where       | Why it breaks     |
   +=========================+=============+===================+
   | g_scanlineOffset[y] * 2 | row setup   | 2 bytes per pixel |
   +-------------------------+-------------+-------------------+
   | g_frameStridePx * 2     | row advance | 2 bytes per pixel |
   +-------------------------+-------------+-------------------+

   Only two, and both are the same assumption. The walker is otherwise
   entirely format-agnostic - it deals in x, y and fixed point. Combined
   with section 11.3 that gives a precise account of the flat path: the
   geometry generalises for free, and the 16-bit dependency is confined
   to row addressing in the walker and to the store width in the filler.


11.7.  The scalar default, and how the filler is chosen

   maybe_Screen3D_ClipSpanFlatScalar at 0x004a2f10 is the non-MMX
   default. Both DrawPrim-layer functions install it unconditionally and
   then overwrite the pointer when MMX is on [verified]:



       MOV [maybe_g_spanClipper], 0x4a2f10   ; scalar, always

       MOV EAX, [maybe_g_useMMX]

       TEST EAX, EAX

       JZ   skip

       MOV [maybe_g_spanClipper], 0x4a31d0   ; MMX, overrides

     skip:

   So the pointer is always valid and the MMX variant is a pure opt-in
   override. There is no third filler and no CPU-detect branch at this
   level - the detection happened earlier, in whatever writes
   maybe_g_useMMX.

11.7.1.  The two fillers differ only in the inner loop

   Everything else is identical - the same 19.13 unpack of
   maybe_g_spanXLeft and maybe_g_spanXRight, the same
   g_spanBufferEnabled two-mode split, the same MR_ClipSpan free-list
   walk with shrink, unlink and split [verified].

   +------------+-------------------+----------------------+
   |            | Scalar 0x004a2f10 | MMX 0x004a31d0       |
   +============+===================+======================+
   | align to   | 4 bytes           | 8 bytes              |
   +------------+-------------------+----------------------+
   | prologue   | up to 1 pixel     | up to 3 pixels       |
   +------------+-------------------+----------------------+
   | bulk store | 32-bit, 2 pixels  | MOVQ, 4 pixels       |
   +------------+-------------------+----------------------+
   | tail       | 1 pixel if odd    | up to 3 pixels       |
   +------------+-------------------+----------------------+
   | EMMS       | n/a               | issued by the caller |
   +------------+-------------------+----------------------+

11.7.2.  Why the colour global is a dword

   maybe_g_spanFlatColor holds the 16-bit pixel DUPLICATED into both
   halves, and that is what makes both fillers cheap [verified]. Both
   DrawPrim functions build it the same way:



       CALL Color_Convert555ToSurface   ; -> 16-bit pixel in AX

       AND  EAX, 0xffff

       SHL  ECX, 0x10

       OR   ECX, EAX                    ; (c << 16) | c

       MOV  [maybe_g_spanFlatColor], ECX



   The scalar filler then writes that dword directly as two pixels; the
   MMX filler reaches four lanes from one MOVD plus PUNPCKLWD. Neither
   has to duplicate anything per span.

   CORRECTION. An earlier note said the two DrawPrim functions differ in
   how they obtain the colour, one storing a register directly and the
   other combining components. They do not - both run the same sequence
   above, and the apparent difference was two different points in it.
   What actually distinguishes the two functions is still unestablished.

   PORT: the duplication is itself a 16 bpp assumption. At 32 bpp one
   pixel fills the dword, so the scalar bulk loop becomes one pixel per
   store and the MMX loop two per MOVQ - both bulk paths change shape,
   not just their width.

11.7.3.  A third installer, and the scatter trap

   Screen3D_DispatchPrimitive also writes maybe_g_spanClipper, at
   0x004af0c9, from the walker table at 0x004f1ee0. Each 16-byte record
   is {key, draw, fillerNow, fillerDefer} and the dispatcher picks
   fillerNow or fillerDefer on a flag before calling draw [verified].

   Reading that table statically is a trap, and
   Screen3D_ScatterTableByKey already carries a plate comment saying so:
   at startup each record is MOVED to table[key], so the static order is
   meaningless and only the key field gives the index. Accounting for
   that, the live entries are:

   +-----+---------------------------+-----------+-------------+
   | Key | draw                      | fillerNow | fillerDefer |
   +=====+===========================+===========+=============+
   | 2   | maybe_Screen3D_SetupPrim0 | -         | -           |
   +-----+---------------------------+-----------+-------------+
   | 4   | maybe_Screen3D_SetupPrim1 | Walk4Now  | Walk4Defer  |
   +-----+---------------------------+-----------+-------------+
   | 5   | maybe_Screen3D_SetupPrim2 | Walk5Now  | Walk5Defer  |
   +-----+---------------------------+-----------+-------------+
   | 6   | maybe_Screen3D_SetupPrim3 | Walk6Now  | Walk6Defer  |
   +-----+---------------------------+-----------+-------------+
   | 7   | maybe_Screen3D_SetupPrim4 | Walk7Now  | Walk7Defer  |
   +-----+---------------------------+-----------+-------------+

   which agrees with the slot table in section 10.3, independently
   derived. Key 2 has NO fillers, which is consistent: that entry's draw
   function is expected to install its own, exactly as the flat DrawPrim
   pair does.

   Two functions sit immediately past the end of the 12-entry walker
   table, at 0x004f1fa4 and 0x004f1fa8. They are now identified as
   maybe_Screen3D_SpanFlatScalar and maybe_Screen3D_SpanFlatMMX - see
   section 11.8 [verified].


11.8.  The extent pair is a calling convention

   The two orphans turned out to be the key to a structural fact that
   had not been stated anywhere: maybe_g_spanFillLeft and
   maybe_g_spanFillRight are not bookkeeping. They are HOW A CLIPPED
   SUB-SPAN IS PASSED FROM A CLIPPER TO A FILLER [verified].

   Cross-referencing both globals over the whole rasterizer gives a
   clean split. Every ClipSpan* function WRITES the pair; every Span*
   filler READS it and takes no arguments at all:

   +-----------------------------+-------------------------------+
   | Writes the pair             | Reads the pair                |
   +=============================+===============================+
   | Screen3D_ClipSpanK1Full     | Screen3D_SpanTexK1Full        |
   +-----------------------------+-------------------------------+
   | Screen3D_ClipSpanK1Half     | Screen3D_SpanTexK1Half        |
   +-----------------------------+-------------------------------+
   | Screen3D_ClipSpanK2Full     | Screen3D_SpanTexKeyedK2Full   |
   +-----------------------------+-------------------------------+
   | Screen3D_ClipSpanK2Half     | Screen3D_SpanTexKeyedK2Half   |
   +-----------------------------+-------------------------------+
   | Screen3D_ClipSpanK42        | Screen3D_SpanStencilFlatK42   |
   +-----------------------------+-------------------------------+
   | the Walk4-7 Now/Defer pairs | SpanBlendFlat, SpanBlend1/2   |
   +-----------------------------+-------------------------------+
   | ClipSpanFlatScalar / MMX    | SpanCopyTexels, SpanShadedTex |
   +-----------------------------+-------------------------------+

   Screen3D_FlushSpans also writes the pair, which is consistent:
   replaying a deferred span means restoring the extent before calling a
   filler.

   This explains something that had been noted as odd twice already.
   Every Span* filler has ZERO call references, and a scan for zero-
   reference functions in the 0x004a0000 range returned a long list of
   them. They are not dead - they are reached through g_spanTable, which
   Screen3D_ScatterTableByKey rearranges at startup, so no static call
   edge exists.

   For the reconstruction this matters more than it looks. Two globals
   carrying a live argument between two layers is exactly the sort of
   thing that gets 'cleaned up' into parameters during transcription,
   which would be a behaviour change if anything else reads them between
   the write and the call. Rule 5 in CLAUDE.md applies: leave it as it
   is until the subsystem is fully understood.

11.8.1.  The two orphans

   maybe_Screen3D_SpanFlatScalar at 0x004a2ed0 and
   maybe_Screen3D_SpanFlatMMX at 0x004a3180 are the flat members of the
   Span* family: they read the extent, fill it, and do no clipping. Each
   is byte-for-byte the inner loop of its ClipSpanFlat counterpart with
   the free-list walk removed [verified].

   The four form a matched set, and the addresses pair them - the bare
   fill immediately precedes the clipping version in each case, so they
   were written together:

   +--------+------------+---------------------------+
   |        | bare fill  | with span-buffer clipping |
   +========+============+===========================+
   | scalar | 0x004a2ed0 | 0x004a2f10                |
   +--------+------------+---------------------------+
   | MMX    | 0x004a3180 | 0x004a31d0                |
   +--------+------------+---------------------------+

   Both bare versions are UNREACHABLE in the shipped build. A scan of
   the entire image finds each pointer exactly once, at 0x004f1fa4 and
   0x004f1fa8. Those four dwords read {0, 0x004a2ed0, 0x004a3180, 0} -
   the shape of a table record naming a scalar and an MMX filler - but
   they sit past the end of the walker table, which is 12 entries ending
   at 0x004f1fa0, and they are not in g_spanTable either. Nothing reads
   that memory [verified].

   So it is a record that was written and never wired up. Worth noting
   that the walker table is not full either: its source list terminates
   after five records, leaving seven of its twelve slots unused.
   Whatever this pair was for, the table it belonged to had room.

   They are excluded from the port. Recording them matters only so that
   a future pass does not spend time wondering why two well-formed
   fillers have no callers.


12.  The Span* filler family: six affine/perspective pairs

   Section 11.8 established that Screen3D_Span* fillers take no
   arguments and read the extent from the globals. Reading one of them
   in full, maybe_Screen3D_SpanStencilFlatPersp at 0x004a5150, shows the
   family has a regular two-by-six shape [verified].

   +-------------------------+------+-----------------------------+------+
   | Affine                  | size | Perspective                 | size |
   +=========================+======+=============================+======+
   | FUN_004a50c0            | 134  | 0x004a5150 StencilFlatPersp | 472  |
   +-------------------------+------+-----------------------------+------+
   | FUN_004a5330            | 125  | FUN_004a53b0                | 460  |
   +-------------------------+------+-----------------------------+------+
   | FUN_004a5580            | 129  | FUN_004a5610                | 469  |
   +-------------------------+------+-----------------------------+------+
   | FUN_004a57f0            | 151  | FUN_004a5890                | 485  |
   +-------------------------+------+-----------------------------+------+
   | Screen3D_SpanCopyTexels | 391  | FUN_004a5c40                | 455  |
   +-------------------------+------+-----------------------------+------+
   | FUN_004a5e10            | 128  | FUN_004a5e90                | 465  |
   +-------------------------+------+-----------------------------+------+

   The two are told apart mechanically: every function in the right-hand
   column contains a CMP against 0x10 and none in the left-hand column
   does. That is the 16-pixel subdivision, so the right column is
   perspective-correct and the left is affine. The pairs are adjacent in
   address order, affine first, so each pair was written together.

   Screen3D_SpanCopyTexels, named in earlier work, sits in an affine
   slot, which anchors the reading independently.

12.1.  Perspective correction by 16-pixel subdivision

   The standard technique of the period, and worth recording exactly
   because a port will not reproduce it [verified]:



       while (count > 0) {

           if (count >= 16) {

               advance the three float accumulators by one step

               u1,v1 = ftol(perspective divide)

               du = (u1 - u0) >> 4;  dv = (v1 - v0) >> 4;

               n = 16;

           } else {

               scale the step by count * maybe_g_subdivRecip

               u1,v1 = ftol(...);  n = count;

           }

           count -= n;

           inner loop of n pixels, stepping u,v linearly

       }



   One divide per sixteen pixels, linear interpolation between.
   maybe_g_subdivRecip at 0x004d1fb8 is a DOUBLE holding 0.0625; reading
   only its low dword shows 0.0, which is misleading.

   RESOLVED - see section 16.3. The accumulators are maybe_g_perspU
   (0x006d1054), maybe_g_perspV (0x006d1f84) and maybe_g_perspW
   (0x006d20ac), stepped by maybe_g_perspStepU, ...V and ...W. They were
   identified by positional aliasing in the batch and span unions, not
   by reading the arithmetic.

12.2.  A stencil, not a texture blit

   maybe_Screen3D_SpanStencilFlatPersp does NOT write the texel it
   reads. The texel is a mask and the colour is the flat one [verified]:



       if (texel != 0) *dst = maybe_g_spanFlatColor;



   That confirms the textured-stencil mode section 9 mentions, and
   matches the separately named Screen3D_SpanStencilFlatK42. It is how a
   cut-out shape - foliage, a sign, a shadow - gets drawn in a single
   colour without a per-pixel colour fetch.

   It also DESTROYS the extent globals. Its first act is to turn the
   pair into a count with maybe_g_spanFillRight -= maybe_g_spanFillLeft,
   then decrement it. That is why the cross-reference in section 11.8
   shows READ_WRITE on the right edge for this family where the clippers
   only WRITE. A reconstruction must not assume the extent survives the
   call.

12.3.  Texture addressing: 256 x 256, 16-bit texels

   The texel fetch is a single masked add, and it encodes the texture
   dimensions as shifts [verified]:



       off = ((v & 0xffffe01f) >> 4)      /* v_int * 512 bytes */

           + ((u & 0xffffefff) >> 12)     /* u_int *   2 bytes */

       texel = *(u16 *)(g_texBase + (off & 0x1fffe))



   u and v are 19.13 fixed point. The two intermediate masks keep each
   contribution clear of the other's bit range so the add cannot carry
   between them. The final 0x1fffe does two jobs: it wraps the address
   to 64K texels, which is 256 x 256, and it clears bit 0 so the 16-bit
   read stays aligned.

   So the texture size is not read from a header or a register - it is
   baked into the shift pair. Any port that wants a texture size other
   than 256 x 256 changes these shifts, and there are twelve fillers to
   change.

12.4.  What this costs the port

   +--------------------------+-------------------------------+
   | Assumption               | Where                         |
   +==========================+===============================+
   | destination step 2 bytes | dst pointer arithmetic        |
   +--------------------------+-------------------------------+
   | texel read as u16        | the fetch                     |
   +--------------------------+-------------------------------+
   | texel stride 2 bytes     | the 0x1fffe mask              |
   +--------------------------+-------------------------------+
   | texture is 256 x 256     | the >> 4 and >> 12 shift pair |
   +--------------------------+-------------------------------+

   None of this survives a move to D3D9, where texture addressing is the
   hardware's job and the whole twelve-function family collapses into
   sampler state plus a shader. The value of reading them is not to port
   them but to know exactly which modes exist: affine and perspective,
   across six texturing kinds, one of which is a flat stencil.


12.5.  The filler argument set, in full

   Reading the affine partner maybe_Screen3D_SpanStencilFlatAffine at
   0x004a50c0 completed the picture. The Span* fillers take no arguments
   at all; everything arrives in globals, and cross-referencing them
   shows the set is TWO-TIER [verified].

   +-----------------------+---------------+----------------------------+---------------------+
   | Global                | Tier          | Written by                 | Read by             |
   +=======================+===============+============================+=====================+
   | g_texStepU 0x00655d20 | per triangle  | the 9 TriKn + 2 EmitTri    | ClipSpan + fillers  |
   +-----------------------+---------------+----------------------------+---------------------+
   | g_texStepV 0x00655d24 | per triangle  | same                       | same                |
   +-----------------------+---------------+----------------------------+---------------------+
   | g_spanU 0x006d20b0    | per span      | the 8 ClipSpanKn + Walk4/5 | the 14 fillers      |
   +-----------------------+---------------+----------------------------+---------------------+
   | g_spanV 0x006d20b8    | per span      | same                       | same                |
   +-----------------------+---------------+----------------------------+---------------------+
   | maybe_g_spanFillLeft  | per span      | same                       | same                |
   +-----------------------+---------------+----------------------------+---------------------+
   | maybe_g_spanFillRight | per span      | same                       | same, destructively |
   +-----------------------+---------------+----------------------------+---------------------+
   | maybe_g_spanRowPtr    | per scanline  | the Tri layer              | the fillers         |
   +-----------------------+---------------+----------------------------+---------------------+
   | maybe_g_spanFlatColor | per primitive | the DrawPrim layer         | flat fillers        |
   +-----------------------+---------------+----------------------------+---------------------+

   The tiering matches the three-layer chain exactly and is a good
   independent check on it:

   o The TRI layer owns the per-pixel gradients. Under affine mapping du
     and dv are constant across a whole triangle, so that is the right
     place for them, and the fact that only TriKn functions write them
     confirms the layer boundary.

   o The CLIPSPAN layer owns the span extent and the starting u,v,
     because both depend on where the visible sub-span begins - which is
     what clipping decides.

   o The FILLER layer only reads. Its sole write is the destructive
     conversion of the extent pair into a count.

   Screen3D_FlushSpans writes every one of them, which is exactly what
   replaying a deferred span requires: the whole argument set has to be
   restored before the filler is called. That it writes the per-triangle
   tier as well as the per-span tier is a useful confirmation that the
   deferred record carries both.

12.5.1.  A caution for the reconstruction

   This is the second place in this subsystem where live arguments
   travel in globals - section 11.8 made the same point about the extent
   pair. The temptation to turn eight globals into a parameter list is
   strong and should be resisted until the subsystem is fully
   understood, per rule 5 in CLAUDE.md.

   Two specific hazards. First, the fillers DESTROY
   maybe_g_spanFillRight, so anything reading it after a filler call
   sees a count, not an edge. Second, the two tiers have different
   lifetimes: a caller that sets g_texStepU once and then loops over
   scanlines is relying on the ClipSpan layer not to touch it, and the
   cross-reference above confirms it does not.

12.5.2.  The two stencil fillers, side by side

   +-------------+-------------------------------+------------------------+
   |             | Affine 0x004a50c0             | Perspective 0x004a5150 |
   +=============+===============================+========================+
   | size        | 134 bytes                     | 472 bytes              |
   +-------------+-------------------------------+------------------------+
   | u,v advance | constant per pixel            | re-derived every 16 px |
   +-------------+-------------------------------+------------------------+
   | divides     | none                          | one per 16 pixels      |
   +-------------+-------------------------------+------------------------+
   | ftol calls  | none                          | two per block          |
   +-------------+-------------------------------+------------------------+
   | texel fetch | identical                     | identical              |
   +-------------+-------------------------------+------------------------+
   | writes      | flat colour on non-zero texel | same                   |
   +-------------+-------------------------------+------------------------+

   The identical texel fetch in two independently written functions is
   what makes the 256 x 256 / 16-bit-texel reading of section 12.3 safe
   rather than a single-site inference.


12.6.  Stencil versus keyed, and a cheap way to tell modes apart

   maybe_Screen3D_SpanTexKeyedAffine at 0x004a5330 is the second affine
   filler read in full, and the comparison with the stencil isolates
   exactly one difference [verified]:



       stencil :  t = texel(u,v);  if (t) *dst = flatColor;

       keyed   :  t = texel(u,v);  if (t) *dst = t;



   Same skeleton, same destructive extent-to-count conversion, same
   texel fetch, same stepping. Zero is the transparent colour key in
   both; what differs is only what gets written.

   That difference is mechanically detectable without decompiling: a
   stencil filler READS maybe_g_spanFlatColor and a keyed one never
   touches it. Scanning the family for which globals each function
   references classifies all sixteen fillers in one pass, which is much
   cheaper than reading them individually [verified]:

   subdivRecip is present in exactly the six perspective fillers and

   Only three fillers read the flat colour: the two stencils and
   SpanBlendFlat. Everything else writes texels. So the flat-colour

12.6.1.  What is still unread

   Four affine fillers remain, and their sizes suggest small variations
   on the keyed loop rather than new modes: 0x004a5580 at 129 bytes,
   0x004a57f0 at 151, 0x004a5e10 at 128, against 125 for the keyed one
   just read. Their perspective partners follow by pairing.

   o Screen3D_SpanCopyTexels is the odd one. It reads g_spanU and
     g_texStepU like the rest, but it contains NONE of the >> 4 / >> 12
     shift pair that every other textured filler uses, and it has two
     16-bit stores rather than one. Whatever addressing it uses is
     different, and that is worth reading before the near-duplicates.

   None of this changes the port conclusion in section 12.4. The value
   of finishing the family is a complete list of the modes the software
   renderer supports, which is what a replacement has to cover.


12.7.  Screen3D_SpanCopyTexels: a third addressing scheme

   Section 12.6 flagged this one as the outlier because it contains none
   of the >> 4 / >> 12 shift pair every other textured filler uses. The
   reason is that it is SELF-MODIFYING CODE, already documented from the
   patching side in subsystems/pixel-format.txt section 1.3. What was
   not recorded anywhere is how it actually addresses the texture, and
   that is worth having because it confirms the texture geometry by a
   third independent route [verified].

   It keeps u and v ROTATED rather than masked. For 19.13 fixed point, a
   rotate right by 13 brings the integer part down into the low byte and
   pushes the fraction into the high bits:



       u_rot = ROR(u, 13);      /* g_spanU >> 0xd | g_spanU << 0x13 */

       v_rot = ROR(v, 13);

       index = (byte)v_rot << 8 | (byte)u_rot;   /* CONCAT11 */

       texel = ((u16 *)g_texBase)[index];



   So the texel index is built by concatenating two BYTES - v in the
   high half, u in the low half - giving a 16-bit index into a 64K array
   of 16-bit texels. That is a 256 x 256 texture with 2-byte texels,
   exactly what section 12.3 derived from the mask and shift arithmetic
   of the other fillers, reached a completely different way.

   Advancing is the neat part. The rotated step is added to the rotated
   coordinate, and the carry out of the fractional half is detected by a
   comparison and folded into the integer byte:



       carry = (0xedcba987 < u_rot);     /* 0xedcba987 == ~step   */

       u_rot += step;

       u_int += 0x12 + carry;



   0x12345678 and 0xedcba987 are the PLACEHOLDER immediates - they are
   what the patch block overwrites, and 0xedcba987 is the one's
   complement of 0x12345678, so the comparison really is an overflow
   test against the patched step. Reading them as constants is
   meaningless.

12.7.1.  It is the opaque mode

   Unlike the two fillers read before it, this one applies NO test to
   the texel - it stores it verbatim. That completes the taxonomy of
   what the family does with a fetched texel [verified]:

   +---------+-------------------------+-------------------------+
   | Mode    | Inner statement         | Example                 |
   +=========+=========================+=========================+
   | stencil | if (t) *dst = flatColor | 0x004a50c0 / 0x004a5150 |
   +---------+-------------------------+-------------------------+
   | keyed   | if (t) *dst = t         | 0x004a5330              |
   +---------+-------------------------+-------------------------+
   | copy    | *dst = t                | Screen3D_SpanCopyTexels |
   +---------+-------------------------+-------------------------+

   Being a plain copy is also why the existing plate comment can call it
   pixel-format agnostic BY CONSTRUCTION: it never decomposes or
   recombines a colour, so nothing in it assumes 5/6/5. The 16 bpp
   dependency that remains is only the width - u16 loads, u16 stores,
   and a 2-byte texel stride.

12.7.2.  Only three fillers are self-modifying

   Cross-referencing the patch dirty flag g_spanPatchDirty at 0x00624b50
   bounds the self-modifying machinery precisely [verified]:

   +---------+-------+-------------------------------------------------+
   |         | Count | Who                                             |
   +=========+=======+=================================================+
   | writers | 17    | every TriKn, the 3 EmitTri, TriFlat, FlushSpans |
   +---------+-------+-------------------------------------------------+
   | readers | 3     | SpanCopyTexels, SpanBlend1, SpanBlend2          |
   +---------+-------+-------------------------------------------------+

   So thirteen of the sixteen fillers do their addressing
   straightforwardly and only three patch themselves. That is a much
   smaller blast radius than the phrase 'the rasterizer patches its own
   instruction stream' suggests, and it is good news for the port: the
   self-modifying paths can be dropped entirely and the remaining
   thirteen read normally.

   The writer list is also a clean confirmation of the layering in
   section 12.5. Every writer is in the Tri or Emit layer, plus
   FlushSpans - the same set that owns the per-triangle interpolant
   steps. maybe_Screen3D_TriFlat raising the flag immediately after its
   vertex sort, noted when it was read, is this same protocol.

   The two SpanBlend fillers appear in BOTH lists because they clear the
   flag after patching. Screen3D_SpanCopyTexels does not, which pixel-
   format.txt section 1.3.2 already establishes is a missed optimisation
   rather than a bug.


12.8.  A darkened mode, and where the format-independence lives

   maybe_Screen3D_SpanTexKeyedHalfAffine at 0x004a5580 is the keyed
   textured span again, with one extra operation [verified]:



       t = texel(u, v);

       if (t != 0) *dst = (t >> 1) & g_halveMask;



   129 bytes against 125 for the plain keyed version - exactly the SHR
   and the AND. It writes the texel at half brightness, which is how a
   darkened or shadowed textured surface is drawn without a second
   texture.

12.8.1.  g_halveMask is derived, not hardcoded

   This is the part worth having. g_halveMask at 0x0050270c is ZERO in
   the static image and has exactly one writer,
   maybe_Color_BuildHalveMask at 0x00401fc0 [verified]:



       m = (-2 << g_shlR) & g_maskR

         | (-2 << g_shlB) & g_maskB

         | (-2 << g_shlG) & g_maskG;

       m |= m << 16;              /* both halves of a dword */

       g_halveMask = m >> 1;



   -2 is 0xfffffffe. Shifting it left by a channel's shift and masking
   to that channel gives the channel with its low bit cleared; OR the
   three and shift right by one and (c >> 1) & g_halveMask is a correct
   per-channel halve with no bleed between neighbouring channels.

   Every input is a RUNTIME pixel-format global - g_shlR/G/B and
   g_maskR/G/B, which Cdd_InitCapsVariables reads off the primary
   surface, per subsystems/pixel-format.txt. Nothing here assumes 5/6/5.

   That is the third independent instance of the same pattern, and it is
   now worth stating as a general finding about this renderer:

   +------------------------------------------------+-------------------+
   | Layer                                          | Format dependence |
   +================================================+===================+
   | colour conversion (Color_Convert555ToSurface)  | derived           |
   +------------------------------------------------+-------------------+
   | flat colour packing (the dword duplication)    | derived           |
   +------------------------------------------------+-------------------+
   | channel arithmetic (g_halveMask)               | derived           |
   +------------------------------------------------+-------------------+
   | pixel WIDTH (strides, u16 loads/stores, masks) | HARDCODED         |
   +------------------------------------------------+-------------------+

   So the software rasterizer's COLOUR arithmetic is already general and
   would produce correct results at any RGB layout. What is baked in is
   the assumption that a pixel is two bytes: the x * 2 addressing, the
   u16 loads and stores, the 0x1fffe texel mask, and the two-pixels-per-
   dword and four-per-MOVQ bulk paths.

   That is a much more precise statement of the 16-bit problem than the
   mission note started with, and a more encouraging one. The work is
   mechanical width changes, not re-deriving the colour model.

   The m |= m << 16 duplication is the same two-pixels-per-dword
   convention as maybe_g_spanFlatColor, so it is itself one of the width
   assumptions even though the mask it builds is not.

   +------------+----------------------------------+------------------------+

   | stencil    | if (t) *dst = flatColor          | 0x004a50c0, 0x004a5150 |

   The extra ADDs in 0x004a57f0 suggest it combines two values rather

12.9.  A blended mode, and a split that matters for the port

   maybe_Screen3D_SpanTexKeyedBlendAffine at 0x004a57f0 is the keyed
   textured span blended 50/50 with the existing pixel [verified]:



       t = texel(u, v);

       if (t != 0)

           *dst = ((*dst >> 1) & g_halveMask)

                + ((t    >> 1) & g_halveMask);



   151 bytes against 125 for the plain keyed version - two SHR/AND pairs
   and one ADD. The same g_halveMask as section 12.8, so the blend
   arithmetic is format-derived rather than hardcoded.

12.9.1.  Write-only versus read-modify-write

   This is the first filler in the family that READS the destination,
   and that turns out to be the useful axis for the port - more useful
   than affine versus perspective, which disappears entirely under
   hardware texturing [verified]:

   +-------------+-----------------------------------------+-------------------+
   | Mode        | Statement                               | Touches dst       |
   +=============+=========================================+===================+
   | stencil     | if (t) *dst = flatColor                 | write only        |
   +-------------+-----------------------------------------+-------------------+
   | keyed       | if (t) *dst = t                         | write only        |
   +-------------+-----------------------------------------+-------------------+
   | keyed-half  | if (t) *dst = (t>>1) & M                | write only        |
   +-------------+-----------------------------------------+-------------------+
   | copy        | *dst = t                                | write only        |
   +-------------+-----------------------------------------+-------------------+
   | keyed-blend | if (t) *dst = (dst>>1 & M) + (t>>1 & M) | READ-MODIFY-WRITE |
   +-------------+-----------------------------------------+-------------------+
   | blend-flat  | *dst = (dst>>1 & M) + flatColor         | READ-MODIFY-WRITE |
   +-------------+-----------------------------------------+-------------------+

   The write-only modes map onto a plain textured draw with an alpha
   test. The read-modify-write modes map onto hardware alpha blending,
   which costs nothing on a GPU and is where the software renderer
   spends most of its per-pixel budget. So the modes that look most
   expensive here are the ones that get cheapest in a port.

   It also means the six modes collapse to two pipeline states plus a
   constant, rather than twelve functions.

12.9.2.  The mode list

   Five of the six affine fillers have now been read in full. The
   perspective partners follow by pairing - each is the same inner
   statement wrapped in the 16-pixel subdivision of section 12.1
   [inferred from the pairing, not read individually].

   +------------+-------------+----------------------------+
   | Affine     | Perspective | Mode                       |

   +------------+-------------+----------------------------+
   | 0x004a5330 | 0x004a53b0  | keyed texture              |
   +------------+-------------+----------------------------+
   | 0x004a5580 | 0x004a5610  | keyed texture, halved      |
   +------------+-------------+----------------------------+
   | 0x004a57f0 | 0x004a5890  | keyed texture, 50/50 blend |
   +------------+-------------+----------------------------+
   | 0x004a5ab0 | 0x004a5c40  | opaque copy                |
   +------------+-------------+----------------------------+
   | 0x004a5e10 | 0x004a5e90  | UNREAD                     |

   The one remaining affine filler, 0x004a5e10 at 128 bytes, has one SHR
   and no extra ADD beyond the loop's own. On the arithmetic of the
   others that is a single halving with no blend, and at 128 bytes

12.10.  The affine family is complete

   maybe_Screen3D_SpanTexHalfAffine at 0x004a5e10 is the last of the
   six, and it is the unkeyed halved copy predicted in section 12.9.2
   from instruction counts [verified]:



       *dst = (texel(u, v) >> 1) & g_halveMask;    /* no key test */



   All six affine fillers have now been read in full. They decompose on
   two orthogonal axes plus two extras, which is a tidier structure than
   the flat list suggested:

   +------------------+----------------------+---------------------------+
   |                  | keyed (skip texel 0) | unkeyed                   |
   +==================+======================+===========================+
   | write texel      | 0x004a5330           | 0x004a5ab0 SpanCopyTexels |
   +------------------+----------------------+---------------------------+
   | write texel >> 1 | 0x004a5580           | 0x004a5e10                |
   +------------------+----------------------+---------------------------+

   plus two that exist only in a keyed form:

   +---------+-----------------------------------------+------------+
   | Mode    | Statement                               | Address    |
   +=========+=========================================+============+
   | stencil | if (t) *dst = flatColor                 | 0x004a50c0 |
   +---------+-----------------------------------------+------------+
   | blend   | if (t) *dst = (dst>>1 & M) + (t>>1 & M) | 0x004a57f0 |
   +---------+-----------------------------------------+------------+

   So the renderer supports exactly six span operations: copy, halved
   copy, and stencil, each with or without a colour key where that
   combination exists, plus a 50/50 blend. Nothing else. There is no
   additive mode, no modulate, no per-pixel alpha - the only
   translucency is a fixed 50 percent.

12.10.1.  Confirming the pairing

   Each of the six has a perspective partner, and the pairing can be
   tested mechanically rather than by reading six more functions. Every
   filler was scanned for which of the three colour globals it
   references [verified]:

   +------------+-------------+---------------------+
   | Affine     | Perspective | Shared signature    |
   +============+=============+=====================+
   | 0x004a50c0 | 0x004a5150  | flatColor + texBase |
   +------------+-------------+---------------------+
   | 0x004a5330 | 0x004a53b0  | texBase             |
   +------------+-------------+---------------------+
   | 0x004a5580 | 0x004a5610  | texBase + halveMask |
   +------------+-------------+---------------------+
   | 0x004a57f0 | 0x004a5890  | texBase + halveMask |
   +------------+-------------+---------------------+
   | 0x004a5ab0 | 0x004a5c40  | texBase             |
   +------------+-------------+---------------------+
   | 0x004a5e10 | 0x004a5e90  | texBase + halveMask |
   +------------+-------------+---------------------+

   All six pairs match. That rules out any pair being mismatched - no
   perspective filler uses colour inputs its affine twin does not.

   It does NOT by itself identify each perspective filler's mode,
   because three share the signature texBase + halveMask. One of those
   three, 0x004a5890, has since been read in full and is the blend,
   exactly as the pairing predicted - see section 12.11. The remaining
   ambiguity is only between 0x004a5610 and 0x004a5e90, one keyed-half
   and one half-copy, assigned by address adjacency [verified for
   0x004a5890; inferred for the other two].

12.10.2.  What a replacement has to cover

   With the mode list closed, the span layer's requirements for the port
   are now fully enumerated:

   o One textured draw with an alpha test, covering stencil, keyed,
     keyed-half, copy and halved-copy - five of the six modes are write-
     only.

   o One textured draw with SRCALPHA/INVSRCALPHA blending at a fixed
     one-half, covering the blend mode and maybe_Screen3D_SpanBlendFlat.

   o A constant-colour path for the stencil mode, which writes the flat
     colour rather than the texel.

   o Nothing for affine versus perspective. That distinction is the
     entire reason there are twelve functions instead of six, and
     hardware texturing removes it.

   Twelve functions, roughly 3.4 KB of hand-tuned code, reduce to two
   pipeline states and a shader constant. That is the clearest single
   argument in this document for replacing the software rasterizer
   rather than porting it.


12.11.  One skeleton, six inner statements

   maybe_Screen3D_SpanTexKeyedBlendPersp at 0x004a5890 is the second
   perspective filler read in full, and it settles how the family is
   built [verified].

   Its inner statement is byte-for-byte the affine blend from section
   12.9:



       t = texel(u, v);

       if (t != 0)

           *dst = ((*dst >> 1) & g_halveMask)

                + ((t    >> 1) & g_halveMask);



   and the wrapper around it is byte-for-byte the subdivision skeleton
   from maybe_Screen3D_SpanStencilFlatPersp - the same three float
   accumulators, the same three steps, the same maybe_g_subdivRecip
   scaling for a partial block, the same two __ftol calls per block.

   So the twelve fillers are not twelve algorithms. They are SIX
   operations crossed with TWO wrappers:

   +-------------+----------------+---------------------+
   |             | affine wrapper | perspective wrapper |
   +=============+================+=====================+
   | stencil     | 0x004a50c0     | 0x004a5150 (read)   |
   +-------------+----------------+---------------------+
   | keyed       | 0x004a5330     | 0x004a53b0          |
   +-------------+----------------+---------------------+
   | keyed-half  | 0x004a5580     | 0x004a5610          |
   +-------------+----------------+---------------------+
   | keyed-blend | 0x004a57f0     | 0x004a5890 (read)   |
   +-------------+----------------+---------------------+
   | copy        | 0x004a5ab0     | 0x004a5c40          |
   +-------------+----------------+---------------------+
   | half-copy   | 0x004a5e10     | 0x004a5e90          |
   +-------------+----------------+---------------------+

   Two of the six perspective members have now been read, at opposite
   ends of the table - the stencil and the blend - and both are exactly
   their affine twin's inner statement inside the shared skeleton.
   Combined with the signature match of section 12.10.1 and the
   consistent address adjacency across all six pairs, the table can be
   treated as established.

   RESOLVED. 0x004a5610 has since been read and DOES carry the colour-
   key test, so it is the keyed half and 0x004a5e90 is the unkeyed half-
   copy by elimination. Nothing in the family now rests on adjacency
   alone [verified].

12.11.1.  Why this matters more than it looks

   The affine wrapper is about 130 bytes and the perspective one about
   470, so roughly 340 bytes of each perspective filler is the SAME
   subdivision code repeated six times. Of the family's 3.4 KB, over 2
   KB is one duplicated skeleton.

   That is a strong hint about the original source: this was almost
   certainly a macro or an include-with-different-inner-statement, not
   six hand-written functions. The reconstruction should express it that
   way rather than transcribing six near copies [inferred - no source
   artefact confirms it, but the byte-level identity of the wrappers is
   hard to explain otherwise].

   It also sharpens section 12.10.2: a replacement does not need to
   reproduce six operations and two wrappers. It needs six blend/test
   states, and the wrapper distinction vanishes.


12.12.  The family is closed

   maybe_Screen3D_SpanTexKeyedHalfPersp at 0x004a5610 was the last open
   question in the span-filler family. It carries the colour-key test,
   so it is the keyed half; 0x004a5e90 is therefore the unkeyed half-
   copy, forced by elimination [verified for 0x004a5610, inferred for
   0x004a5e90].

   +----------------------+-----------------+------------------------+
   | Operation            | Affine          | Perspective            |
   +======================+=================+========================+
   | stencil, flat colour | 0x004a50c0 read | 0x004a5150 read        |
   +----------------------+-----------------+------------------------+
   | keyed texture        | 0x004a5330 read | 0x004a53b0 pairing     |
   +----------------------+-----------------+------------------------+
   | keyed, halved        | 0x004a5580 read | 0x004a5610 read        |
   +----------------------+-----------------+------------------------+
   | keyed, 50/50 blend   | 0x004a57f0 read | 0x004a5890 read        |
   +----------------------+-----------------+------------------------+
   | opaque copy          | 0x004a5ab0 read | 0x004a5c40 pairing     |
   +----------------------+-----------------+------------------------+
   | halved copy          | 0x004a5e10 read | 0x004a5e90 elimination |
   +----------------------+-----------------+------------------------+

   Nine of the twelve have been read in full. The three that have not -
   0x004a53b0, 0x004a5c40 and 0x004a5e90 - are determined by a pairing
   that now has three independent supports: identical global signatures
   within each pair, consistent address adjacency across all six, and
   three perspective members read at different points in the table,
   every one of which turned out to be its affine twin's inner statement
   inside the shared skeleton.

   Reading the remaining three would confirm what is already determined
   and is not worth the effort unless something later contradicts it.
   This note records that as a deliberate stopping point rather than an
   oversight.

12.12.1.  The skeleton, three times over

   The subdivision wrapper has now been read in three separate functions
   - the stencil, the keyed-half and the blend - and is byte-for-byte
   identical in all three: same three float accumulators, same three
   steps, same maybe_g_subdivRecip scaling, same two __ftol calls per
   block, same 16-pixel chunking.

   Three independent instances of an identical 340-byte wrapper makes
   the macro-or-include reading of section 12.11.1 considerably harder
   to argue against. The reconstruction should write one wrapper and six
   bodies.

12.12.2.  Where the subsystem stands

   The span layer is now understood end to end, and the chain from
   section 12.5 is complete at every level:



       DrawPrim    sets the colour, installs a filler

         Tri       per-triangle gradients, walks edges, EMMS

           ClipSpan  per-scanline extent and starting u,v

             Span*   one of six operations, two wrappers



   What remains unread in this area is the Emit and Setup layer above it
   - maybe_Screen3D_SetupPrim0 through SetupPrim4, and the EmitTri
   functions - which is where the primitive kinds and the pipeline-slot
   table of section 10.3 are actually decided.


13.  The Setup layer, and the top of the chain

   maybe_Screen3D_SetupPrim0 at 0x004a4820 is the entry for walker-table
   key 2 and sits ABOVE everything section 12 describes. Reading it
   extends the chain upward by two stages and yields the vertex format
   [verified].



       Screen3D_DispatchPrimitive   picks the table entry by kind

         SetupPrimN                 colour, depth, NEAR CLIP, reject

           EmitTriN / TriKn         per-triangle gradients, edges

             ClipSpanKn             per-scanline extent, u,v

               Span*                one of six operations



13.1.  What SetupPrim0 does

   o COLOUR. The packed 555 colour at p+0x02 goes through
     Color_Convert555ToSurface, is halved with g_halveMask, and is
     stored duplicated into maybe_g_spanFlatColor. So key 2 draws a PRE-
     DARKENED flat colour, which fits its emitting through
     maybe_Screen3D_EmitTriBlend.

   o DEPTH. maybe_g_edgeShade is set to the mean of the three vertices'
     +0x0c fields. That is the sort key the span buffer depends on -
     section 10.1 notes the scene is drawn front to back, and this is
     where the ordering value comes from.

   o NEAR CLIP. Each vertex's +0x08 float is tested against
     maybe_g_nearPlaneZ. The combinations collapse to three cases - none
     behind, one behind, two behind - resolved by calling
     maybe_Screen3D_ClipEdgeNear to manufacture intersection vertices,
     then emitting one or two triangles. Three behind emits nothing.

   o TRIVIAL REJECT. A per-axis counter runs over the three vertices and
     gates the emit. See the caution in 13.3.

   o TWO TRIANGLES. Indices are u16 at p+0x2c. The first pass uses
     [0],[1],[2]; if the short at p+0x34 is not -1 a second uses
     [0],[2],[3]. A quad is a two-triangle fan - the same 'DrawPrim
     calls Tri twice' shape section 10.4 records, here expressed as a
     loop with an early exit for triangles.

13.2.  MR_Vertex is 0x1c bytes

   The vertex array arrives as the first argument and is indexed as
   verts + i * 0x1c. Four fields are confirmed by use [verified]:

   +--------+-------+----------------------------------------+
   | Offset | Type  | Use                                    |
   +========+=======+========================================+
   | +0x08  | float | compared against maybe_g_nearPlaneZ    |
   +--------+-------+----------------------------------------+
   | +0x0c  | int   | depth; averaged into maybe_g_edgeShade |
   +--------+-------+----------------------------------------+
   | +0x10  | uint  | screen x, passed to the Emit layer     |
   +--------+-------+----------------------------------------+
   | +0x14  | uint  | screen y, passed to the Emit layer     |
   +--------+-------+----------------------------------------+

   COMPLETE. +0x18 is the 1/z term (section 19.1) and +0x00 / +0x04 are
   camera-space X and Y (section 28), which confirms the guess that
   +0x00, +0x04 and +0x08 form a float x, y, z triple. The whole record
   is written up in structs/MR_Vertex.txt [verified].

13.3.  A test not fully pinned down

   Before each emit, and separately for x and y, the code runs:



       n = 2;

       for each of the three vertices:

           if (viewMax < (unsigned)coord) {

               if ((signed)coord < 0) n -= 2;

               n += 1;

           }

       if (n < 6) emit;



   The unsigned compare catches both edges at once - a negative
   coordinate is huge unsigned - and the inner signed test then
   separates left from right. So the counter is 2, plus one per vertex
   past the right edge, minus one per vertex past the left.

   The intent is plainly an outcode-style trivial reject. But the
   arithmetic as decompiled is asymmetric: three vertices off the left
   give -1, which as unsigned is not less than 6 and so rejects, while
   three off the right give 5, which passes. Either the decompilation is
   misleading or the test genuinely only trivially rejects on one side,
   with the span clipper catching the rest.

   This is recorded as UNVERIFIED rather than guessed at. It should be
   re-derived from the assembly by anyone who needs the detail; nothing
   else in this document depends on it.

13.4.  Three globals named

   +-------------------------------+-----------------------+----------------------------------+
   | Global                        | Meaning               | Notable                          |
   +===============================+=======================+==================================+
   | maybe_g_nearPlaneZ 0x00625774 | near-clip threshold   | runtime; 256 in menus, 64 racing |
   +-------------------------------+-----------------------+----------------------------------+
   | maybe_g_edgeShade 0x0068b00c  | primitive sort depth  | flows Setup -> Tri -> ClipSpan   |
   +-------------------------------+-----------------------+----------------------------------+
   | maybe_g_primCount 0x00625730  | primitives this frame | shared with D3D_DrawScene        |
   +-------------------------------+-----------------------+----------------------------------+

   THE NEAR PLANE HAS TWO VALUES AND ONLY ONE WRITER IS OBVIOUS.
   Menu_SetPage writes 256.0 at 0x0040a037, and that is the only
   reference to the global a displacement search finds. The other is
   Race_SetupRenderState (0x00410e10), which writes 64.0 and is
   called once by maybe_Game_LoadRace - so a race clips at 64 and a
   menu at 256. Read live mid-race: 64.0. [verified]

   NOTHING REWRITES IT DURING A RACE, which is what makes the pair
   easy to miss: a watchpoint armed after the race has started
   records no hits and the value reads like a constant. It is set
   once, at load.

   A PORT THAT COPIES ONLY THE MENU WRITER CLIPS FOUR TIMES TOO
   FAR. Ours did, and it stayed invisible while the only camera was
   the chase - which sits 484 or more from the bike. It surfaced the
   moment a side camera put the eye 250 out and the bike fell inside
   the near plane; the road immediately under and behind the bike
   had been clipping early the whole time.

   maybe_g_primCount being shared with D3D_DrawScene is the first global
   found that both the software and hardware renderers write. Everything
   else in section 12 is software-path only.

13.5.  maybe_Screen3D_ClipEdgeNear is universal

   227 bytes, fifteen callers - every one of the five SetupPrimN and
   every one of the nine DrawPrimKn, plus the two flat DrawPrims. It is
   the single shared near-clip primitive of the whole software renderer
   [verified].

   For the port that is convenient: near-plane clipping is one function
   to understand, not fifteen, and under D3D9 it disappears into the
   fixed-function or shader pipeline entirely.


14.  The Emit layer, and what it says about the batch record

   maybe_Screen3D_EmitTriBlend at 0x004a4350 is the stage between
   maybe_Screen3D_SetupPrim0 and the span fillers, completing the flat-
   blend path from Screen3D_DispatchPrimitive down to the pixel
   [verified].

14.1.  Emit and Tri are the same layer

   The edge walking here is the SAME code as maybe_Screen3D_TriFlat:
   rotate the vertices until y0 is smallest, gradients as (dx * 0x2000)
   / dy in 19.13, pre-step the DDA when y is negative, shorten the count
   past g_viewMaxY, handle two halves.

   So the EmitTriN and TriKn families are one layer under two names.
   What actually distinguishes them is how they reach the filler and
   whether they queue:

   +--------------------------+----------------------------+--------------+
   |                          | TriFlat                    | EmitTriBlend |
   +==========================+============================+==============+
   | reaches filler by        | maybe_g_spanClipper pointer | direct call |
   +--------------------------+----------------------------+--------------+
   | gated on g_spanAccepting | no                         | yes          |
   +--------------------------+----------------------------+--------------+
   | appends a batch record   | no                         | yes          |
   +--------------------------+----------------------------+--------------+
   | issues EMMS              | yes                        | yes          |
   +--------------------------+----------------------------+--------------+

   The direct call is what section 9.1 meant by the specialised paths
   not needing the walker indirection, now seen from the producing side.

14.2.  A second reading of the batch record

   Section 7.2 derived the 0x24-byte batch record from a different
   emitter. This one writes only THREE of its seven known fields
   [verified]:

   +--------+-----------------------+---------------------+
   | Offset | This emitter writes   | Section 7.2 emitter |
   +========+=======================+=====================+
   | +0x00  | LITERAL 0xc           | maybe_g_primKind    |
   +--------+-----------------------+---------------------+
   | +0x04  | spans this triangle   | same                |
   +--------+-----------------------+---------------------+
   | +0x08  | -                     | g_texBase           |
   +--------+-----------------------+---------------------+
   | +0x0c  | maybe_g_spanFlatColor | same                |
   +--------+-----------------------+---------------------+
   | +0x14  | -                     | g_texStepU          |
   +--------+-----------------------+---------------------+
   | +0x18  | -                     | g_texStepV          |
   +--------+-----------------------+---------------------+
   | +0x20  | -                     | maybe_g_edgeShade   |
   +--------+-----------------------+---------------------+

   Leaving texture base, both UV steps and depth untouched is
   independent confirmation of the union reading in section 7.2: the
   record is keyed by +0x00 and only the fields that kind needs are
   meaningful. A flat blend has no texture and no UVs, so it writes
   none.

   The literal 0xc is the sharper finding. Where
   maybe_Screen3D_EmitTriFlatAffine and
   maybe_Screen3D_EmitTriGouraudAffine copy maybe_g_primKind into +0x00,
   this emitter hardcodes 12 - so kind 12 is its own signature to
   Screen3D_FlushSpans rather than something the dispatcher chose.

   maybe_g_primKind at 0x00624358 is written only by
   Screen3D_DispatchPrimitive, which is the tidy answer to where the
   kind comes from: the dispatcher reads it off the primitive record
   once and the emitters copy it forward.

14.3.  Overflow is silent

   g_spanAccepting is now confirmed rather than inferred.
   Screen3D_BeginFrame resets it each frame; any emitter or clipper that
   fills a queue clears it - the batch queue at 1000 records, the
   deferred span buffer at 0x2800 spans.

   What matters is that emitters TEST it before walking. Once it is
   clear, every remaining triangle in the frame is DISCARDED ENTIRELY -
   not clipped, not partially drawn, not reported. A scene heavy enough
   to exhaust either queue simply loses geometry [verified].

   o For the reconstruction: this is observable behaviour and must be
     preserved if the goal is byte-faithful rendering, however much it
     looks like a bug.

   o For the port: the caps exist because the queues are fixed arrays. A
     D3D9 renderer has no equivalent limit and the flag, both queues and
     the drop behaviour all disappear together.

   It also explains a class of bug reports that would be hard to
   diagnose from the outside - geometry vanishing in complex scenes
   rather than the frame rate dropping.


15.  The dispatcher, and the master mode table

   Screen3D_DispatchPrimitive at 0x004aef20 is the top of the chain.
   Reading it, together with the static contents of g_spanTable,
   resolves several things this document had left open [verified].

15.1.  Three dispatch paths, not one

   The argument is a render CONTEXT, not a primitive: +0x00 is the
   primitive record, +0x0c the vertex array, +0x10 a mode selector. The
   primitive kind is a u16 at prim+0x3a.

   +-----------------------------+-----------------------------------------------+
   | Condition                   | Path                                          |
   +=============================+===============================================+
   | ctx+0x10 != 0               | the specialised switch - kinds 0,1,2,3,4,9,42 |
   +-----------------------------+-----------------------------------------------+
   | ctx+0x10 == 0, altMode == 0 | the g_spanTable path                          |
   +-----------------------------+-----------------------------------------------+
   | ctx+0x10 == 0, altMode != 0 | kinds 6, 7, 11 only                           |
   +-----------------------------+-----------------------------------------------+

   The third path is new. maybe_g_altDispatchMode at 0x006d20a0, written
   only by FUN_004995a0, diverts to a handler set recognising kind 6,
   kinds 7 and 11 - which draw a single POINT from vertex 0 after a
   near-plane test - and a catch-all. Kinds 6, 7 and 11 appear in
   neither g_spanTable nor the switch, so this is the only way they are
   ever drawn.

15.2.  Two levels, and a name corrected

   On the table path the dispatcher sets up two different function
   pointers, and this document had been conflating them [verified]:



       maybe_g_spanClipper = walkerTable[idx]

                           + (deferMode ? 0x0c : 0x08);

       maybe_g_spanFiller  = g_spanTable[kind] + 0x0c;

       call walkerTable[idx] + 0x04;        /* SetupPrimN */



   o maybe_g_spanClipper (0x006d20bc) is the PER-SCANLINE routine. On
     the Walk4-7 paths it clips against the free list and then calls the
     filler; on the flat path it is ClipSpanFlatScalar or ...MMX, which
     clip and fill in one function.

   o maybe_g_spanFiller (0x00655d08) is the actual pixel filler, one of
     the Screen3D_Span* family, read by all eight Walk functions.

   The global at 0x006d20bc was previously called maybe_g_spanFiller
   throughout this document. It has been renamed to maybe_g_spanClipper
   and the name maybe_g_spanFiller given to 0x00655d08, which is what
   actually fills. All mentions above have been updated.

15.3.  g_spanTable is the master mode table

   32 live records, each 0x10 bytes. Remember they are stored pre-
   scatter, so the KEY is the primitive kind and the slot position is
   meaningless [verified]:

   +--------+-----------------------------------------------------+
   | Offset | Field                                               |
   +========+=====================================================+
   | +0x00  | key = primitive kind                                |
   +--------+-----------------------------------------------------+
   | +0x04  | walker index into the table at 0x004f1ee0, 0 = none |
   +--------+-----------------------------------------------------+
   | +0x08  | defer flag -> maybe_g_spanDeferMode                 |
   +--------+-----------------------------------------------------+
   | +0x0c  | the span filler for this kind                       |
   +--------+-----------------------------------------------------+

   The walker index is the interpolant set, and it lines up exactly with
   the slot table of section 10.3: 4 carries U,V; 5 adds shade; 6 adds
   the 1/z terms; 7 has all four. Index 2 is the flat SetupPrim0 path
   and index 0 means no walker at all, so the +0x0c function is called
   directly.

15.3.1.  It confirms the affine/perspective pairing outright

   Section 12.10.1 established the six pairs by signature matching and
   address adjacency, and three of the perspective members were assigned
   without being read. The table settles it from an entirely independent
   direction: every affine filler has walker index 4 and every
   perspective one has index 6 - the difference between those two
   walkers being precisely the 1/z terms [verified].

   +---------------+------------------+-----------------------+
   | Operation     | affine, walker 4 | perspective, walker 6 |
   +===============+==================+=======================+
   | keyed texture | kind 38          | kind 53               |
   +---------------+------------------+-----------------------+
   | keyed, halved | kind 39          | kind 54               |
   +---------------+------------------+-----------------------+
   | keyed, blend  | kind 44          | kind 62               |
   +---------------+------------------+-----------------------+
   | stencil, flat | kind 37          | kind 51               |
   +---------------+------------------+-----------------------+
   | opaque copy   | kind 16          | kind 31               |
   +---------------+------------------+-----------------------+
   | halved copy   | kind 21          | kind 32               |
   +---------------+------------------+-----------------------+

   So the three fillers never read directly - kinds 53, 31 and 32 - are
   confirmed as the perspective partners of 38, 16 and 21. Nothing in
   the family now rests on inference.

15.4.  Deferral is a property of the kind

   maybe_g_spanDeferMode is copied straight out of g_spanTable + 0x08
   and is 0 or 1 per kind. It is not a runtime decision, a frame state
   or a performance heuristic - which kinds defer is fixed in the table
   [verified].

   Of the 32 kinds, the deferred ones are the blends, stencils and keyed
   textures; the plain copies and the flat kinds are immediate. That
   fits: deferral exists so translucent geometry can be drawn after the
   opaque geometry has claimed its pixels.

15.5.  The two kind-0 handlers

   RESOLVED, having been recorded as unestablished twice.
   maybe_Screen3D_DrawPrimK0Table at 0x004a3950 and
   maybe_Screen3D_DrawPrimK0Switch at 0x004a3cf0 are the same primitive
   kind reached through the two dispatch paths [verified]:

   o 0x004a3950 is g_spanTable[0] + 0x0c with walker index 0, so the
     dispatcher calls it directly with (verts, prim).

   o 0x004a3cf0 is case 0 of the specialised switch, called with (verts,
     prim, mode) - the extra argument being the context field that chose
     that path.

   That is why their bodies are near-identical and why comparing their
   colour handling never yielded a difference: there is no difference to
   find beyond the argument.


16.  The flusher, and three confirmations

   Screen3D_FlushSpans at 0x004af130 drains the batch queue. Its
   mechanism was already documented from the self-modifying-code angle
   in subsystems/pixel-format.txt section 1.3.2. What is new here is
   what its SWITCH says, now that sections 12 to 15 have established the
   mode table [verified].

16.1.  Producer and consumer agree exactly

   Section 14 found that maybe_Screen3D_EmitTriBlend writes only three
   fields of the batch record and stamps a literal kind of 12. The
   flusher's case for kind 12 reads exactly one field:



       case 0xc:

           maybe_g_spanFlatColor = batch[+0x0c];

           break;



   Kind and span count are handled outside the switch, so that is three
   written and three read. No texture base, no UV steps, no depth - on
   either side. Producer and consumer agree offset for offset, derived
   independently from opposite ends, which is the strongest confirmation
   of the union reading available without running the game.

   Kind 12 is also the one switch case with no defer=1 entry in
   g_spanTable. That is consistent rather than contradictory: kind 12
   batches exist because an emitter hardcodes them, not because the
   table asked for deferral.

16.2.  The switch enumerates the deferred kinds

   Twenty-one cases, and every one is a key that appears in g_spanTable.
   Comparing the two lists is a clean cross-check [verified]:

   +-----------------------------------+------------------------------------+
   | Set                               | Members                            |
   +===================================+====================================+
   | kinds with defer=1 in g_spanTable | 20                                 |
   +-----------------------------------+------------------------------------+
   | cases in the flusher switch       | 21                                 |
   +-----------------------------------+------------------------------------+
   | the difference                    | kind 12, hardcoded by EmitTriBlend |
   +-----------------------------------+------------------------------------+

   Every table kind with defer=0 - 1, 3, 5, 16, 18, 21, 28, 29, 31 and
   32 - is absent from the switch, exactly as it should be: those kinds
   never queue, so the flusher never sees them.

16.3.  Affine versus perspective, a third confirmation

   The switch splits its per-span restore into two groups, and the split
   is the pairing again [verified]:

   +----------------+--------------------+-------------------------+
   | Group          | Restores           | Kinds                   |
   +================+====================+=========================+
   | fixed point    | g_spanU, g_spanV   | 2, 8, 37-42, 44, 68, 69 |
   +----------------+--------------------+-------------------------+
   | floating point | maybe_g_perspU/V/W | 50, 51, 53, 54, 62      |
   +----------------+--------------------+-------------------------+

   The float group is precisely the walker-6 kinds of section 15.3.1 -
   the perspective fillers - and the fixed-point group is the walker-4
   and walker-0 kinds. So the affine/perspective split has now been
   confirmed three independent ways: by signature matching in section
   12.10.1, by the walker index in the table in section 15.3.1, and by
   which interpolants the flusher restores here.

16.3.1.  Which accumulator is which

   Section 12.1 recorded three float accumulators and said which was u,
   v or 1/z had not been established. The union settles it without
   reading any arithmetic, because the affine and perspective variants
   are restored FROM THE SAME OFFSETS:

   +-------------+--------------+--------------------+
   | Offset      | Affine kinds | Perspective kinds  |
   +=============+==============+====================+
   | batch +0x14 | g_texStepU   | maybe_g_perspStepU |
   +-------------+--------------+--------------------+
   | batch +0x18 | g_texStepV   | maybe_g_perspStepV |
   +-------------+--------------+--------------------+
   | batch +0x1c | -            | maybe_g_perspStepW |
   +-------------+--------------+--------------------+
   | span +0x0c  | g_spanU      | maybe_g_perspU     |
   +-------------+--------------+--------------------+
   | span +0x10  | g_spanV      | maybe_g_perspV     |
   +-------------+--------------+--------------------+
   | span +0x14  | -            | maybe_g_perspW     |
   +-------------+--------------+--------------------+

   u aliases u, v aliases v, and the third slot - present only for the
   perspective kinds - is the 1/z term. That is also a neat restatement
   of what makes the two walkers differ: walker 6 carries one more
   interpolant than walker 4, and it is exactly this one [inferred,
   strongly - from the layout rather than the arithmetic].

16.4.  The span record, completed

   Section 9.2 recorded three fields of the 0x1c-byte span record from
   the producing end. The flusher reads three more [verified]:

   +--------+-------------------------------------------+
   | Offset | Field                                     |
   +========+===========================================+
   | +0x04  | framebuffer row pointer                   |
   +--------+-------------------------------------------+
   | +0x08  | x start, u16                              |
   +--------+-------------------------------------------+
   | +0x0a  | x end, u16                                |
   +--------+-------------------------------------------+
   | +0x0c  | u, or the perspective u accumulator       |
   +--------+-------------------------------------------+
   | +0x10  | v, or the perspective v accumulator       |
   +--------+-------------------------------------------+
   | +0x14  | the perspective w accumulator             |
   +--------+-------------------------------------------+
   | +0x18  | maybe_g_spanShade, for kinds 4, 9, 19, 20 |
   +--------+-------------------------------------------+

   maybe_g_spanShade is the interesting one. It is restored PER BATCH
   for most kinds but PER SPAN for kinds 4, 9, 19 and 20 - which is what
   a shade term should do: constant across a flat-shaded primitive,
   varying across a Gouraud-shaded one. The arithmetic that consumes it
   has not been read, so the name is inferred from where it is restored.

16.5.  What the port takes from this

   o The flusher resolves ONE filler per batch, outside the inner loop,
     so every span in a batch runs the same code. That is already the
     shape of a modern draw call.

   o The per-batch constants it restores - texture base, interpolant
     steps, shade - are exactly a material and its constants. The per-
     span values are a vertex stream. The deferred path is,
     structurally, already a batched renderer.

   o Nothing here needs self-modification. As the existing plate comment
     says, hoisting the per-batch constants into locals reproduces the
     semantics exactly - and section 12.7.2 established only three
     fillers self-patch at all.


17.  The Setup layer completed, and a name corrected

   maybe_Screen3D_SetupPrim1 at 0x0049e510 is the walker-4 entry.
   Structurally it is maybe_Screen3D_SetupPrim0 with interpolants: the
   same depth average, near-plane clip, trivial reject and quad loop,
   but 2103 bytes instead of 922 because every clipped vertex's U and V
   must be interpolated too [verified].

17.1.  The Setup-to-Emit mapping is one-to-one

   Listing what each Setup function calls completes the layer and lines
   up exactly with the walker interpolant sets of section 10.3
   [verified]:

   +-----------------------+--------+------------------+----------------------+
   | Setup                 | Walker | Interpolants     | Emitter              |
   +=======================+========+==================+======================+
   | SetupPrim0 0x004a4820 | 2      | none, flat blend | EmitTriBlend         |
   +-----------------------+--------+------------------+----------------------+
   | SetupPrim1 0x0049e510 | 4      | U, V             | EmitTriFlatAffine    |
   +-----------------------+--------+------------------+----------------------+
   | SetupPrim2 0x0049fa10 | 5      | U, V, shade      | EmitTriGouraudAffine |
   +-----------------------+--------+------------------+----------------------+
   | SetupPrim3 0x004a0f90 | 6      | U, V, 1/z        | EmitTriFlatPersp     |
   +-----------------------+--------+------------------+----------------------+
   | SetupPrim4 0x004a2630 | 7      | U, V, shade, 1/z | EmitTriGouraudPersp  |
   +-----------------------+--------+------------------+----------------------+

   The last two emitters were FUN_004a0700 and FUN_004a1cb0 and are now
   named from their position in this mapping. Their bodies have NOT been
   read, so the names are inferred - but the symmetry is complete and
   each was already known to write maybe_g_edgeShade and read
   maybe_g_primKind like the other emitters.

   Sizes are telling: 922 bytes for the no-interpolant setup and about
   2000 for each of the other four. The extra bulk is entirely the
   interpolation of clipped vertices - when the near plane cuts an edge,
   every interpolant carried by that walker has to be interpolated at
   the intersection, and the code does it inline per interpolant.

17.2.  A correction to maybe_g_spanShade

   In the previous session 0x006d1f80 was named maybe_g_spanShade,
   reasoning that Screen3D_FlushSpans restores it per span for the
   Gouraud kinds and per batch for the rest - the behaviour of a shade
   term. Reading SetupPrim1 shows that was too quick, and it has been
   renamed maybe_g_spanShade.

   The two globals are the producer and consumer halves of one value
   [verified]:



       Setup/Emit  ->  maybe_g_edgeShade   (0x0068b00c)

                   ->  batch record +0x20

                   ->  maybe_g_spanShade   (0x006d1f80)



   and SetupPrim1 sets both: this one once from the face's original
   three indices before the quad loop, and maybe_g_edgeShade per
   triangle inside it. Both are the mean of the vertices' +0x0c field,
   so they are the same quantity at different stages, not two different
   ones.

   WHAT THE QUANTITY IS remains open, and the name should not be built
   on. Two independent earlier readings call vertex +0x0c a depth, and
   the span buffer does need a front-to-back order. Against that, for
   kinds 4, 9, 19 and 20 the flusher restores this PER SPAN from span
   record +0x18 while routing batch +0x20 to DAT_00655d30 instead - so
   those kinds carry two distinct quantities, and a per-span depth would
   have to be an interpolated one rather than a primitive sort key.

   o Settling it means reading what consumes maybe_g_spanShade inside a
     walker-5 or walker-7 span loop. That is the next concrete question
     in this subsystem.

17.3.  Where the rewrite boundary sits

   The existing plate comment on SetupPrim1 puts it well and the reading
   confirms it: this layer has no self-modifying code, one colour call,
   and is otherwise ordinary geometry - vertex indexing, a near-plane
   clip, an outcode reject and a quad fan. It is portable as written.

   Everything format-dependent is below it, in the emitters and span
   loops. So the five Setup functions are translate-list work even
   though they sit inside screen3d.cpp, and the replace-list boundary
   runs between Setup and Emit rather than at the file edge.


18.  Vertex +0x0c is shade, not depth

   maybe_Screen3D_SetupPrim2 at 0x0049fa10 is the walker-5 entry - the
   Gouraud one. Comparing it against SetupPrim1 settles a question this
   document has had open since section 13, and overturns a reading that
   had been carried since section 7 [verified].

18.1.  The evidence

   The two functions are the same skeleton. The difference is what they
   do with each vertex's +0x0c field:

   +------------------+--------------------------+---------------------+
   |                  | SetupPrim1, flat         | SetupPrim2, Gouraud |
   +==================+==========================+=====================+
   | +0x0c handling   | averaged over 3 vertices | passed per vertex   |
   +------------------+--------------------------+---------------------+
   | emitter arity    | 13 dwords                | 16 dwords           |
   +------------------+--------------------------+---------------------+
   | flat colour call | yes                      | no                  |
   +------------------+--------------------------+---------------------+

   A quantity that is AVERAGED for flat shading and INTERPOLATED PER
   VERTEX for Gouraud shading is a lighting term. A depth would not be
   averaged away for one primitive kind and carried per vertex for
   another.

   It also explains, at last, why Screen3D_FlushSpans restores this
   value PER SPAN for kinds 4, 9, 19 and 20 and PER BATCH for everything
   else: those four are the kinds that interpolate it across the span.
   Section 17.2 flagged exactly that asymmetry as the thing a depth
   reading could not explain.

   And it matches section 10.3 from the other direction: the walker-5
   and walker-7 interpolant sets differ from walkers 4 and 6 by one
   extra term, listed there as SHADE. This is that term.

18.2.  What was renamed

   +------------------------------+-------------------+-----------------------------+
   | Was                          | Now               | What it is                  |
   +==============================+===================+=============================+
   | maybe_g_primDepth 0x0068b00c | maybe_g_edgeShade | mean of the 3 vertex shades |
   +------------------------------+-------------------+-----------------------------+
   | maybe_g_spanDepth 0x006d1f80 | maybe_g_spanShade | the same value, restored    |
   +------------------------------+-------------------+-----------------------------+
   | batch record +0x20           | flat shade        | was labelled depth          |
   +------------------------------+-------------------+-----------------------------+

   One caveat kept: a single dword could hold a packed per-vertex COLOUR
   rather than a scalar intensity, and the existing plate comment on
   SetupPrim2 reads it as colour. Nothing here distinguishes the two,
   and nothing yet depends on which it is. Either way it is a lighting
   term and not a z value.

18.3.  What this invalidates

   o Section 10.1 cited 'the depth field in the batch record' as
     supporting evidence that the scene is drawn front to back. There is
     no depth field. The front-to-back conclusion still stands - it
     follows from the free-list algorithm, which consumes coverage as it
     draws - but that particular clause was wrong and has been struck.

   o Section 7.2's batch record table labelled +0x20 'depth'. Corrected
     to flat shade.

   o Sections 13 and 16 described the value as a sort key. Corrected.

   Nothing was BUILT on the depth reading beyond those references, which
   is the only reason the correction is cheap. It is a good argument for
   the project's habit of tagging inferences: the claim was carried as
   fact for several sections because it sounded reasonable, and only
   fell when a function was read that used the field differently.

18.4.  A naming that went wrong twice

   Worth recording plainly. 0x006d1f80 was first named
   maybe_g_spanShade, from where Screen3D_FlushSpans restores it. It was
   then 'corrected' to maybe_g_spanDepth in section 17 on the strength
   of two earlier readings calling vertex +0x0c a depth. It is now
   maybe_g_spanShade again, on direct evidence.

   The first instinct was right and the correction was the error - made
   by deferring to older prose instead of testing it. The older prose
   was the thing that needed checking.


19.  The perspective setup, and four things it settles

   maybe_Screen3D_SetupPrim3 at 0x004a0f90 is the walker-6 entry - flat
   colour with perspective-correct texturing. The skeleton is
   SetupPrim1's, but the interpolant handling identifies two struct
   fields and confirms two earlier inferences [verified].

19.1.  MR_Vertex +0x18 is the 1/z term

   UVs are carried PREMULTIPLIED by it, and dividing recovers the true
   UV:



       u_texel = vertex[+0x18] * face_u * maybe_g_texDimF

       true_u  = premultiplied_u / vertex[+0x18]



   It is also what the emitter receives as its first three arguments,
   one per vertex. That completes the vertex layout except for two
   fields:

   +--------+----------------------------+----------------+
   | Offset | Field                      | Established in |
   +========+============================+================+
   | +0x00  | unexamined                 | -              |
   +--------+----------------------------+----------------+
   | +0x04  | unexamined                 | -              |
   +--------+----------------------------+----------------+
   | +0x08  | z, for the near-plane test | section 13.2   |
   +--------+----------------------------+----------------+
   | +0x0c  | shade                      | section 18     |
   +--------+----------------------------+----------------+
   | +0x10  | screen x                   | section 13.2   |
   +--------+----------------------------+----------------+
   | +0x14  | screen y                   | section 13.2   |
   +--------+----------------------------+----------------+
   | +0x18  | 1/z                        | here           |
   +--------+----------------------------+----------------+

19.2.  The face record carries four UV pairs

   As floats, normalised, one pair per vertex [verified]:



       +0x04, +0x08   UV of vertex 0

       +0x0c, +0x10   UV of vertex 1

       +0x14, +0x18   UV of vertex 2

       +0x1c, +0x20   UV of vertex 3



   The second pass of the quad loop reads +0x14 and +0x1c, which is the
   same [0],[2],[3] fan the vertex indices describe. So the face record
   holds a quad's worth of UVs whether or not the fourth index is used,
   and the triangle case simply ignores the last pair.

19.3.  Emitter arity confirms the interpolant sets

   The stack cleanup of each emitter is an independent measurement of
   what it carries, and it comes out exactly right [verified]:

   +----------------------+------+--------+------------------+
   | Emitter              | RET  | dwords | Interpolants     |
   +======================+======+========+==================+
   | EmitTriBlend         | 0x18 | 6      | none             |
   +----------------------+------+--------+------------------+
   | EmitTriFlatAffine    | 0x34 | 13     | U, V             |
   +----------------------+------+--------+------------------+
   | EmitTriGouraudAffine | 0x40 | 16     | U, V, shade      |
   +----------------------+------+--------+------------------+
   | EmitTriFlatPersp     | 0x40 | 16     | U, V, 1/z        |
   +----------------------+------+--------+------------------+
   | EmitTriGouraudPersp  | 0x4c | 19     | U, V, shade, 1/z |
   +----------------------+------+--------+------------------+

   13 is the base - six screen coordinates, the texture page and six
   UVs. Shade adds three, 1/z adds three, and having both adds six.
   EmitTriBlend's 6 is just three screen positions, with no texture page
   at all, which is what a flat blend needs.

   This reproduces the slot table of section 10.3 from a completely
   different direction, and it upgrades the two perspective emitter
   names from inferred to verified. They were named last session purely
   from their position in the Setup-to-Emit mapping.

19.4.  Near clipping is perspective-correct

   Worth recording verbatim, because it is the sort of thing a
   reconstruction gets subtly wrong. Rather than lerping the
   premultiplied UV, it divides 1/z out at both ends, interpolates in z,
   then re-premultiplies at the near plane [verified]:



       ua = u_a / w_a;

       ub = u_b / w_b;

       u  = (((ub - ua) / (z_b - z_a)) * (nearZ - z_a) + ua)

            / maybe_g_nearPlaneZ;



   The affine setups do the same interpolation without the divisions,
   which is exactly the difference between the two families and another
   reason walker 6 costs more than walker 4.

19.5.  A fourth confirmation of the texture size

   maybe_g_texDimF at 0x004d1fb0 is the float 256.0, and the face UVs
   are normalised 0..1 and scaled by it. So the texture is 256 wide,
   established now four separate ways: the mask-and-shift addressing of
   section 12.3, the ROR byte-concatenation of section 12.7, the walker
   table, and this scale factor.

   It sits immediately before maybe_g_subdivRecip at 0x004d1fb8, which
   is a DOUBLE. Reading the region as one array of floats would give
   256.0, 0.0, and a nonsense value - the same trap section 12.1 records
   for the subdivision reciprocal.


20.  The Setup family closed, and the walker index decoded

   maybe_Screen3D_SetupPrim4 at 0x004a2630 is the last of the five. It
   is the fullest variant and composes the two axes exactly as the other
   four predict [verified]:

   o From SetupPrim2 - no Color_Convert555ToSurface call, each vertex's
     +0x0c shade forwarded separately.

   o From SetupPrim3 - UVs premultiplied by vertex +0x18, and the
     perspective-correct near clip that divides 1/z out, interpolates in
     z and re-premultiplies.

   Its emitter call is 19 dwords, which is the arity section 19.3
   measured from the stack cleanup: 3 for 1/z, 6 screen coordinates, 1
   texture page, 6 UVs, 3 shades.

20.1.  The walker index is a bitfield

   With all five read, the numbering stops looking arbitrary. Across the
   four textured setups [verified]:



       walker = 4 | (perspective ? 2 : 0) | (gouraud ? 1 : 0)



   +--------+------+---------+-------------+------------+
   | Walker | Bits | Shading | Texturing   | Setup      |
   +========+======+=========+=============+============+
   | 4      | 100  | flat    | affine      | SetupPrim1 |
   +--------+------+---------+-------------+------------+
   | 5      | 101  | Gouraud | affine      | SetupPrim2 |
   +--------+------+---------+-------------+------------+
   | 6      | 110  | flat    | perspective | SetupPrim3 |
   +--------+------+---------+-------------+------------+
   | 7      | 111  | Gouraud | perspective | SetupPrim4 |
   +--------+------+---------+-------------+------------+

   Bit 0 selects per-vertex shade, bit 1 selects perspective. The split
   is directly checkable: walkers 4 and 6 call Color_Convert555ToSurface
   for a flat primitive colour, walkers 5 and 7 do not and pass three
   per-vertex values instead.

   Walker 2, the flat blend of SetupPrim0, sits outside the scheme
   because it carries no texture at all - which is also why its emitter
   takes 6 dwords rather than 13.

   This is the same two-axis structure the FILLERS have, one layer down.
   Section 12.10 found six span operations crossed with an
   affine/perspective wrapper; here the Setup layer is four variants
   crossed the same way. The renderer is built as a product of small
   independent choices at every level, which is why the function count
   is large and the actual variety is small.

20.2.  The Setup layer, complete

   +-----------------------+--------+-------+--------------+-------------+---------------+
   | Setup                 | Walker | Bytes | Colour       | UV          | Emitter arity |
   +=======================+========+=======+==============+=============+===============+
   | SetupPrim0 0x004a4820 | 2      | 922   | flat, halved | none        | 6             |
   +-----------------------+--------+-------+--------------+-------------+---------------+
   | SetupPrim1 0x0049e510 | 4      | 2103  | flat         | affine      | 13            |
   +-----------------------+--------+-------+--------------+-------------+---------------+
   | SetupPrim2 0x0049fa10 | 5      | 2127  | per vertex   | affine      | 16            |
   +-----------------------+--------+-------+--------------+-------------+---------------+
   | SetupPrim3 0x004a0f90 | 6      | 2009  | flat         | perspective | 16            |
   +-----------------------+--------+-------+--------------+-------------+---------------+
   | SetupPrim4 0x004a2630 | 7      | 1997  | per vertex   | perspective | 19            |
   +-----------------------+--------+-------+--------------+-------------+---------------+

   All five share one skeleton: average the shade, fetch the texture
   page, near-clip against maybe_g_nearPlaneZ with
   maybe_Screen3D_ClipEdgeNear, apply the outcode reject, and run the
   body twice for a quad. Only the interpolant handling differs.

   None of them contains self-modifying code, format-specific arithmetic
   beyond the single colour conversion, or any assumption about pixel
   width. The whole layer is portable geometry, and section 17.3's
   conclusion holds for all five: the replace-list boundary runs between
   Setup and Emit, not at the file edge.

20.3.  What is left in this subsystem

   o The five emitters. Only maybe_Screen3D_EmitTriBlend has been read

21.  The first textured emitter

   maybe_Screen3D_EmitTriFlatAffine at 0x0049dde0 is the walker-4
   emitter and the first with interpolants to be read in full - section
   14 covered only maybe_Screen3D_EmitTriBlend, which carries none.
   Three things come out of it [verified].

21.1.  A third interpolant tier

   Section 12.5 described the filler argument set as two tiers, per
   triangle and per span. There is one in between:

   +--------------+-------------------+----------------+-------------------+
   | Tier         | Globals           | Written by     | Read by           |
   +==============+===================+================+===================+
   | per triangle | g_texStepU / V    | Tri and Emit   | ClipSpan, fillers |
   +--------------+-------------------+----------------+-------------------+
   | per SCANLINE | maybe_g_edgeU / V | Tri and Emit   | ClipSpan, Walk4/5 |
   +--------------+-------------------+----------------+-------------------+
   | per span     | g_spanU / V       | ClipSpan, Walk | the fillers       |
   +--------------+-------------------+----------------+-------------------+

   maybe_g_edgeU and maybe_g_edgeV at 0x0068b018 and 0x0068b01c hold the
   interpolant at the LEFT EDGE of the current scanline. The emitter
   steps them down the edge alongside the x values; the clipper then
   advances from the edge to wherever the visible sub-span actually
   starts and leaves that in g_spanU / g_spanV.

   Only the affine consumers read them. Walk6 and Walk7 do not, because
   the perspective paths carry maybe_g_perspU, ...V and ...W as floats
   instead - the same split section 16.3 found in the flusher.

21.2.  One emitter, both dispatch modes

   EmitTriBlend gated its whole scanline loop on g_spanAccepting and
   always queued, because kind 12 always defers. This emitter serves
   eleven kinds of both sorts, and branches [verified]:



       if (maybe_g_spanDeferMode == 0 || g_spanAccepting) {

           ...walk the scanlines, calling maybe_g_spanClipper...

           if (maybe_g_spanDeferMode && spansEmitted)

               ...append the batch record...

       }



   So immediate kinds draw and queue nothing; deferred kinds require the
   accepting flag and then queue. That is a cleaner statement of the
   mechanism than section 14 could give from the always-deferring case,
   and it is where the static per-kind defer flag of section 15.4 is
   actually consumed.

21.3.  The batch record, from the producing side

   The record write confirms section 16's union reading and, more
   usefully, confirms section 18's rename from the OTHER end [verified]:

   +--------+--------------------------------+
   | Offset | Written from                   |
   +========+================================+
   | +0x00  | maybe_g_primKind               |
   +--------+--------------------------------+
   | +0x04  | spans emitted by this triangle |
   +--------+--------------------------------+
   | +0x08  | g_texBase                      |
   +--------+--------------------------------+
   | +0x0c  | maybe_g_spanFlatColor          |
   +--------+--------------------------------+
   | +0x14  | g_texStepU                     |
   +--------+--------------------------------+
   | +0x18  | g_texStepV                     |
   +--------+--------------------------------+
   | +0x20  | maybe_g_edgeShade              |
   +--------+--------------------------------+

   Section 7.2 labelled +0x20 'depth'. The producer writes
   maybe_g_edgeShade into it and Screen3D_FlushSpans restores it into
   maybe_g_spanShade, so both ends now agree it is the shade term.
   Section 18 corrected the label from the consuming side; this is the
   producing side saying the same thing.

   It also writes maybe_g_primKind rather than a literal, which is the
   contrast section 14.2 drew with EmitTriBlend's hardcoded 12.

21.4.  A guard on degenerate triangles

   Before computing any gradient the emitter tests [verified]:



       n = __ftol(...);

       if (maybe_g_minDenom <= (float)n) { ...compute steps... }

       /* otherwise return, drawing nothing */



   maybe_g_minDenom at 0x004d1f4c is the float 1.0, and it is read by
   all nine Screen3D_TriKn, all four textured emitters and
   maybe_Screen3D_ClipEdgeNear - the shared guard of the entire triangle
   path.

   RESOLVED in section 23: n is the triangle's AREA, the cross product
   that becomes the divisor of the gradient formula. maybe_g_minDenom is
   therefore a minimum triangle area of 1.0, and the test drops
   degenerate and sub-pixel triangles before anything can divide by zero
   [verified].


22.  The shade interpolant, and a third rename

   maybe_Screen3D_EmitTriGouraudAffine at 0x0049f1e0 is the walker-5
   emitter. It is maybe_Screen3D_EmitTriFlatAffine with one more
   interpolant carried through every stage, and following that
   interpolant completes a picture that sections 18, 16 and 21 each had
   a piece of [verified].

22.1.  Shade has the same three tiers as U and V

   +--------------+---------------+---------------+-------------------+
   | Tier         | U             | V             | Shade             |
   +==============+===============+===============+===================+
   | per triangle | g_texStepU    | g_texStepV    | maybe_g_shadeStep |
   +--------------+---------------+---------------+-------------------+
   | per scanline | maybe_g_edgeU | maybe_g_edgeV | maybe_g_edgeShade |
   +--------------+---------------+---------------+-------------------+
   | per span     | g_spanU       | g_spanV       | maybe_g_spanShade |
   +--------------+---------------+---------------+-------------------+

   The Gouraud emitter does everything the flat one does, three times
   over instead of twice: the Y sort swaps s0, s1 and s2 along with the
   coordinates and UVs; a third __ftol computes maybe_g_shadeStep next
   to the two UV gradients; and maybe_g_edgeShade is initialised at the
   top vertex and stepped once per scanline next to maybe_g_edgeU and
   maybe_g_edgeV.

22.2.  Batch record +0x20 is a union slot

   The one place the two emitters genuinely differ [verified]:

   +----------------------+-------------------------------------+
   | Emitter              | writes into batch +0x20             |
   +======================+=====================================+
   | EmitTriFlatAffine    | maybe_g_edgeShade, a constant shade |
   +----------------------+-------------------------------------+
   | EmitTriGouraudAffine | maybe_g_shadeStep, a gradient       |
   +----------------------+-------------------------------------+

   and Screen3D_FlushSpans restores it accordingly - into
   maybe_g_shadeStep for kinds 4, 9, 19 and 20, into maybe_g_spanShade
   for everything else. Section 16.2's switch reading and section 18's
   shade identification now join up: the slot holds a constant for flat
   kinds and a gradient for Gouraud kinds, and the kind tells the
   flusher which.

   That also finally explains the asymmetry section 18.1 could only
   describe. maybe_g_spanShade is restored PER SPAN for exactly kinds 4,
   9, 19 and 20 because those are the Gouraud kinds, and a Gouraud span
   needs a start value of its own as well as the gradient the batch
   supplies.

22.3.  A global renamed three times

   0x0068b00c has now been called three things, and the history is worth
   keeping because each rename was caused by reading a function the
   previous name could not describe:

   +-----------------------------------+--------------------------------------+
   | Name                              | Why it was wrong                     |
   +===================================+======================================+
   | maybe_g_primDepth                 | vertex +0x0c is not a z value at all |
   +-----------------------------------+--------------------------------------+
   | maybe_g_edgeShade (was primShade) | right quantity, wrong scope          |
   +-----------------------------------+--------------------------------------+
   | maybe_g_edgeShade                 | current                              |
   +-----------------------------------+--------------------------------------+

   o The first fell in section 18, when SetupPrim2 was seen passing
     +0x0c per vertex to a Gouraud emitter - something no depth would
     be.

   o The second fell here, when the Gouraud emitter was seen STEPPING it
     once per scanline. A per-primitive value is not stepped; a per-
     scanline edge value is. For a flat primitive the two descriptions
     coincide, which is why the wrong scope survived reading three flat
     setups.

   The pattern in both cases is the same: a name derived from one usage
   site survived until a site with different usage was read. Neither
   error was detectable from the function that introduced it, which is
   an argument for reading a family through before trusting names drawn
   from any one member of it.

22.4.  What the port takes from this

   The three-tier structure is uniform across all three interpolants
   and, from section 16.3, across the perspective ones too. A
   replacement does not need to reproduce the tiers - a GPU interpolates
   from vertex attributes directly - but it does need to know that there
   are exactly three interpolants in the affine path and four in the
   perspective one, and that shade is a scalar carried alongside U and V
   rather than anything more elaborate.


23.  The perspective emitter, and the 16 that ties it together

   maybe_Screen3D_EmitTriFlatPersp at 0x004a0700 is
   maybe_Screen3D_EmitTriFlatAffine with every fixed-point interpolant
   replaced by a float. Reading it completes the interpolant tables and
   settles two things left open elsewhere [verified].

23.1.  Three tiers again

   +--------------+-------------------+----------------------------+
   | Tier         | Affine            | Perspective                |
   +==============+===================+============================+
   | per triangle | g_texStepU / V    | maybe_g_perspStepU / V / W |
   +--------------+-------------------+----------------------------+
   | per scanline | maybe_g_edgeU / V | maybe_g_perspEdgeU / V / W |
   +--------------+-------------------+----------------------------+
   | per span     | g_spanU / V       | maybe_g_perspU / V / W     |
   +--------------+-------------------+----------------------------+

   The new middle row is at 0x00624b00, 0x00624b08 and 0x00624b10. They
   are written and stepped only by the two perspective emitters and read
   only by Walk6 and Walk7 - the exact mirror of maybe_g_edgeU and
   maybe_g_edgeV with Walk4 and Walk5. Note they are not contiguous:
   maybe_g_spanXLeft sits between V and W at 0x00624b0c.

23.2.  Where the 16 comes from

   The gradients are computed twice, and the factor between them closes
   a loop with section 12.1 [verified]:



       grad = ((du * dy1) + (du * dy2)) / area;   /* per pixel */

       step = grad * maybe_g_subdivLen;           /* per block */



   maybe_g_subdivLen at 0x004d1fac is the float 16.0. So the emitter
   hands the fillers a step sized for one 16-pixel block, the filler
   advances by it and derives the per-pixel delta with a shift of 4, and
   a final partial block is scaled by maybe_g_subdivRecip - the double
   1/16 at 0x004d1fb8.

   The pair 16.0 and 1/16 bracket the whole perspective scheme from
   opposite ends, and they were found five sections apart from opposite
   ends of the pipeline.

   They sit near each other but are three different types and must not
   be read as one array: 0x004d1fac is a float 16.0, 0x004d1fb0 is
   maybe_g_texDimF at 256.0f, and 0x004d1fb8 is a DOUBLE 0.0625. That
   region has now caught the same misreading twice.

23.3.  maybe_g_minDenom is a minimum triangle area

   Section 21.4 recorded the guard but could not say what it tested. The
   perspective emitter shows it directly: the guarded value is the
   divisor of the gradient formula, which is the cross product of the
   two edge vectors - the triangle's area [verified].



       area = __ftol(cross product);

       if (maybe_g_minDenom <= (float)area) { ...gradients... }

       /* else drop the primitive entirely */



   So a triangle of area below 1.0 is discarded before any division.
   Read by all nine Screen3D_TriKn, all four textured emitters and
   maybe_Screen3D_ClipEdgeNear, it is the degenerate guard of the whole
   triangle path.

23.4.  The batch record, all four writers agreed

   +--------+-------------------+-------------------+--------------------+
   | Offset | Affine flat       | Affine Gouraud    | Persp flat         |
   +========+===================+===================+====================+
   | +0x14  | g_texStepU        | g_texStepU        | maybe_g_perspStepU |
   +--------+-------------------+-------------------+--------------------+
   | +0x18  | g_texStepV        | g_texStepV        | maybe_g_perspStepV |
   +--------+-------------------+-------------------+--------------------+
   | +0x1c  | -                 | -                 | maybe_g_perspStepW |
   +--------+-------------------+-------------------+--------------------+
   | +0x20  | maybe_g_edgeShade | maybe_g_shadeStep | maybe_g_edgeShade  |
   +--------+-------------------+-------------------+--------------------+

   Every slot is a union whose meaning the primitive kind selects, and
   Screen3D_FlushSpans restores each into the global the matching filler
   expects. Section 16.2 derived that from the consuming side by
   enumerating the switch; three of the four producers have now been
   read and they agree with it exactly.


24.  The last emitter, and a third of the kinds draw nothing

   maybe_Screen3D_EmitTriGouraudPersp at 0x004a1cb0 is the fifth and
   last emitter. It is exactly the union of the previous two with no
   surprises, which is itself the useful result - the family really is a
   product of two independent choices and not five hand-written variants
   [verified].

24.1.  The batch union is indexed by the walker bits

   With all four textured producers read, the union layout is complete
   and regular:

   +--------+-------------+----------------+------------+---------------+
   | Offset | Affine flat | Affine Gouraud | Persp flat | Persp Gouraud |
   +========+=============+================+============+===============+
   | +0x14  | g_texStepU  | g_texStepU     | perspStepU | perspStepU    |
   +--------+-------------+----------------+------------+---------------+
   | +0x18  | g_texStepV  | g_texStepV     | perspStepV | perspStepV    |
   +--------+-------------+----------------+------------+---------------+
   | +0x1c  | -           | -              | perspStepW | perspStepW    |
   +--------+-------------+----------------+------------+---------------+
   | +0x20  | edgeShade   | shadeStep      | edgeShade  | shadeStep     |
   +--------+-------------+----------------+------------+---------------+

   Bit 0 of the walker index - Gouraud - decides whether +0x20 holds a
   constant shade or a shade gradient. Bit 1 - perspective - decides
   whether +0x1c is meaningful and whether +0x14 and +0x18 are fixed
   point or float. The record layout is indexed by exactly the two bits
   section 20.1 found in the walker number.

24.2.  Walker 7 serves one kind, and it draws nothing

   Dumping g_spanTable by walker index gives the population of each path
   [verified]:

   +------------------------+-------+-------------------+
   | Walker                 | Kinds | Of which deferred |
   +========================+=======+===================+
   | 0, no walker           | 7     | 5                 |
   +------------------------+-------+-------------------+
   | 2, flat blend          | 1     | 0                 |
   +------------------------+-------+-------------------+
   | 4, affine flat         | 11    | 8                 |
   +------------------------+-------+-------------------+
   | 5, affine Gouraud      | 4     | 2                 |
   +------------------------+-------+-------------------+
   | 6, perspective flat    | 8     | 5                 |
   +------------------------+-------+-------------------+
   | 7, perspective Gouraud | 1     | 0                 |
   +------------------------+-------+-------------------+

   So the most elaborate path in the renderer - the 19-argument emitter,
   the 1997-byte setup, four interpolants carried through clipping and
   edge walking - is used by a SINGLE primitive kind, number 29. That
   kind is never deferred, and its span filler is one RET instruction.

   It walks a triangle interpolating U, V, shade and 1/z, and then draws
   no pixels. Since it is immediate, its clipper consumes the span-
   buffer free list on the way past - which is the OCCLUDER pattern the
   Screen3D_DispatchPrimitive plate comment already describes for kind
   3: claim the coverage, paint nothing.

   o The likeliest explanations are that the Defer clippers do consume

24.4.  The emitter family is closed

   All five emitters have now been read in full, and with them every
   layer of the software rasterizer: dispatch, setup, emit, clip, fill.

   Screen3D_TriKn of the specialised chains, which section 14.1

25.  A Defer clipper read, and the no-op kinds explained

   maybe_Screen3D_Walk4Defer at 0x0049dbf0 was read to settle the
   question section 24.3 raised. It settles that and confirms two other
   things from the opposite end [verified].

25.1.  The free list really is untouched

   The walk is strictly read-only - psVar = psVar->next and nothing
   else. No node is shrunk, unlinked or split anywhere in the function.
   Section 10.2's table was right.

   That resolves section 24.3. A kind that is BOTH deferred AND has an
   empty filler claims no coverage and paints no pixels:

   +---------------------+--------------------------------------------+---------------------+
   | Filler empty and... | Effect                                     | Kinds               |
   +=====================+============================================+=====================+
   | immediate           | OCCLUDER - claims coverage, paints nothing | 1, 3, 5, 18, 28, 29 |
   +---------------------+--------------------------------------------+---------------------+
   | deferred            | INERT - claims nothing, paints nothing     | 2, 4, 8, 9, 50      |
   +---------------------+--------------------------------------------+---------------------+

   The immediate group is a real technique: the Now clippers shrink,
   unlink and split nodes as they go, so the coverage is consumed and
   later primitives are clipped against it. That is the occluder the
   Screen3D_DispatchPrimitive plate comment describes for chain kind 3.

   The deferred group does nothing at all. Those five kinds occupy a
   table slot, run a setup, walk a triangle, queue span records and have
   them replayed into a routine that returns. They read as disabled or
   vestigial features rather than a technique [inferred - nothing
   observed contradicts it, but no positive evidence of intent either].

25.2.  Two corrections to section 24.3

   o The count was wrong. It is TWELVE kinds with an empty filler, not
     ten - eleven with a filler of three bytes or fewer, plus kind 2
     whose 16-byte filler pushes a stack frame and jumps straight to its
     own epilogue. All were checked at the byte level: every short one
     is a genuine 0xc3 RET followed by 0xcc padding, not a mis-bounded
     function.

   o Kind 2 was omitted entirely, on the strength of its filler being 16
     bytes rather than 1. Size was the wrong test.

   Twelve of thirty-two is 37 percent of the primitive kinds drawing no
   pixels, which is a large enough share that a port should treat
   occluders as a first-class case rather than an oddity.

25.3.  Deferral depends on the span buffer, not just the variant

   A detail that changes how section 10.2 should be read. When
   g_spanBufferEnabled is 0, the Defer variant does not defer
   [verified]:



       if (g_spanBufferEnabled == 0) {

           ...clamp to the screen...

           (*maybe_g_spanFiller)();     /* immediate */

           return;

       }

       ...otherwise queue records...



   So the Now/Defer distinction only exists while the span buffer is on.
   With it off, all eight clippers behave identically - clamp and fill -
   and the batch queue is never written.

25.4.  The three tiers, confirmed from the consumer side

   Section 21.1 introduced the per-scanline edge tier from the emitter
   side. The clipper shows the other half of it [verified]:



       rec[+0x0c] = maybe_g_edgeU

                  + g_texStepU * (spanStart - edgeStart);



   The clipper takes the scanline's edge value and advances it by the
   per-pixel gradient to wherever the visible sub-span actually begins.
   Per-triangle gradient, per-scanline edge, per-span start - now
   verified from both ends.

   The record it writes is +0x04 row pointer, +0x08 x0, +0x0a x1, +0x0c
   u, +0x10 v, which is exactly what Screen3D_FlushSpans reads back in
   section 16.4. That is the third producer/consumer pair in this
   subsystem to agree offset for offset.


26.  The Now twin, and the occluder claim verified

   maybe_Screen3D_Walk4Now at 0x0049d9e0 is the immediate twin of the
   clipper read in section 25. Reading it turns the occluder reading
   from something inherited out of section 10.2 into something checked
   [verified].

26.1.  All three list operations, seen

   +--------------+-------------------------------------------------------+
   | Operation    | Code                                                  |
   +==============+=======================================================+
   | shrink right | psVar->x1 = spanStart                                 |
   +--------------+-------------------------------------------------------+
   | shrink left  | psVar->x0 = spanEnd                                   |
   +--------------+-------------------------------------------------------+
   | unlink       | *g_spanCurScanline = psVar->next, or prev->next = ... |
   +--------------+-------------------------------------------------------+
   | split        | bump-allocate from g_spanFreePool, link the remainder |
   +--------------+-------------------------------------------------------+

   Each visible sub-range is drawn by calling (*maybe_g_spanFiller)()
   and THEN the list is edited. The two are independent: the editing
   happens whatever the filler does.

   That is precisely what makes an empty filler an occluder. A kind
   whose filler is a bare RET still runs every shrink, unlink and split,
   so it consumes coverage and clips everything drawn after it while
   painting nothing itself. Section 25.1 asserted this from section
   10.2's table; it is now read directly.

   The g_spanBufferEnabled == 0 path is identical to the Defer twin's,
   which confirms section 25.3 from the second of the two functions.

26.2.  One free-list algorithm, nine copies

   The five-statement split sequence here is byte-identical to the one
   in maybe_Screen3D_ClipSpanFlatScalar and ...MMX. Counting the
   functions that write g_spanFreeCount gives the full population
   [verified]:

   +-----------------------------------------+---------------------------+
   | Function                                | Role                      |
   +=========================================+===========================+
   | Screen3D_BeginFrame                     | seeds and resets the pool |
   +-----------------------------------------+---------------------------+
   | maybe_Screen3D_Walk4Now .. Walk7Now     | the four Now clippers     |
   +-----------------------------------------+---------------------------+
   | maybe_Screen3D_ClipSpanFlatScalar / MMX | the flat pair             |
   +-----------------------------------------+---------------------------+
   | Screen3D_ClipSpanK1Full / K1Half / K3   | three of the eight Kn     |
   +-----------------------------------------+---------------------------+

   Nine clippers carry the same allocator. Like the subdivision wrapper
   of section 12.11.1 and the edge walker of section 14.1, it reads as
   one macro or include instantiated repeatedly rather than nine hand-
   written copies - the third such family in this subsystem.

26.3.  Five ClipSpanKn do not split - resolved in section 27

   Screen3D_ClipSpanK2Full, K2Half, K4, K42 and K9 never write
   g_spanFreeCount, so they never split a free node. The other three do.

   The obvious guess is that the non-splitting five are the deferred
   chains - the Screen3D_DispatchPrimitive plate comment does say chain
   kind 4 queues records and that its immediate path is a RET, and
   section 25.1 established that Defer clippers leave the list alone.
   But the specialised chains are dispatched by the switch rather than
   through g_spanTable, so their defer behaviour is not governed by the
   table flag and the correspondence has NOT been checked [guess].

   RESOLVED in section 34.2. The correspondence does hold, but deferral
   is not the cause of it. Both facts follow from a third: whether the
   kind writes every pixel of its span.

   o Reading Screen3D_ClipSpanK2Full against Screen3D_ClipSpanK1Full
     would settle it, and would also say whether the specialised chains
     have a Now/Defer split at all or simply hardcode one behaviour per
     chain.

26.4.  The span buffer, end to end

   With both twins read the mechanism is complete:



       BeginFrame   seeds one free node per scanline, full width

       Now clipper  draws each free sub-range, then consumes it

       Defer clipper records each free sub-range, consumes nothing

       FlushSpans   replays the records into the per-kind filler



   Front-to-back ordering makes the consumption correct: whatever draws
   first claims the pixels, and later primitives find less free list to
   draw into. That is the whole hidden-surface algorithm, and it is why
   there is no z-buffer.

   The deferred path exists so translucent geometry can be drawn after
   the opaque geometry has claimed its coverage without itself claiming
   any - which is exactly what section 15.4 found the per-kind defer
   flag selecting.


27.  The specialised clippers split the same way

   Screen3D_ClipSpanK2Full at 0x004aa750 was read to settle section
   26.3, and it does: it is a DEFER-style clipper [verified]. The free-
   list walk is read-only, each visible sub-range becomes a 0x1c-byte
   record in g_spanBuffer, and the 0x2800 cap clears g_spanAccepting.
   Nothing is shrunk, unlinked or split.

   Structurally it is maybe_Screen3D_Walk4Defer. The only difference is
   that it calls Screen3D_SpanTexKeyedK2Full directly where the Walk
   variant goes through the maybe_g_spanFiller pointer - one indirect
   call saved per scanline, which is the whole reason the specialised
   chains exist.

27.1.  The same Now/Defer division, twice

   +----------------+---------------+-----------------------------+
   | Style          | Walk family   | Specialised family          |
   +================+===============+=============================+
   | Now, consumes  | Walk4-7 Now   | K1Full, K1Half, K3          |
   +----------------+---------------+-----------------------------+
   | Defer, records | Walk4-7 Defer | K2Full, K2Half, K4, K42, K9 |
   +----------------+---------------+-----------------------------+

   And the division matches the defer flag g_spanTable carries for the
   same kind numbers. The switch path and the table path reach their
   clippers by completely different routes - one hardcoded per chain,

27.2.  Where the half-brightness modes come from

   The plate comment on this function, from earlier work, contains the
   answer to something section 12.10 recorded without explaining. The
   Full and Half variants of kinds 1 and 2 are not two texturing modes -
   they are a TWO-LEVEL LIGHTING QUANTISATION [verified]:



       Screen3D_DispatchPrimitive tests vertex[0] + 0x0c

       against 0x3dfff, which is 31.0 in 19.13 fixed point



           above  -> the Full chain, texel written unchanged

           at or  -> the Half chain, texel >> 1 & g_halveMask

           below



   So the halved fillers catalogued in section 12.10 -
   SpanTexKeyedHalfAffine, SpanTexHalfPersp and the rest - are the dim
   half of a two-level light, not a separate mode. The renderer
   quantises lighting to exactly two levels and pays for it by
   duplicating the entire three-layer chain rather than branching inside
   the per-pixel loop.

   This is also independent corroboration of section 18. That section
   identified vertex +0x0c as a shade term by watching SetupPrim2 pass
   it per vertex to a Gouraud emitter; this comment, written earlier and
   from a different function, calls it a light intensity and gives the
   threshold. Two unrelated routes to the same conclusion.

28.  The near clipper completes the vertex

   maybe_Screen3D_ClipEdgeNear at 0x0049d8f0 is 227 bytes with fifteen
   callers, and it is the only function that builds a whole MR_Vertex
   from scratch. That makes it the clearest statement of both the
   projection and the record [verified].

28.1.  The record is complete

   +--------+-------+---------+-----------------------------+
   | Offset | Type  | Field   | Established by              |
   +========+=======+=========+=============================+
   | +0x00  | float | camX    | this function               |
   +--------+-------+---------+-----------------------------+
   | +0x04  | float | camY    | this function               |
   +--------+-------+---------+-----------------------------+
   | +0x08  | float | camZ    | the near test, section 13.2 |
   +--------+-------+---------+-----------------------------+
   | +0x0c  | int   | shade   | sections 18 and 22          |
   +--------+-------+---------+-----------------------------+
   | +0x10  | int   | screenX | section 13.2                |
   +--------+-------+---------+-----------------------------+
   | +0x14  | int   | screenY | section 13.2                |
   +--------+-------+---------+-----------------------------+
   | +0x18  | float | invZ    | section 19.1                |
   +--------+-------+---------+-----------------------------+

   camX and camY are written as the linear interpolation of the two
   input vertices toward the near plane, which identifies them and
   confirms the guess in section 13.2 that the first three fields are a
   float x, y, z triple. MR_Vertex has been created in the database and
   written up in structs/MR_Vertex.txt.

   It also re-derives +0x18 independently of section 19.1: the clipped
   vertex lies exactly on the near plane, and the value written is 1.0 /
   maybe_g_nearPlaneZ. A second route to the same field.

28.2.  The projection, in one place



       t            = (nearZ - a->camZ) / (b->camZ - a->camZ);

       out->camX    = a->camX + t * (b->camX - a->camX);

       out->camY    = a->camY + t * (b->camY - a->camY);

       out->camZ    = nearZ;          /* exact, not interpolated */

       out->invZ    = 1.0f / nearZ;   /* therefore exact too     */

       out->screenX = g_viewCentreX + (int)project(camX);

       out->screenY = g_viewCentreY - (int)project(camY);



   o Screen Y is viewCentreY MINUS the projected value, so camera Y
     grows upward and screen Y downward - the usual flip, worth
     recording because a port that gets it wrong produces a vertically
     mirrored image that still looks plausible.

   o The 1.0 numerator is maybe_g_minDenom, the constant the emitters
     use as a minimum triangle area. One shared float, two unrelated
     roles; the name is narrower than the constant.

28.3.  What the vertex does not carry

29.  A second texture format, found by reading a copy

   Screen3D_TriK2Full at 0x004aa940 was read to check the claim that the

29.1.  maybe_g_texPalette

   The global at 0x0065e1cc, carried through this document as
   maybe_g_batchExtra because it was known only by where it was stored,
   is the TEXTURE PALETTE. Screen3D_SpanTexK1Full uses it like this:



       MOV EBP, [g_texBase]

       MOV AL,  byte ptr [EBX + EBP*1]    ; an 8-BIT texel

       MOV EBX, [maybe_g_texPalette]

       MOV AX,  word ptr [EBX + EAX*2]    ; 256-entry u16 palette

       MOV word ptr [ECX-2], AX           ; store the pixel



   It is set once per primitive by all eight Screen3D_DrawPrimKn from
   their own argument, copied into batch record +0x10 by the Tri layer,
   and restored by Screen3D_FlushSpans for kinds 19, 20, 40, 41, 42 and
   51 - which is exactly the set section 16 listed as reading +0x10
   without knowing why.

29.2.  The renderer has TWO texture formats

   +------------+---------------------+--------------------+
   |            | Table path          | Specialised chains |
   +============+=====================+====================+
   | texel size | 16 bits             | 8 bits             |
   +------------+---------------------+--------------------+
   | palette    | none                | 256 entries of u16 |
   +------------+---------------------+--------------------+
   | index mask | 0x1fffe byte offset | 0xffff byte offset |
   +------------+---------------------+--------------------+
   | dimensions | 256 x 256           | 256 x 256          |
   +------------+---------------------+--------------------+
   | read in    | section 12.3        | here               |
   +------------+---------------------+--------------------+

   Both are 256 x 256 - the two masks are the same 65536 texels at two
   bytes and at one. Section 12.3 established the 16-bit form from the
   Walk-path fillers and this document then treated it as THE texture
   format. It is the format of one path.

   That also explains a detail section 12.7 recorded without comment:
   Screen3D_SpanCopyTexels was called pixel-format agnostic BY
   CONSTRUCTION because it copies texels verbatim. True of a 16-bit
   direct texel; a paletted chain cannot be, because the palette entries
   are in surface format and must be rebuilt when the format changes.

29.3.  What this changes for the port

   o A replacement needs BOTH sampling paths, or must convert the 8-bit
     textures to direct colour at load time. The second is almost
     certainly right for a modern target, but it is a decision that has
     to be made rather than a detail that disappears.

   o The palette is per PRIMITIVE, not per texture - it arrives as an
     argument to DrawPrimKn and is queued per batch. Several primitives
     can share a texture with different palettes, which is a real
     feature and would be lost by a naive conversion.

   o Palette entries are in surface format, so they are part of the
     16-bit dependency catalogue that section 12.8 concluded was
     confined to pixel width. That conclusion needs this caveat: the
     palette is colour data in surface format and has to be rebuilt if
     the format changes.

29.4.  A judgement that was wrong

   Section 27.3 said of the remaining unread functions that only
   ClipEdgeNear was likely to contain anything new, and section 28.4
   repeated it. The very next function read - one of the seven dismissed
   as copies - produced the palette, a second texture format and a
   caveat to section 12.8.

   The structural claim was right: TriK2Full IS the same edge walker.
   What that reasoning missed is that per-chain SPECIALISATION lives in
   exactly the few instructions a structural comparison discards - a
   literal instead of a global, one extra field in a record. Being a
   copy of a known shape does not make a function uninformative.


30.  The paletted filler, and one formula for both

   Screen3D_SpanTexK1Full at 0x004a7240 is the paletted counterpart of
   the direct-colour fillers of section 12. Setting the two addressing
   schemes side by side shows they are ONE formula parameterised by
   texel size [verified]:



   8-bit:   off = ((v & 0xffffe01f) >> 5) + (u >> 13)   & 0xffff

            px  = palette[ ((u8 *)g_texBase)[off] ]



   16-bit:  off = ((v & 0xffffe01f) >> 4)

                + ((u & 0xffffefff) >> 12)              & 0x1fffe

            px  = *(u16 *)(g_texBase + off)



   The v mask is identical in both. Only the shifts differ, by exactly
   one, because the texel is half the size - and both address 256 x 256,
   which is the fifth independent confirmation of that dimension.

30.1.  Two details the comparison exposes

   o The 0xffffefff mask on u in the 16-bit path exists ONLY to force an
     even byte offset so the u16 read stays aligned. Section 12.3
     recorded the mask without being able to say why it was there and
     not on v. At one byte per texel there is nothing to align, so this
     path has no such mask, and its final mask is 0xffff where the other
     is 0x1fffe for the same reason.

   o The DESTINATION is still 16-bit - dst = maybe_g_spanRowPtr +
     maybe_g_spanFillLeft * 2. Only the SOURCE is paletted. The palette
     entries are already in surface format, which is why the filler can
     store one directly.

30.2.  The paletted family mirrors the direct one

   +---------+-------------------------+------------------------------+
   | Mode    | Direct, section 12      | Paletted, specialised chains |
   +=========+=========================+==============================+
   | opaque  | Screen3D_SpanCopyTexels | SpanTexK1Full / K1Half       |
   +---------+-------------------------+------------------------------+
   | keyed   | SpanTexKeyedAffine      | SpanTexKeyedK2Full / K2Half  |
   +---------+-------------------------+------------------------------+
   | stencil | SpanStencilFlatAffine   | SpanStencilFlatK42           |
   +---------+-------------------------+------------------------------+
   | shaded  | -                       | maybe_Screen3D_SpanShadedTex |
   +---------+-------------------------+------------------------------+

   The Full and Half suffixes are the two-level lighting of section
   27.2, not a texturing distinction: the Half variant applies texel >>
   1 & g_halveMask to the PALETTE OUTPUT, which is correct because the
   palette entry is already a surface colour.

   So the renderer carries two parallel filler families - one sampling
   16-bit texels directly, one sampling 8-bit texels through a palette -
   offering broadly the same modes. Section 29 found the second family;
   this is what it contains.

30.3.  A note on effort

   This filler is a plain scalar loop: no unrolling, no MMX, no
   alignment prologue, none of the machinery section 12.7 found in
   Screen3D_SpanCopyTexels. The paletted path was evidently not the one
   worth hand-optimising, which is a hint about which format the game
   actually uses for most geometry - though not evidence, and nothing
   here establishes it [guess].


31.  The shading filler, and a table nothing fills

   maybe_Screen3D_SpanShadedTex at 0x004adbf0 is the only filler with no
   direct-colour counterpart, and the only reader of maybe_g_spanShade.
   It is where the shade term is finally consumed [verified]:



       texel = palette[ page[idx] ];

       if (texel == 0)

           *dst = (*dst >> 1) & g_halveMask;      /* DARKEN */

       else

           *dst = g_shadeLut[ ((t & 0x3e7ff) >> 11)

                            + ((texel & 0xf80f) >> 4) ]

                | (texel & 0x7ff);

       u += g_texStepU;  v += g_texStepV;

       t  = (t & 0x3ffff) + maybe_g_shadeStep;



   The shade is stepped PER PIXEL by maybe_g_shadeStep and wrapped to 18
   bits. That completes the tier model of section 22 at its last level:
   gradient per triangle, edge value per scanline, start value per span,
   and here the per-pixel step.

31.1.  A transparent texel darkens rather than skips

   Palette entry 0 does not leave the pixel alone the way every keyed
   filler in section 12 does - it halves the destination. So kind 20 is
   a shadow or darkening pass, and its 'transparent' texels are the part
   that darkens [verified for the behaviour, inferred for the purpose].

31.2.  g_shadeLut

   +-----------------+-------------------------------------------------+
   | Property        | Value                                           |
   +=================+=================================================+
   | address         | 0x004f62f0                                      |
   +-----------------+-------------------------------------------------+
   | size            | 0x1000 bytes - bounded by the next named symbol |
   +-----------------+-------------------------------------------------+
   | static contents | all zero                                        |
   +-----------------+-------------------------------------------------+
   | readers         | maybe_Screen3D_SpanShadedTex, and only it       |
   +-----------------+-------------------------------------------------+
   | writers         | none found                                      |
   +-----------------+-------------------------------------------------+

   CORRECTED in section 36.2. The index arithmetic does fit the size
   exactly, but not by the sum given in an earlier version of this
   paragraph. Both masks are non-contiguous and both terms step by more
   than one [verified]:

       (t     & 0x3e7ff) >> 11    0 .. 124  in steps of 4
       (texel & 0xf80f) >> 4      0 .. 3968 in steps of 128

   The shade mask clears bits 11 and 12, so its term advances four bytes
   at a time; the texel mask keeps only bits 15 to 11 once the shift has
   discarded the rest, so its term advances 128. The largest byte offset
   is 3968 + 124 = 4092, and the read is a DWORD, so it touches bytes
   4092 to 4095 and the 0x1000-byte table is filled exactly to its last
   byte.

   So the table is 32 x 32 entries of FOUR bytes: 32 shade levels for
   each of 32 levels of the texel's top five bits, indexed as
   g_shadeLut[texelLevel][shadeLevel]. The entry is read as a dword and
   truncated to 16 bits, so either the upper half is unused or the
   entries are packed in pairs. Which, is not determined by the read
   alone.

   The result is OR-ed with texel & 0x7ff, so the low eleven bits of the
   palette colour pass through untouched and the table supplies the
   rest. The exact channel layout that implies has NOT been worked out
   and should not be guessed at from the masks alone.

31.3.  Nothing initialises it

   The table is zero in the image, and neither the reference database
   nor a raw scan of the whole of .text for the immediate 0x004f62f0
   finds anything that writes it. There is exactly one mention of the
   address in the binary, and it is the read [verified].

   o It may be filled by code that computes the address indirectly -
     from a register base, or through a pointer held elsewhere - which
     neither method would see. Several tables in this project are
     written by computed index and show no references.

   o Or it may genuinely never be filled, in which case the lookup
     contributes zero and kind 20 writes only the low eleven bits of
     each palette colour.

   Distinguishing the two matters, because the second would mean a
   visibly broken primitive kind in the shipped game. It is left OPEN
   rather than guessed: the evidence available says only that nothing in
   .text names the address except the reader.

31.4.  The answer was already in the database

   This function's plate comment, written in earlier work, already says
   in capitals that the third interpolant is light intensity and not
   depth, and gives g_shadeLut as the reason. Sections 17, 18 and 22
   rediscovered that independently over three sessions, including one
   rename in the wrong direction.

   The lesson is procedural and worth recording. Section 17 checked
   docs/ before naming, per the rule in CLAUDE.md, but did not search
   the GHIDRA COMMENTS. The database carries findings that never reached
   docs/, and a global's identity may already be written in the plate
   comment of a function that has not been read yet. Searching comments
   for an address is cheap and should come before reasoning about what a
   global means.

32.  The keyed paletted filler, and where transparency lives

   Screen3D_SpanTexKeyedK2Full at 0x004aa6c0 is the colour-keyed member
   of the paletted family, and the counterpart to the opaque
   Screen3D_SpanTexK1Full read in section 30. It is called directly by
   Screen3D_ClipSpanK2Full rather than through maybe_g_spanFiller
   [verified].

   Structurally it is the shortest function in the family and confirms
   section 30 rather than extending it. The addressing arithmetic is
   identical, byte for byte, to the 8-bit branch of SpanTexK1Full -
   which is worth stating, because that formula was derived from a
   single function and had not been seen twice [verified]:

       off = ((v & 0xffffe01f) >> 5) + (u >> 13)  &  0xffff;
       px  = palette[ ((u8 *)g_texBase)[off] ];
       if (px != 0) *dst = px;
       u += g_texStepU;  v += g_texStepV;

32.1.  The key is on the palette output, not the index

   The one real finding is in that third line, and it corrects the
   function's own plate comment, which said 'a palette entry of 0 is
   skipped, so texel index 0 is transparent'. The second half of that
   does not follow from the first.

   The test happens AFTER the palette lookup. What is compared against
   zero is the 16-bit colour that came out of the palette, not the 8-bit
   index that went in. So the transparent set is every index whose
   palette entry happens to be zero, which need not be index 0 alone and
   need not include index 0 at all [verified].

   Index 0 is almost certainly transparent in practice, because
   palette[0] is conventionally 0. But that is a property of the palette
   data, not of the code, and the two are worth keeping apart.

   The same shape holds everywhere the rasterizer keys.
   maybe_Screen3D_SpanShadedTex tests the palette output in section 31,
   and the 16-bit fillers of section 12 test the fetched texel itself,
   which is the same rule with no palette in the way. Stated once for
   the whole rasterizer: the colour key is 'the resulting colour is
   zero', never 'the index is zero' [verified].

   This matters for the port. Transparency in the paletted path cannot
   be reproduced by declaring index 0 the alpha key when the texture is
   converted, because that would make opaque any other index whose entry
   is zero, and would make transparent an index 0 whose entry is not.
   The conversion has to scan the palette and mark every zero entry.

   It also means transparency is a property of the PALETTE and not of
   the texture. Two textures sharing one palette share their transparent
   set; the same texture under two palettes does not.

32.2.  The paletted family, complete

   With this function read, every filler that goes through
   maybe_g_texPalette has been seen [verified]:

   +------------------------------+------------+---------------------------------------------+
   | Filler                       | Address    | On the fetched colour                       |
   +==============================+============+=============================================+
   | Screen3D_SpanTexK1Full       | 0x004a7240 | written unconditionally                     |
   +------------------------------+------------+---------------------------------------------+
   | Screen3D_SpanTexKeyedK2Full  | 0x004aa6c0 | written if non-zero                         |
   +------------------------------+------------+---------------------------------------------+
   | maybe_Screen3D_SpanShadedTex | 0x004adbf0 | shaded if non-zero, else destination halved |
   +------------------------------+------------+---------------------------------------------+

   Three treatments of the same fetch, and the difference between them
   is entirely in what happens to a zero: ignored, skipped, or turned
   into a darkening of what is already there. Only the third is a blend;
   the first two write or do not write.

32.3.  What the read did not find

   o No literals standing in for globals. Every step, base and palette
     pointer is the same global the rest of the family uses, so the
     specialisation warned about in section 29 is absent here.

   o No Half counterpart read yet. Section 27.2 has the Full/Half suffix
     as the two-level lighting quantisation, threshold 0x3dfff, and on
     that reading the Half form should differ only by halving the
     written colour. Not verified - the function has not been opened.

   o No second addressing mode - and NO filler has one. An earlier
     version of this bullet said Screen3D_SpanTexK1Full carried both the
     8-bit and the 16-bit formula. It does not. Section 30 sets the two
     side by side as a comparison of two FAMILIES, and reading that as
     one function with two branches was a misreading of the note,
     corrected in section 32.5 [verified].


32.4.  The Half counterpart, and the order of the two tests

   Screen3D_SpanTexKeyedK2Half at 0x004ab840 closes the open item left
   in section 32.3. It is the Full function with one operation changed,
   exactly as the Full/Half reading of section 10.4 predicted. The
   prediction is now confirmed on a second member of the family rather
   than assumed from the first [verified]:

       Full:  if (px != 0) *dst = px;
       Half:  if (px != 0) *dst = px >> 1 & g_halveMask;

   Everything else - the addressing, the stepping, the extent handling -
   is identical. The size difference is ten bytes, the same ten by which
   Screen3D_SpanTexK1Half exceeds Screen3D_SpanTexK1Full, which is the
   shift, the mask load and the AND.

   g_halveMask is derived from the runtime pixel format rather than
   hardcoded; that was established in section 12.8.1 and nothing here
   changes it. The darkening arithmetic in this function generalises to
   any RGB layout on its own.

32.4.1.  Halving cannot create transparency

   The one detail that is not simply a repeat is the ORDER of the key
   test and the halve. The test is on the palette output BEFORE it is
   darkened [verified].

   That matters at the bottom of the range. A palette entry of 1 passes
   the key test, is halved to 0, and is written - an opaque black pixel.
   Had the order been reversed it would have been skipped instead,
   leaving whatever was underneath.

   So the dim rendering of a primitive covers exactly the same pixels as
   the bright one. Darkening changes what is written, never whether it
   is written, and the transparent set is fixed by the palette for both
   variants alike. A port that darkens first and keys afterwards would
   punch holes in dim geometry that the original fills.


32.5.  The last Half, and a correction to 32.3

   Screen3D_SpanTexK1Half at 0x004a8340 completes the paletted family.
   It adds nothing: it is Screen3D_SpanTexK1Full with the store changed
   to palette[texel] >> 1 & g_halveMask, ten bytes larger, exactly as
   section 10.4 established by diffing the Tri layer and section 32.4
   confirmed for kind 2. The Half delta is now read directly in both
   families rather than inferred in either [verified].

   The value of the read was not in the function. Opening SpanTexK1Full
   alongside it to compare showed that the third bullet of section 32.3
   was wrong, and that bullet has been corrected in place.

   What it claimed: that SpanTexK1Full carries both the 8-bit and the
   16-bit addressing formula, and that this made it unusual among
   fillers. What is true: SpanTexK1Full contains only the 8-bit paletted
   formula. Section 30 quotes the 16-bit one beside it as a comparison
   against the DIRECT family of section 12, which is a different set of
   functions entirely, and section 30.2 says so in as many words. The
   error was in reading the note, not in the note [verified].

   The distinction matters because the wrong version implies a runtime
   branch on texel size inside a per-pixel loop, which is both a
   performance claim and a porting constraint, and there is no such
   branch anywhere in the rasterizer:

   +--------------------------+--------+--------------------------------+
   | Family                   | Texel  | Selected by                    |
   +==========================+========+================================+
   | direct, section 12       | 16-bit | which filler is in g_spanTable |
   +--------------------------+--------+--------------------------------+
   | paletted, sections 30-32 | 8-bit  | which filler is in g_spanTable |
   +--------------------------+--------+--------------------------------+

   So texel format is fixed per primitive KIND, resolved when
   Screen3D_ScatterTableByKey lays the table out at startup, and no
   filler ever tests it. The conclusion drawn in the faulty bullet -
   that format selection happens before the filler is chosen - was
   right; only its premise was wrong.

   Worth noting how it survived. The claim was tagged [inferred] and
   read as a plausible aside in a list of things a read did NOT find,
   which is the least scrutinised place in a note. Negative findings
   deserve the same check as positive ones - a single decompile would
   have settled it, and did.


33.  The stencil filler, and what the mask actually is

   Screen3D_SpanStencilFlatK42 at 0x004a9440 is the paletted stencil,
   and the last member of the paletted family. Section 12.2 already had
   its shape from the direct-colour side [verified]:

       if (palette[texel] != 0) *dst = (short)maybe_g_spanFlatColor;

   The texture selects WHETHER to write, never WHAT to write. Every
   covered pixel gets the same flat colour, computed once per primitive
   by the DrawPrim layer. That is how a cut-out shape - foliage, a sign,
   a shadow - is drawn in one colour with no per-pixel colour fetch.

33.1.  The mask is the palette entry, not the texel

   This is the third and sharpest instance of the rule in section 32.1.
   The value tested is the 16-bit colour that came OUT of the palette,
   not the 8-bit index that went in [verified].

   In the keyed fillers that rule decided transparency. Here it decides
   the SILHOUETTE. A stencil primitive's outline is whatever set of
   indices maps to a non-zero palette entry, so the same 8-bit texture
   bound under two palettes cuts out two different shapes. The shape is
   not a property of the texture.

   The direct-colour stencils at 0x004a50c0 and 0x004a5150 test the
   fetched 16-bit texel itself, which is the same rule with no palette
   in the way, so all four stencil and keyed families agree: the test is
   always on the resulting colour.

33.2.  Kind 42 has no Half variant

   Kinds 1 and 2 each have a Full and a Half filler, selected per
   primitive on the first vertex's intensity against 0x3dfff - section
   10.4. Kind 42 has neither. There is one Screen3D_ClipSpanK42 and one
   Screen3D_SpanStencilFlatK42, with no brightness pair anywhere in the
   chain [verified].

   The structural reason is clear enough. A Half filler exists because
   the colour comes from the texture and can only be darkened at the
   point of the store. Kind 42's colour does not come from the texture -
   it is a single value built once per primitive - so darkening it needs
   no second filler and no per-pixel work at all [inferred].

   ANSWERED in section 48.2. Screen3D_DrawPrimK42 does darken it, with
   the same 0x3e000 threshold and the same g_halveMask the Half fillers
   use - applied to the COLOUR at setup instead of to the texel at the
   store. So kind 42 does have two-level lighting; it simply does not
   need a second chain to get it [verified].

33.3.  The duplicated dword buys the stencils nothing

   Section 11.7.2 established that maybe_g_spanFlatColor holds the
   16-bit pixel duplicated into both halves of a dword, so the scalar
   flat filler can write two pixels at once and the MMX one can reach
   four lanes from a single MOVD.

   Neither stencil filler benefits. Both truncate to the low half and
   store one pixel at a time [verified] - the direct one as MOV word ptr
   [EAX],BX at 0x004a5128, the paletted one as MOV word ptr [ECX],AX at
   0x004a94ac. That is not an oversight: the store is conditional per
   pixel, so two adjacent pixels cannot share one write when either may
   be masked out.

   So the duplication serves the UNCONDITIONAL flat fillers only. Every
   filler with a per-pixel test - keyed, stencil, shaded - is scalar by
   necessity, and the width tricks of section 12.7 apply to none of
   them.

33.3.1.  One codegen difference, and only one

   Comparing the two stencils instruction by instruction shows a single
   difference in how they treat their globals [verified]:

   +-----------------------+--------------------------------+----------------------------+
   | Global                | direct 0x004a50c0              | paletted 0x004a9440        |
   +=======================+================================+============================+
   | maybe_g_spanFlatColor | hoisted to EBX before the loop | reloaded per written pixel |
   +-----------------------+--------------------------------+----------------------------+
   | g_texBase             | reloaded per pixel             | reloaded per pixel         |
   +-----------------------+--------------------------------+----------------------------+
   | g_texStepU / V        | reloaded per pixel             | reloaded per pixel         |
   +-----------------------+--------------------------------+----------------------------+

   The paletted one reloads the flat colour inside the branch, so it
   costs a memory read only on pixels that survive the mask, not on
   every pixel. It is a small difference and it is the only one - both
   loops reload the texture base and both step constants every
   iteration.

   Worth stating because section 30.3 observed that the paletted path
   got less optimisation attention than the direct one. That observation
   stands on the absence of MMX and unrolling, which is real. It should
   NOT be supported by this comparison: on the evidence of these two
   functions the register allocation is almost identical, and one missed
   hoist is not a pattern.


34.  The stencil clipper, and why only some kinds claim coverage

   Screen3D_ClipSpanK42 at 0x004a94d0 is the per-kind clipper for the
   stencil, and structurally it holds no surprises. It is the documented
   Defer shape, and reading it is worth recording mainly because it
   confirms three separate earlier findings from a function none of them
   was derived from [verified]:

   o The two-mode split of section 25.3. When g_spanBufferEnabled is 0
     it clamps to [0, g_viewMaxX + 1] and calls
     Screen3D_SpanStencilFlatK42 immediately; only with the buffer on
     does it queue records. So it is a Defer clipper only while the span
     buffer is enabled, exactly as section 25.3 said of the Walk family.

   o The span record layout of section 16.4. It writes +0x04 row
     pointer, +0x08 and +0x0a as the two u16 x bounds, +0x0c u and +0x10
     v, at a stride of 0x1c.

   o The three-tier interpolant model of section 25.4. The record gets
     maybe_g_edgeU + g_texStepU * (spanStart - edgeStart), the per-span
     value derived from the per-scanline edge value by the per-triangle
     step.

   One detail of the immediate path is worth stating because it is easy
   to get wrong in a port: only the LEFT clamp adjusts the interpolants.
   Clamping x to 0 advances u and v by the discarded pixels, while
   clamping the right edge to g_viewMaxX + 1 merely shortens the count.
   That is correct - stepping begins at the left - but the asymmetry is
   not obvious from the shape of the code.

34.1.  What it does not write, and the field nobody writes

   Two of the record's seven fields are left untouched, and both
   absences are explained by section 16.4 rather than being new gaps
   [verified]:

   +----------------------+-----------------+-----------------------------------------------+
   | Field                | Written by K42? | Why                                           |
   +======================+=================+===============================================+
   | +0x14, perspective w | no              | kind 42 is affine; there is no w              |
   +----------------------+-----------------+-----------------------------------------------+
   | +0x18, shade         | no              | restored per span only for kinds 4, 9, 19, 20 |
   +----------------------+-----------------+-----------------------------------------------+

   So a fresh function independently reproduces the rule section 16.4
   inferred about which kinds carry a per-span shade, which is a better
   check on it than the flusher alone could give.

   The record's FIRST dword is a different matter. K42 does not write
   +0x00, and neither does any clipper read so far - section 16.4's
   table begins at +0x04 because nothing had been seen touching the
   field. Four bytes at the head of a 0x1c-byte record that no producer
   writes is worth an answer. It may be written by the batch layer
   rather than the span layer, or be padding that alignment demands, or
   be read by Screen3D_FlushSpans without ever being written. OPEN.

34.2.  What decides whether a kind claims coverage

   CORRECTED. An earlier version of this section claimed that a kind
   consumes coverage if and only if its filler writes every pixel of the
   span, and called that a correctness requirement of the algorithm.
   Half of it is right. The biconditional is not, and section 35 records
   the read that broke it.

   Section 26.3 recorded that five of the eight ClipSpanKn never write
   g_spanFreeCount and so never split a free-list node, and guessed the
   five were simply the deferred chains. Section 27.1 found the
   Now/Defer division matches the split/no-split division exactly. That
   much holds [verified]:

   +-------------+------------------------------------------+---------+-------------------+
   | Kind        | Filler behaviour                         | Clipper | Consumes coverage |
   +=============+==========================================+=========+===================+
   | 1 Full/Half | opaque textured, every texel written     | Now     | yes               |
   +-------------+------------------------------------------+---------+-------------------+
   | 3           | a bare RET, draws nothing                | Now     | yes               |
   +-------------+------------------------------------------+---------+-------------------+
   | 2 Full/Half | colour-keyed, zero entries skipped       | Defer   | no                |
   +-------------+------------------------------------------+---------+-------------------+
   | 42          | stencil, masked by the palette entry     | Defer   | no                |
   +-------------+------------------------------------------+---------+-------------------+
   | 9           | writes every pixel but READS dst on zero | Defer   | no                |
   +-------------+------------------------------------------+---------+-------------------+
   | 4           | a bare RET, draws nothing                | Defer   | no                |
   +-------------+------------------------------------------+---------+-------------------+

   So coverage consumption is decided by the CLIPPER STYLE, and by
   nothing else. It is a per-kind design decision recorded in the
   dispatch structure, not a property that can be computed from what the
   filler does.

34.2.1.  One direction is a correctness requirement

   Splitting a free-list node asserts that those pixels are now opaque
   and finished, and that anything behind them may be discarded. Two
   different things stop a kind making that claim, and section 36 found
   the second one after this section first stated only the first
   [inferred, but forced by the algorithm]:

   o It does not WRITE every pixel. The geometry behind the gaps is
     still visible, so the pixels are not finished. Kinds 2 and 42 are
     this case - a colour key and a stencil mask.

   o It READS the destination. A blend needs what is behind it to have
     been drawn already, which is the opposite of the front-to-back
     order coverage consumption requires. Kind 9 is this case, and it
     writes every pixel of its span.

   Either way the kind MUST be a Defer kind. Phrased to cover both: a
   Now kind has to write every pixel of its span without reading any of
   them.

   That explains kinds 2, 9 and 42 completely, and it explains why
   deferral and transparency travel together: front-to-back drawing with
   coverage consumption only works for primitives that occlude, so
   everything with holes has to be held back and replayed after the
   opaque pass. That is what the span buffer and Screen3D_FlushSpans
   exist to do.

34.2.2.  The converse does not hold, and kinds 3 and 4 prove it

   Kinds 3 and 4 are IDENTICAL at the filler level. Both fillers are
   empty - kind 3's at 0x004a6070 and kind 4's at 0x004ac9c0 are bare
   RETs - so both draw exactly nothing. Their coverage behaviour is
   opposite [verified].

   Kind 3 has a Now clipper, consumes coverage, and is therefore an
   OCCLUDER: invisible geometry whose only job is to hide what is behind
   it. Kind 4 has a Defer clipper, walks the free list read-only, and is
   therefore INERT: it draws nothing and hides nothing, which is the
   vestigial-feature reading section 25 already reached from the other
   direction.

   Two kinds, the same empty filler, opposite meaning. Nothing about a
   filler predicts whether its kind claims coverage, and the earlier
   phrasing of this section was wrong to suggest it could. What the
   filler settles is only the forced case: if it has holes, the kind
   cannot be a Now kind.

34.3.  What the port takes from it

   The span buffer is not a general hidden-surface structure that the
   renderer happens to use twice. It is an OPACITY-ONLY structure, and
   the deferred queue is the transparency pass that every renderer since
   has had in some form.

   That maps cleanly onto modern hardware and is worth deciding early:
   the coverage-consuming kinds become ordinary depth-buffered draws,
   and the deferred kinds become a second pass with depth writes off,
   drawn after them. The span buffer itself does not need to survive the
   port - only the two-pass ordering it enforces does.

   Which pass a kind belongs to must be READ from the dispatch
   structure, not inferred from what its filler does - see section
   34.2.2. And two kinds need no pass at all: kind 3 is a pure occluder,
   which on modern hardware is a depth-only draw with colour writes
   masked off, and kind 4 is inert and can be dropped entirely.



35.  The inert kind, and the dispatcher switch read out in full

   Screen3D_ClipSpanK4 at 0x004ac9d0 was named in section 34.2 as the
   one function that could falsify the rule stated there. It did.

   The function itself is the documented Defer shape and adds two
   confirmations. It writes span-record field +0x18 from
   maybe_g_edgeShade, which is the first time the per-span shade of
   section 16.4 has been seen from the PRODUCING side rather than
   inferred from what Screen3D_FlushSpans restores. And it carries the
   shade through the left clamp alongside u and v - shade -= shadeStep *
   x for a negative x - so the third interpolant is clipped exactly like
   the first two [verified].

   It does not write g_spanFreeCount, so it claims no coverage, and its
   immediate path calls Screen3D_SpanNopK4, a bare RET. Kind 4 draws
   nothing on either path: the g_spanTable entry that
   Screen3D_FlushSpans resolves for the deferred replay, FUN_004a5a80,
   is also empty [verified]. Kind 4 is inert, which is what section 25
   concluded from the other end.

35.1.  Which kinds have specialised chains, from the jump table

   Chasing this required reading the dispatcher switch properly rather
   than collecting function names, and the result is worth recording on
   its own. Screen3D_DispatchPrimitive selects on the primitive kind at
   prim+0x3a through a two-level MSVC switch [verified]:

       kind = *(u16 *)(prim + 0x3a);
       if (kind > 0x2a) goto default;
       slot = ((u8 *)0x004af100)[kind];      /* case index   */
       goto ((void **)0x004af0e0)[slot];     /* jump table   */

   Dumping both tables gives the complete list of specialised kinds, and
   it is short. Six kinds have hand-written chains; every other value
   from 0 to 42, and everything above 42, falls to the default and is
   drawn through g_spanTable [verified]:

   +------------+------+-------------------------------------+
   | Kind       | Slot | Chain                               |
   +============+======+=====================================+
   | 0          | 0    | calls 0x004a3cf0 directly, no chain |
   +------------+------+-------------------------------------+
   | 1          | 1    | DrawPrimK1Full / K1Half             |
   +------------+------+-------------------------------------+
   | 2          | 2    | DrawPrimK2Full / K2Half             |
   +------------+------+-------------------------------------+
   | 3          | 3    | DrawPrimK3                          |
   +------------+------+-------------------------------------+
   | 4          | 4    | DrawPrimK4                          |
   +------------+------+-------------------------------------+
   | 9          | 5    | DrawPrimK9                          |
   +------------+------+-------------------------------------+
   | 42         | 6    | DrawPrimK42                         |
   +------------+------+-------------------------------------+
   | all others | 7    | default: the g_spanTable path       |
   +------------+------+-------------------------------------+

   This settles a naming question that had never been checked. The K<n>
   suffixes on the specialised chains ARE the primitive kinds, exactly
   as section 10.4 assumed - kind 4 reaches DrawPrimK4, kind 42 reaches
   DrawPrimK42, and so on for all six [verified]. The assumption was
   correct; it had simply never been tested against the dispatch table.

   It is worth stating because g_spanTable makes it look wrong. Table
   key 19 holds Screen3D_SpanNopK4 and table key 20 holds
   maybe_Screen3D_SpanShadedTex, which invites the reading that the
   chains named K4 and K9 are really kinds 19 and 20. They are not - the
   dispatcher jump table is unambiguous.

   PARTLY CORRECTED in section 41.1. This paragraph went on to call
   those table kinds UNRELATED, and explained the shared filler as
   coincidence. That was wrong. Keys 19, 20, 40, 41 and 42 are the
   DEFERRED IDENTITIES of the specialised chains: a chain queues its
   batches under a second kind number, and the flusher resolves the
   filler from that. The two numbering systems are connected, and the
   connection is the batch record.

   o Do not infer a chain's kind from the g_spanTable key of the filler
     it calls. The jump table at 0x004af100 is the only authority on
     which kind reaches which chain.

35.2.  The brightness split, as the compiler emitted it

   The switch also shows the two-level lighting test of section 10.4 in
   its compiled form. Kinds 1 and 2 are the only slots with a branch
   before the call [verified]:

       MOV ECX, [EAX + 0xc]        ; first vertex's shade
       CMP ECX, 0x3e000            ; 31.0 in 19.13
       JL  half

   Section 10.4 recorded the threshold as > 0x3dfff, which is the same
   test written the other way round. Nothing changes; the point is that
   the selection happens in the DISPATCHER, one level above the chain,
   and reads the shade straight out of the vertex array at prim+0x0c
   before any setup has run.


36.  The shaded clipper, and a blend is not a hole

   Screen3D_ClipSpanK9 at 0x004adce0 is the same function as
   Screen3D_ClipSpanK4. Not similar - the same. Both are 167
   instructions, and diffing them instruction by instruction shows only
   branch targets, a handful of EAX/EBX swaps the register allocator
   made differently, and the immediate call target [verified]. The four-
   byte size difference is entirely encoding: MOV EBX,[mem] is one byte
   longer than MOV EAX,[mem], and the IMUL operands are arranged
   differently.

   So there is no per-chain specialisation here at all, which is worth
   recording as a negative result. Section 29 warned that specialisation
   hides in exactly the few instructions a structural comparison
   discards; this is a case where looking there found nothing, and the
   two chains really are one template with the filler call substituted.

   It confirms the same two things ClipSpanK4 did - the per-span shade
   written to record +0x18 from the producing side, and the shade
   clipped through the left clamp with u and v - from a second,
   independent chain.

36.1.  Kind 9 has no holes; it blends

   The read forced a correction to the table in section 34.2, which
   listed kind 9 as a holed kind alongside the keyed and stencil kinds.
   It is not one. Re-reading maybe_Screen3D_SpanShadedTex settles it
   [verified]:

       if (texel == 0) px = (*dst >> 1) & g_halveMask;
       else            px = g_shadeLut[...] | (texel & 0x7ff);
       *dst = px;                    /* UNCONDITIONAL */

   The store is outside the branch. Every pixel of the span is written.
   What the transparent branch does is READ the destination and halve
   it, which is a blend, not a skip - the shadow-pass reading section 31
   gave it.

   The error came from compressing that behaviour to the phrase 'zero
   entries darken instead' in a summary table and then reasoning from
   the phrase rather than the code. Darkening still writes the pixel.
   Section 31 said so plainly in the sentence the table was summarising.

   The correction is not cosmetic, because it changes WHY kind 9 must be
   deferred. Not because the geometry behind it shows through gaps, but
   because it needs that geometry already drawn to blend against.
   Section 34.2.1 has been widened to cover both reasons.

36.2.  The shade lookup, indexed correctly

   Re-reading the filler also corrected the index arithmetic recorded in
   section 31.2, which had the table nearly full where it is exactly
   full. Both masks in the expression are non-contiguous, which is what
   the earlier reading missed [verified]:

   +-------+---------------------------------------+-----------+------+
   | Term  | Mask                                  | Range     | Step |
   +=======+=======================================+===========+======+
   | shade | 0x3e7ff, bits 12 and 11 clear         | 0 .. 124  | 4    |
   +-------+---------------------------------------+-----------+------+
   | texel | 0xf80f, only bits 15..11 survive >> 4 | 0 .. 3968 | 128  |
   +-------+---------------------------------------+-----------+------+

   Maximum byte offset 4092, read as a dword, so the last byte touched
   is 4095 and the 0x1000-byte table is filled exactly. The shape is 32
   x 32 entries of four bytes - g_shadeLut[texelLevel][shadeLevel] -
   which is a cleaner reading than the earlier one and a better argument
   that the bounds are understood.

   It does not change section 31.3. The table is still all zero in the
   image with no writer findable by references or by a raw scan for its
   address, and that remains OPEN.

36.3.  One more detail of the shade accumulator

   The per-pixel step is maybe_g_spanShade = (maybe_g_spanShade &
   0x3ffff) + maybe_g_shadeStep. The accumulator is MASKED to eighteen
   bits every pixel, so it wraps rather than saturating [verified].

   A port must reproduce the wrap. Clamping instead would look more
   correct and would be wrong: an over-bright span in the original rolls
   back to dark rather than flattening to white, and any content that
   relies on the shade staying in range will look identical either way,
   while content that does not will differ visibly.


37.  The occluder clipper, and eight copies of one algorithm

   Screen3D_ClipSpanK3 at 0x004a6080 is the only Now clipper among the
   specialised chains that carries a shade term, and the largest of the
   eight at 588 bytes. Reading it completes the family.

   It confirms section 26.1 from the specialised side. That section read
   all four free-list operations out of maybe_Screen3D_Walk4Now, a
   table-path clipper, and concluded that an empty filler plus a Now
   clipper is an occluder. Kind 3 is that combination in the switch
   path: every shrink, unlink and split runs, and the routine called
   between them is Screen3D_SpanNopK3, a bare RET [verified].

   One detail is only visible here. The clipper writes g_spanU, g_spanV
   and maybe_g_spanShade before EVERY call to the nop, and the nop reads
   none of them. They are dead stores. That is not a quirk of kind 3 -
   it is what a shared template looks like when the filler slot happens
   to be empty, and the next section shows the template is shared
   exactly.

37.1.  Eight clippers, four templates, one algorithm

   Cross-referencing which clippers touch maybe_g_spanShade and which
   touch g_spanFreeCount sorts all eight into a clean two by two
   [verified]:

   +------------------------+---------------------------------+----------------+
   |                        | no shade term                   | carries shade  |
   +========================+=================================+================+
   | Now, consumes coverage | K1Full 515, K1Half 513          | K3 588         |
   +------------------------+---------------------------------+----------------+
   | Defer, records only    | K2Full 488, K2Half 485, K42 488 | K4 550, K9 554 |
   +------------------------+---------------------------------+----------------+

   The sizes cluster by template rather than by kind, which is the first
   sign that the members are copies. Diffing them instruction by
   instruction confirms it. Within a template the members differ ONLY by
   the call target and by compiler noise [verified]:

   o Screen3D_ClipSpanK2Full and Screen3D_ClipSpanK42 are 154
     instructions each. Eight differ, and all eight are the same
     pattern: a CMP with its operands swapped and the branch condition
     mirrored to compensate, CMP EAX,EBX / JG against CMP EBX,EAX / JL.
     Semantically identical.

   o Screen3D_ClipSpanK4 and Screen3D_ClipSpanK9 are 167 instructions
     each, differing in register allocation and the call target, as
     section 36 recorded.

   o Screen3D_ClipSpanK1Full and K1Half are 150 and 149, with the same
     mirrored comparisons plus one instruction the scheduler folded near
     the end.

   So there is no hand specialisation anywhere in the eight. Section
   26.2 called the free-list allocator one macro instantiated nine times
   across the table-path clippers; the switch-path eight are the same
   thing, and the two axes that generate them are exactly the two that
   matter: whether the kind consumes coverage, and whether it
   interpolates a shade.

   That is worth having for the reconstruction. These eight functions
   should be written as ONE parameterised routine, not eight
   transcriptions - and unusually for this project that is not a
   refactor toward nice, because the evidence says the original source
   had one routine too.

37.2.  The free list is sorted, and the code proves it

   Every clipper contains the same early return: if the span ends before
   the current node begins, stop walking [verified].

       if (spanEnd < node->x0) return;

   Abandoning the walk at the first node that starts too far right is
   only correct if no LATER node can start further left. So the per-
   scanline free list is kept sorted ascending by x0, and the ranges are
   non-overlapping [inferred, but the early return is wrong otherwise].

   Nothing sorts it explicitly. It stays sorted because the only
   operations are shrinking an endpoint, unlinking a node, and splitting
   one in place - none of which can reorder the list. Section 10.1 has
   Screen3D_BeginFrame seeding each scanline with a single node, which
   is trivially sorted, and the invariant holds from there.

   A port that replaces the list with anything else must preserve that
   ordering, or the early return becomes a silent correctness bug rather
   than an optimisation.


37.3.  The template, verified by construction

   Screen3D_ClipSpanK1Full at 0x004a72d0 adds nothing new. It is the
   plain Now template - the free-list walk of section 26.1 with
   Screen3D_SpanTexK1Full in the filler slot and no shade term - and it
   is recorded here because reading it turns the matrix of section 37.1
   from an inference about size clustering into something checked
   instruction by instruction.

   Diffing it against Screen3D_ClipSpanK3 by longest common subsequence
   gives 125 instructions in common out of 150 and 164. Every one of the
   39 that K3 has and K1Full does not is part of the shade term
   [verified]:

   +-------------------+------------+--------------------------------+
   | Global            | Address    | Role in the extra instructions |
   +===================+============+================================+
   | maybe_g_edgeShade | 0x0068b00c | the per-scanline source value  |
   +-------------------+------------+--------------------------------+
   | maybe_g_shadeStep | 0x00655d30 | multiplied by the x offset     |
   +-------------------+------------+--------------------------------+
   | maybe_g_spanShade | 0x006d1f80 | the per-span result, stored    |
   +-------------------+------------+--------------------------------+

   maybe_g_spanShade is written at three sites, which is exactly the
   number of places either function sets up a span before calling its
   filler. The remainder of the difference is the mirrored comparisons
   and register shuffling that the extra pressure of a third interpolant
   forced on the allocator.

   So K3 is K1Full plus a shade, in the literal sense that deleting the
   shade instructions from one yields the other. The two axes of section
   37.1 are real and the eight clippers are four templates, not eight
   functions [verified].

   Nothing else came out of the read, which is worth saying plainly
   rather than padding. The remaining unread clippers - K1Half, K2Half -
   are the second members of templates whose first members have been
   diffed, so unless a diff shows otherwise there is no reason to expect
   content in them.


38.  BeginFrame: the seed, the stride, and a lock that is not held

   Screen3D_BeginFrame at 0x0049a160 is 400 bytes with forty-seven
   callers - every menu page tick, every error dialog, and
   maybe_Game_RenderFrame. It locks the frame buffer and resets the per-
   frame span state, and it answers two questions left open elsewhere
   while raising one that matters for the port.

38.0.  The two arguments, and what resume means

   Both parameters are now named [verified]:

       Screen3D_BeginFrame(int resume, int skipLock)

   skipLock non-zero skips Cdd_LockMain and leaves g_frameLockValid
   clear; the reset still runs. resume non-zero skips THE WHOLE RESET -
   the span seeding of section 38.1 AND four pool cursors - so
   everything the frame had accumulated survives.

   That explains a call pattern recorded in two other notes without an
   explanation. subsystems/dd-errors.txt and display-mode-gate.txt both
   show a message box raised mid-frame being bracketed by

       Screen3D_EndFrame(1, 0)  ...dialog...  Screen3D_BeginFrame(1, 0)

   Passing 1 means "carry on the frame I already had". The queued
   geometry, the vertex pool and the span free list are preserved
   rather than thrown away, so the interrupted frame can finish after
   the dialog closes. It is a RESUME flag, not an error code.

38.0.1.  Four pool cursors reset here, not just the span list

   Section 38.1 records the span free list. The same guarded block
   resets three more cursors that this note did not previously mention
   [verified]:

   +--------------+--------------------------------------------------+
   | Global       | What it counts                                   |
   +==============+==================================================+
   | 0x0068b014   | g_vertexPoolCount - the MR_Vertex bump allocator |
   |              | at 0x006d20d8. See structs/MR_Vertex.txt sect 7  |
   +--------------+--------------------------------------------------+
   | 0x00655d14   | queue nodes used, capped at 0x1d4b by            |
   |              | Screen3D_QueuePrimitive                          |
   +--------------+--------------------------------------------------+
   | 0x0065e1c8   | the split-primitive pool index, the MR_Primitive |
   |              | array at 0x0062ebf0                              |
   +--------------+--------------------------------------------------+
   | 0x00624f60   | not identified                                   |
   +--------------+--------------------------------------------------+

   o So every per-frame allocator in the renderer is a bump pointer
     reset here, and none of them is bounds-checked at the allocation
     site. Only the queue count is checked, and by its consumer rather
     than by this function. A port that keeps the bump allocators
     should add the bounds the original does without.

   o Before zeroing the vertex count, the block adds it into an
     accumulator at 0x0053469c. That is a running TOTAL across frames,
     not a high-water mark - nothing compares it against anything.

38.0.2.  What the abort actually is

   The one fatal site in this function is Cdd_LockMain returning NULL.
   It prints "BeginDisplay failed" with screen3d.cpp line 0x516 = 1302,
   then App_Shutdown and _exit(1) [verified].

   subsystems/game-object.txt section 6.1 left this open. It had first
   read the abort as surface loss, corrected that when Cdd_Present was
   found to recover DDERR_SURFACELOST properly, and then recorded that
   what BeginFrame aborts on "has not been identified". It is a failed
   main-surface LOCK - a different failure from surface loss, and one
   the engine has no recovery for.

38.1.  The seeding loop

   The free-list seed of section 10.1 is now read directly rather than
   inherited [verified]:

       g_spanFreeCount = 0;
       g_spanAccepting = 1;
       for (y = 0; y < g_viewHeight; y++) {
           g_spanScanlineHead[y] = &g_spanFreePool[y];
           pool[y].x0   = 0;
           pool[y].x1   = g_viewMaxX + 1;
           pool[y].next = NULL;
           g_spanFreeCount++;
       }
       g_spanBufferCount = 0;
       maybe_g_batchCount = 0;

   So the allocator is index-parallel with the scanline: node y belongs
   to scanline y, and g_spanFreeCount leaves this function equal to
   g_viewHeight. Every node beyond that is a split produced during the
   frame.

   That bounds the pool question docs/structs/MR_ClipSpan.txt leaves
   open. At the tallest supported mode the seed costs 480 nodes, so the
   headroom for splits is whatever the pool holds minus 480 - about
   11,041 if the 0x16808-byte gap to the next referenced global is the
   true extent. The bound is still not read from the code, but the
   demand side of it now is.

   Note the loop is over g_viewHeight, the VIEW height, not the screen
   height. With the letterboxing of section 11.1 those differ, and the
   head array is only initialised for the rows inside the view.

38.2.  Another hardcoded 16-bit assumption

   The frame buffer pointer is biased before use [verified]:

       g_frameBuffer = Cdd_LockMain(&g_frameStridePx);
       g_frameBuffer += (g_frameStridePx * g_viewTopMargin
                         + DAT_00624374) * 2;

   The trailing * 2 is bytes per pixel, written as a literal. It belongs
   on the catalogue of 16-bit assumptions the port has to find, and it
   is a good example of why that catalogue cannot be built by searching
   for 5/6/5 shifts alone: nothing here mentions a channel layout, yet
   the line is exactly as depth-dependent as a packing mask.

   g_frameStridePx is filled by the lock and is a stride in PIXELS,
   since it is multiplied by the margin before the byte conversion.

38.3.  The lock is released immediately, by default

   This is the finding worth the read. After taking the pointer,
   BeginFrame may hand the lock straight back [verified]:

       if (DAT_004dc170 != 0) Cdd_UnlockMain();

   Following the flag settles what it is. It initialises to 1, and the
   single site that writes it is Main_InitAndParseCommandLine at
   0x004144d9, which sets it to 0 immediately after matching the string
   -DoRealLock at 0x004144c4 [verified]. The binary's own flag
   documentation describes that switch as 'Really use DirectDraw
   lock/unlock'.

   So the DEFAULT is to lock the surface, keep the pointer, unlock at
   once, and then have the software rasterizer write through that
   pointer for the whole frame with no lock held. -DoRealLock turns that
   off and holds the lock properly. The flag is read by exactly three
   functions - Screen3D_BeginFrame, Screen3D_EndFrame and
   maybe_Screen3D_FadeRect - which is the whole lock lifecycle.

   The global has been renamed g_ddReleaseLockEarly to record that, with
   1 meaning release.

   Two consequences for the port, and they pull in opposite directions.
   It is undefined behaviour under the DirectDraw contract, which is
   presumably why the escape hatch exists at all - it works because a
   1997 driver hands back a stable linear framebuffer address and
   nothing moves it. A modern reimplementation must NOT copy the
   pattern: it needs a mapping held for the frame, or a system-memory
   buffer uploaded at the end.

   But the pattern also tells us what the renderer ASSUMES, and that
   part is worth preserving: one base pointer and one stride, both
   constant for the frame, with no re-acquisition anywhere below. Every
   layer under BeginFrame - the emitters, the clippers, all sixteen
   fillers - depends on maybe_g_spanRowPtr being derived from a pointer
   that does not move. A port that re-maps per draw call would break
   assumptions far below the surface code.

38.4.  The original name of this function

   The failure path names it. When Cdd_LockMain returns 0 the assert
   reads 'BeginDisplay failed' at D:\Dsed\mr320\screen3d\screen3d.cpp
   line 1302 [verified].

   Which function BeginDisplay names is not settled. The idiom '<callee>
   failed' would point at Cdd_LockMain, but the Cdd methods elsewhere in
   the binary carry their class prefix - 'Fatal error in
   Cdd::SetCooperativeLevelAndDisplayMode', and the assert in
   Cdd_GetCaps says Cdd::getCaps() - and this message does not. That,
   plus the site being in screen3d.cpp rather than dd.cpp, reads as this
   function reporting its own failure [inferred].

   Not renamed on that. Screen3D_BeginFrame is an accurate name, the
   evidence is suggestive rather than conclusive, and replacing a good
   name with a maybe-correct one costs more than it gains. Recorded here
   so the next reader has the candidate and the doubt together. Section
   1 of docs/source-map.txt has the full set of line anchors this
   belongs to.


39.  EndFrame, and why the free list is a list

   Screen3D_EndFrame at 0x0049b0e0 is 210 bytes and calls exactly one
   function, Cdd_UnlockMain. It does not flush spans and it does not
   present. What it does instead answers a question section 10.5 raised
   and could only half answer.

39.1.  The background fill IS the free list

   At the end of the frame it walks every scanline's remaining free
   ranges - the x ranges no polygon ever covered - and paints them
   [verified]:

       for (y = 0; y < g_viewHeight; y++) {
           for (n = g_spanScanlineHead[y]; n; n = n->next) {
               dst = g_frameBuffer
                   + (g_scanlineOffset[y] + n->x0) * 2;
               for (i = n->x1 - n->x0; i--; )
                   *dst++ = g_backgroundColor;
           }
           g_spanScanlineHead[y] = NULL;
       }

   This is not new. Section 10.5 already had the deferred fill and
   already drew the conclusion that the span buffer pays for itself
   twice, on the way in and on the way out. It is restated here only
   because the next subsection needs it, and because the colour global
   now has a name.

39.2.  Screen3D_Clear has two implementations

   The function at 0x0049a560, now named Screen3D_Clear, is where the
   two halves meet, and it is nine lines that explain the whole design
   [verified]:

       if (g_spanBufferEnabled) {
           g_backgroundFillPending = 1;
           g_backgroundColor       = colour;   /* deferred */
       } else {
           Cdd_Clear(0, colour, 0);            /* immediate */
       }

   One entry point, two strategies. With the span buffer off it is an
   ordinary full-surface DirectDraw clear before drawing. With it on,
   nothing is painted at all until EndFrame fills the remainder.

   So the span buffer is not merely hidden-surface removal. It also
   eliminates the screen clear, and the two savings come from the same
   structure: the free list is what is left after subtracting every
   polygon, which is simultaneously the set of pixels that may still be
   drawn and the set that needs background. That is why the renderer
   keeps an interval LIST rather than a coverage bitmap - a bitmap would
   answer the first question but would have to be scanned to answer the
   second.

   Both globals initialise to zero, so with no call to Screen3D_Clear
   the uncovered pixels simply keep whatever the previous frame left.
   The engine has no notion of a mandatory clear.

39.3.  The lock policy, confirmed from the far end

   Section 38.3 read g_ddReleaseLockEarly from BeginFrame alone.
   EndFrame is the mirror image and settles it [verified]:

   +------------+------------------------------------+-------------------+
   |            | g_ddReleaseLockEarly = 1 (default) | = 0 (-DoRealLock) |
   +============+====================================+===================+
   | BeginFrame | unlocks immediately                | keeps the lock    |
   +------------+------------------------------------+-------------------+
   | EndFrame   | does nothing                       | unlocks           |
   +------------+------------------------------------+-------------------+

   Exactly one Cdd_UnlockMain per frame on either policy. The difference
   is only whether the lock is held across the drawing, which is what
   the flag name says and what the -DoRealLock switch is for.

   EndFrame then clears g_frameBuffer and g_frameLockValid. So the
   surface pointer is valid WITHIN a frame and re-acquired by every
   BeginFrame - a refinement of section 38.3, which said the pointer
   does not move without saying over what interval. It does not move
   during a frame; it is not assumed stable between frames.

39.4.  Names earned here

   +------------+-------------------------+-------------------------------------------------------+
   | Address    | Name                    | Evidence                                              |
   +============+=========================+=======================================================+
   | 0x0049a560 | Screen3D_Clear          | the two-branch clear above                            |
   +------------+-------------------------+-------------------------------------------------------+
   | 0x004f1a20 | g_frameLockValid        | set by BeginFrame, cleared here, read by 25 functions |
   +------------+-------------------------+-------------------------------------------------------+
   | 0x00625748 | g_backgroundFillPending | gates the fill; set by Clear                          |
   +------------+-------------------------+-------------------------------------------------------+
   | 0x0065f0d8 | g_backgroundColor       | the colour the fill writes                            |
   +------------+-------------------------+-------------------------------------------------------+

   g_frameLockValid is worth noting for its reach. Twenty-five functions
   read it - every menu tick, the error dialogs, the font drawer - as
   the test for whether a frame buffer is currently available to draw
   into. It is the closest thing the renderer has to a global 'is
   drawing legal right now' flag.

39.5.  What the port takes from it

   o The deferred background fill can go. On modern hardware a full
     clear is essentially free, so the correct port of Screen3D_Clear is
     the immediate branch - the one the engine already takes when the
     span buffer is off. Nothing else depends on the deferred path.

   o But note what that removes. Section 34.3 said the span buffer
     itself need not survive, only the two-pass ordering. This is the
     second of its two jobs, and it also does not need to survive. What
     remains is genuinely just the ordering.

   o g_scanlineOffset at 0x0062e468 and maybe_g_spanRowPtr are the same
     thing at two stages, not two tables. CLOSED, and it should not have
     been opened - section 11 already had g_scanlineOffset as the table
     consumers address rows through, and section 11.6 already had the
     walker using it. Confirmed anyway: 14 of the 15 writers of
     maybe_g_spanRowPtr read g_scanlineOffset in the same function. The
     exception is Screen3D_FlushSpans, which restores the row pointer
     from span record +0x04 instead [verified].

   One decompiler artifact worth flagging, since a future reader will
   meet it. The output renders 'g_viewHeight = iVar3' inside the
   scanline loop, which reads as a global being written for no reason.
   It is not: 0x0049b15c is a LOAD of the loop bound, and the assignment
   is register reuse the decompiler could not place. Nothing writes
   g_viewHeight in this function.


40.  FadeRect, and what a caller reveals about BeginFrame

   maybe_Screen3D_FadeRect at 0x0049a5a0 had already been read. Its
   plate comment documents the format-agnostic colour scaling and the
   g_bitsR misuse in full, and pixel-format.txt section 1.1.1 carries
   the analysis. Nothing about the fade itself is revisited here.

   What is new is what it does AROUND the fade, because it is the only
   function that drives the frame lock by hand.

40.1.  The lock-only mode of BeginFrame, demonstrated

   Section 38 described Screen3D_BeginFrame as taking two parameters
   that gate the lock and the span reset separately, but had no caller
   exercising the split. FadeRect is that caller [verified]:

       if (!g_frameLockValid) {
           didLock = true;
           Screen3D_BeginFrame(1, 0);      /* lock, do NOT reset */
       }

   param_1 = 1 skips the whole span-state block - the free-list seed,
   g_spanBufferCount, maybe_g_batchCount, g_spanAccepting - and leaves
   only the surface lock. That is exactly the reading section 38.1 gave
   the gate, now confirmed from the call side rather than from the
   branch structure alone.

   It matters because FadeRect runs on a frame that is already composed.
   Resetting the free list mid-frame would tell the renderer that every
   pixel is uncovered again, and Screen3D_EndFrame would then paint the
   whole screen with the background colour. The parameter exists to
   prevent exactly that.

40.2.  It inlines EndFrame rather than calling it

   The teardown is the unlock block of Screen3D_EndFrame written out
   again, with the same three conditions and the same two final stores
   [verified]:

       if (didLock && g_frameLockValid) {
           if (!g_ddReleaseLockEarly) Cdd_UnlockMain();
           g_frameBuffer    = 0;
           g_frameLockValid = 0;
       }

   So the lock lifecycle has two implementations, not one, and a port
   that changes the policy has to change both. The duplicate is easy to
   miss because FadeRect is filed under drawing rather than under frame
   management.

   The whole software path is additionally gated on g_pCd3d being non-
   null. When it is null the function locks, draws nothing, and unlocks
   - which is harmless but worth knowing before concluding a fade did
   not happen for a colour-related reason.

40.3.  A dead store per pixel, and what it says about the source

   The half-brightness inner loop stores to the same address twice. The
   decompiler shows it, and unlike the g_viewHeight assignment of
   section 39.5 this one is REAL - the disassembly has two MOV word ptr
   to [EBX-2] [verified]:

       0049ac34  MOV word ptr [EBX + -0x2], AX    ; v >> 1
       ...compute the two-bit mask from g_shlR, g_shlG...
       0049ac57  MOV word ptr [EBX + -0x2], DX    ; masked

   The first store is dead; its value is overwritten a few instructions
   later without being read. A 16-bit write to the frame buffer for
   every pixel of every fade, discarded.

   The interesting part is not the waste, which is small. It is what it
   says about the original source. A compiler that could not eliminate
   this store almost certainly received two separate statements
   [inferred]:

       *p = v >> 1;
       *p &= ~((1 << (shlR - 1)) | (1 << (shlG - 1)));

   The reconstruction should keep that shape. It is also a useful
   calibration for the rest of this subsystem: MSVC of this vintage does
   not eliminate dead stores through a pointer, so a redundant-looking
   memory write in the decompiler output is evidence about the source
   rather than something to tidy away.

   Two suspicious constructs in two consecutive functions, one an
   artifact and one real, is a reasonable argument for checking the
   disassembly every time rather than judging from the decompiler.


41.  The flusher, and the second kind numbering

   Screen3D_FlushSpans at 0x004af130 had already been read; section 16
   covers the batch loop, the per-batch dirty flag and the record
   layouts, and pixel-format.txt section 1.3.2 carries the self-
   modification analysis. Re-reading it settles two things that were
   left hanging elsewhere.

41.1.  Every chain queues under a DIFFERENT kind number

   Section 35 established that the K<n> suffix on a specialised chain is
   the primitive kind the dispatcher switches on. That is correct, and
   it is not the number the flusher sees. Each deferring chain writes
   its own literal kind into the batch record at the Tri layer
   [verified]:

   +--------------------+----------------+------------+------------+
   | Chain              | Primitive kind | Batch kind | Written at |
   +====================+================+============+============+
   | Screen3D_TriK2Full | 2              | 40         | 0x004aaf1a |
   +--------------------+----------------+------------+------------+
   | Screen3D_TriK2Half | 2              | 41         | 0x004ac099 |
   +--------------------+----------------+------------+------------+
   | Screen3D_TriK4     | 4              | 19         | 0x004ad2ac |
   +--------------------+----------------+------------+------------+
   | Screen3D_TriK9     | 9              | 20         | 0x004ae5cd |
   +--------------------+----------------+------------+------------+
   | Screen3D_TriK42    | 42             | 42         | 0x004a9c9a |
   +--------------------+----------------+------------+------------+

   So there are TWO kind numberings. The dispatcher switches on one at
   0x004af100; the flusher switches on the other, and resolves the
   filler as g_spanTable[batchKind]. They coincide only for kind 42,
   which is why the collision looked like coincidence in section 35.

   Only the five Defer chains appear. Kinds 1 and 3 are Now chains,
   never queue, and so have no batch kind at all - which is the same
   division as everywhere else in this subsystem.

41.2.  The deferred filler is always the immediate filler

   Resolving each batch kind through g_spanTable gives the function the
   flusher actually calls, and it can be set against the one the clipper
   calls directly [verified]:

   +------------+------------------------------+----------------------+-------+
   | Batch kind | Flusher calls                | Immediate path calls | Same? |
   +============+==============================+======================+=======+
   | 40         | Screen3D_SpanTexKeyedK2Full  | the same             | yes   |
   +------------+------------------------------+----------------------+-------+
   | 41         | Screen3D_SpanTexKeyedK2Half  | the same             | yes   |
   +------------+------------------------------+----------------------+-------+
   | 19         | Screen3D_SpanNopK4           | the same             | yes   |
   +------------+------------------------------+----------------------+-------+
   | 20         | maybe_Screen3D_SpanShadedTex | the same             | yes   |
   +------------+------------------------------+----------------------+-------+
   | 42         | Screen3D_SpanStencilFlatK42  | the same             | yes   |
   +------------+------------------------------+----------------------+-------+

   Five for five. The immediate and deferred paths of a chain draw with
   exactly the same code, and deferral changes only WHEN a span is
   filled, never HOW. That had been assumed since section 25.3 and is
   now read rather than assumed.

   It also closes the doubt section 35 raised about kind 4. Its deferred
   filler really is the bare RET its immediate path calls, so kind 4 is
   inert on both paths and the classification in section 34.2 stands.

41.3.  A trap in reading g_spanTable

   Section 15.3 records that the table is stored PRE-SCATTER, so the key
   field carries the kind and the slot position is meaningless until
   Screen3D_ScatterTableByKey has run. That is easy to read past and
   expensive to forget.

   Indexing the static image by slot returns a well-formed record with a
   plausible filler every time. Doing it here gave kind 9 as
   maybe_Screen3D_SpanTexKeyedHalfAffine and kind 2 as
   maybe_Screen3D_SpanTexHalfAffine - both real fillers, both wrong, and
   neither obviously so. Searching the key field gives
   Screen3D_SpanNopK4 and Screen3D_SpanTexKeyedK2Full.

   o Always search g_spanTable by its key field. Never index it by slot.
     The wrong answer looks exactly like a right one.

41.4.  The span record has no field at +0x00

   Section 34.1 flagged four bytes at the head of the 0x1c-byte span
   record that no producer writes, and asked what fills them. Nothing
   does, and nothing reads them either [verified]. The flusher's seven
   loads are at +0x04 row pointer, +0x08 and +0x0a the x bounds, +0x0c
   u, +0x10 v, +0x14 w and +0x18 shade - the same seven fields the
   clippers write, and no eighth.

   Every reference to 0x0068b040 in the binary is an LEA computing a
   record base, not a field access. So the record simply has an unused
   first dword: four bytes per record across a 0x2800-entry queue, forty
   kilobytes of nothing. CLOSED - it is padding or a removed member, not
   a field waiting to be identified.


42.  TriK9, and a batch is half a triangle

   Screen3D_TriK9 at 0x004adf10 is the edge walker for the shaded chain,
   and the first Tri function read since section 14 established that
   Emit and Tri are one layer. The walking itself is what section 14.1
   described - rotate until y0 is smallest, gradients as (dx * 0x2000) /
   dy, pre-step when y is negative, shorten past g_viewMaxY, two halves
   - and none of that is revisited. Three other things came out of it.

42.1.  The signature, recovered

   Sixteen arguments, and the rotation loop identifies every one of them
   by which others it swaps with [verified]:

       Screen3D_TriK9(x0, y0, x1, y1, x2, y2,
                      texBase,
                      u0, v0, u1, v1, u2, v2,
                      s0, s1, s2)

   The rotation moves (8,9) <- (10,11) <- (12,13) and 14 <- 15 <- 16 in
   step with the three x,y pairs, which fixes the UV pairs and the three
   shades against their vertices. param_7 sits outside the rotation and
   is stored straight into g_texBase, so it is per-triangle rather than
   per-vertex.

   This is the first full argument list recovered for the layer, and it
   is worth having because the layer takes no struct: everything arrives
   flattened, which is why the decompiler shows sixteen ints and no
   shape.

42.2.  A batch is one HALF of one triangle

   Section 7.2 recorded the span count as the spans emitted for a
   triangle. It is finer than that. The append sits INSIDE the two-
   halves loop, and captures the queue depth at the top of each half
   [verified]:

       for each half {
           mark = g_spanBufferCount;
           ...walk the scanlines of this half...
           if (g_spanBufferCount != mark) {
               ...append a batch, count = g_spanBufferCount - mark...
           }
       }

   So one triangle appends up to TWO batch records, and a half that
   produced no spans - fully clipped, or zero height - appends none. A
   batch is not a primitive and not a triangle; it is a contiguous run
   of spans from one triangle half.

   That matters for the self-modifying fillers. The dirty flag that
   makes patching safe is raised once per batch by Screen3D_FlushSpans,
   and section 12.7.2 reasoned about that granularity. The granularity
   is finer than a primitive, which makes the invariant stronger rather
   than weaker - but the reasoning should rest on the right unit.

42.3.  The richest producer-consumer agreement so far

   Section 16.1 matched producer and consumer for kind 12, which writes
   three fields. Kind 20 writes seven, and every one is read back by the
   flusher's case for 0x14 [verified]:

   +--------+--------------------+-------------------------------+
   | Offset | TriK9 writes       | FlushSpans case 0x14 restores |
   +========+====================+===============================+
   | +0x00  | the literal 0x14   | the switch selector           |
   +--------+--------------------+-------------------------------+
   | +0x04  | spans this half    | the inner loop count          |
   +--------+--------------------+-------------------------------+
   | +0x08  | g_texBase          | g_texBase                     |
   +--------+--------------------+-------------------------------+
   | +0x10  | maybe_g_texPalette | maybe_g_texPalette            |
   +--------+--------------------+-------------------------------+
   | +0x14  | g_texStepU         | g_texStepU                    |
   +--------+--------------------+-------------------------------+
   | +0x18  | g_texStepV         | g_texStepV                    |
   +--------+--------------------+-------------------------------+
   | +0x20  | maybe_g_shadeStep  | maybe_g_shadeStep             |
   +--------+--------------------+-------------------------------+

   Seven for seven, derived from opposite ends. It also confirms the
   union reading of +0x20 directly: TriK9 stores a shade STEP there and
   the flusher restores it as one, whereas the flat kinds store and
   restore a shade VALUE in the same slot. Two different tiers of the
   three-tier model sharing an offset.

42.4.  screenX and screenY are plain integers

   docs/structs/MR_Vertex.txt asked whether the screen coordinates carry
   fraction, noting that the emitters scale them by 0x2000 and that this
   would be redundant if they did. TriK9 answers it [verified].

   The x arguments are multiplied - maybe_g_spanXRight = x0 * 0x2000 -
   and the y arguments are used raw as scanline indices and as array
   subscripts into g_scanlineOffset and g_spanScanlineHead. A value
   carrying thirteen fractional bits could not index an array. So both
   are plain integers, and the 0x2000 scaling exists to give the edge
   DDA sub-pixel precision it is not given.

   CLOSED in MR_Vertex.txt.


43.  TriK4, and what an emptied filler costs

   Screen3D_TriK4 at 0x004acc00 is Screen3D_TriK9 with two bytes
   changed. Diffing them by longest common subsequence gives 509
   instructions in common out of 554 and 559, and every difference
   except one is register allocation, mirrored comparisons, or FPU stack
   scheduling. The one exception is the batch kind literal [verified]:

       TriK4   004ad2ac   MOV dword ptr [ECX], 0x13
       TriK9   004ae5cd   MOV dword ptr [ECX], 0x14

   The call target differs too - ClipSpanK4 against ClipSpanK9 - but
   that is a relocation, not a difference in shape. This is the fifth
   family in the subsystem to turn out to be one routine copied, after
   the free-list allocator of section 26.2, the subdivision wrapper, the
   edge walker, and the eight clippers of section 37.1.

43.1.  Kind 4 does the whole job and throws it away

   The append block was checked instruction by instruction rather than
   trusted to the diff, and TriK4 writes exactly the seven fields TriK9
   writes [verified]:

       004ad2a9  MOV [ECX + 0x04], EAX    ; span count
       004ad2ac  MOV [ECX + 0x00], 0x13   ; kind
       004ad2b8  MOV [ECX + 0x08], EBX    ; g_texBase
       004ad2c1  MOV [ECX + 0x14], EDX    ; g_texStepU
       004ad2c9  MOV [ECX + 0x18], EAX    ; g_texStepV
                 ...and maybe_g_texPalette, maybe_g_shadeStep

   So a kind 4 primitive is transformed, rotated, near-clipped, edge-
   walked, clipped against the free list per scanline, queued as span
   records, and given a batch carrying a texture base, a palette, two
   interpolant steps and a shade step. Screen3D_FlushSpans then restores
   all of it and calls Screen3D_SpanNopK4, which returns.

   That changes how the kind should be described. Sections 25 and 34.2
   called it vestigial, which left open whether it was ever finished.
   The machinery says it was: this is not a stub that was never written
   but a COMPLETE PIPELINE whose innermost function was replaced with a
   RET [inferred, and strongly - nobody writes a palette pointer into a
   queue for a primitive they never implemented].

   Its machinery is identical to kind 9's, the shaded textured mode,
   which suggests kind 4 was a second shaded variant that was disabled
   rather than removed. Why is not recoverable from the binary.

43.2.  What it costs, and what that means for the port

   Everything above the filler still runs, so a kind 4 primitive costs
   almost exactly what a kind 9 primitive costs and produces nothing.
   The only work saved is the per-pixel loop itself.

   o It also consumes queue capacity. Kind 4 batches count against the
     1000-batch cap and its spans against the 0x2800 span cap, both of
     which clear g_spanAccepting when reached. So invisible geometry can
     push visible geometry out of a frame.

   o Section 34.3 already concluded kind 4 can be dropped from the port.
     This strengthens that: dropping it is not merely safe, it reclaims
     real per-frame work and real queue capacity.

   o Whether any of this is reachable depends on whether the shipped
     track and object data actually contain kind 4 primitives. Nothing
     in the code answers that; the asset formats would. Worth a look
     when the mesh format is next opened, and cheap to check then. OPEN.

   The same question applies to kind 3, but with the opposite
   significance. Kind 3 is an occluder and its empty filler is the point
   of it, so finding kind 3 primitives in the data would confirm a
   working feature. Finding kind 4 primitives would confirm wasted work.


44.  The Tri layer is the clipper layer, one level up

   Cross-referencing all fourteen functions of the Emit/Tri layer for
   two properties - do they touch maybe_g_shadeStep, and do they append
   to maybe_g_batchQueue - sorts the eight TriKn into the same two by
   two as the eight clippers [verified]:

   +-------+------------------------------+--------------------------+----------------------+
   |       | no shade                     | flat shade               | interpolated shade   |
   +=======+==============================+==========================+======================+
   | Now   | TriK1Full 463, TriK1Half 463 | -                        | TriK3 522            |
   +-------+------------------------------+--------------------------+----------------------+
   | Defer | -                            | TriK2Full/K2Half/K42 498 | TriK4 554, TriK9 559 |
   +-------+------------------------------+--------------------------+----------------------+

   CORRECTED in section 45.1. An earlier version of this table had two
   shade columns and put the 498-instruction trio in the shadeless one,
   because the probe that built it tested only maybe_g_shadeStep. Those
   three do touch maybe_g_edgeShade: they carry a FLAT shade with no
   gradient. The axis has three states, not two.

   Instruction counts, not byte sizes, and they cluster exactly rather
   than approximately. Three functions at 498 and two at 463 is not a
   family resemblance; it is the same code emitted more than once.

   So the Now/Defer property runs coherently through every layer of a
   chain. The dispatcher picks a DrawPrim, which calls a Tri, which
   calls a ClipSpan, which calls a filler - and at each level the same
   two axes decide which variant is used. Section 34.2 established the
   property is a per-kind decision; this shows it is honoured
   identically four levels deep.

44.1.  Two of them are literally the same instruction stream

   Comparing position by position, with branch and call targets
   normalised, gives a sharper result than the clipper diffs of section
   37.1 did [verified]:

   +------------------------+--------------+-----------------------------+
   | Pair                   | Instructions | Positional differences      |
   +========================+==============+=============================+
   | TriK1Full vs TriK1Half | 463 vs 463   | ZERO                        |
   +------------------------+--------------+-----------------------------+
   | TriK2Full vs TriK42    | 498 vs 498   | one: MOV [ECX],0x28 vs 0x2a |
   +------------------------+--------------+-----------------------------+

   TriK1Full and TriK1Half have no differing instruction at all. Every
   opcode and every operand matches; the only thing that distinguishes
   1669 bytes of code from another 1669 bytes is which clipper the CALL
   points at. TriK2Full and TriK42 differ in one immediate, the batch
   kind.

   The clipper pairs of section 37.1 still carried register allocation
   noise and mirrored comparisons. These do not, which makes the macro
   reading close to certain: one body in the source, instantiated per
   kind with the clipper and the batch kind as parameters [inferred, and
   about as strongly as a binary permits].

44.2.  What this is worth to the reconstruction

   The eight TriKn occupy 14,851 bytes. Four templates would occupy
   about 7,476. Roughly half the layer is duplication, and the same
   holds one level down for the clippers and one level up for the
   DrawPrim functions.

   o Write four parameterised routines, not eight. Section 37.1 said
     this for the clippers and noted it is not a refactor toward nice;
     the zero-difference pair here is the proof of that, because a hand-
     written duplicate would have drifted.

   o The parameters are exactly: which clipper to call, which batch kind
     to stamp, whether to carry a shade, and whether to append a batch
     at all. Nothing else varies across the eight.

44.3.  What is left in this family

   Very little, and it is worth saying so rather than reading seven more
   functions to find out:

   +----------------------+-------------------------------------------------+
   | Function             | Status                                          |
   +======================+=================================================+
   | TriK1Half            | proven identical to TriK1Full, zero differences |
   +----------------------+-------------------------------------------------+
   | TriK42               | proven identical to TriK2Full but one immediate |
   +----------------------+-------------------------------------------------+
   | TriK2Full, TriK2Half | same 498-instruction template                   |
   +----------------------+-------------------------------------------------+
   | TriK4, TriK9         | diffed in section 43                            |
   +----------------------+-------------------------------------------------+
   | TriK3                | sole Now+shade member; has no twin              |
   +----------------------+-------------------------------------------------+

   TriK3 is the only one with no counterpart already read. By analogy
   with ClipSpanK3 = ClipSpanK1Full plus a shade term it should be
   TriK1Full plus a shade term, and its 522 against 463 instructions
   fits that. Not verified - the diff has not been run.

   The five maybe_Screen3D_EmitTri* functions are a different matter.
   They reach their filler through the maybe_g_spanClipper pointer
   rather than by direct call, they all append batches, and they carry
   the affine/perspective axis that the specialised chains do not.
   Sections 19 to 23 read them individually; the matrix above is
   consistent with what those found.


45.  TriK3: a full Gouraud setup for a primitive that draws nothing

45.1.  The shade axis has three states

   The matrix in section 44 was built by asking which functions touch
   maybe_g_shadeStep. That is the wrong question, and asking a better
   one splits the family differently [verified]:

   +------------------------------+---------+------+-----------------------+
   | Function                     | RET imm | Args | Shade globals touched |
   +==============================+=========+======+=======================+
   | TriK1Full, TriK1Half         | 0x34    | 13   | none                  |
   +------------------------------+---------+------+-----------------------+
   | TriK2Full, TriK2Half, TriK42 | 0x34    | 13   | edgeShade only        |
   +------------------------------+---------+------+-----------------------+
   | TriK3                        | 0x40    | 16   | edgeShade + shadeStep |
   +------------------------------+---------+------+-----------------------+
   | TriK4, TriK9                 | 0x40    | 16   | edgeShade + shadeStep |
   +------------------------------+---------+------+-----------------------+

   The stack cleanup gives the argument count directly and is a cleaner
   discriminator than any global. Thirteen arguments is
   x0,y0,x1,y1,x2,y2, texBase, u0,v0,u1,v1,u2,v2 - exactly the signature
   of section 42.1 with the three per-vertex shades removed.

   So the middle group takes no shade argument at all and still writes
   maybe_g_edgeShade. Its shade is a per-primitive value arriving
   through a global from the DrawPrim layer, which is the flat tier of
   the three-tier model and matches what Screen3D_FlushSpans does with
   batch +0x20 for kinds 40, 41 and 42 - it restores a shade VALUE
   there, where for kinds 19 and 20 it restores a shade STEP.

   CONFIRMED from the DrawPrim side in section 49.2. The layer above
   splits the same way: DrawPrimK1Full, K1Half, K2Full, K2Half and K42
   write maybe_g_edgeShade and their TriKn does not compute it, while
   DrawPrimK3, K4 and K9 never touch it and pass three per-vertex shades
   as arguments instead [verified].

45.2.  What TriK3 actually does

   Kind 3 is the occluder. Its filler, Screen3D_SpanNopK3, is a single
   0xc3. TriK3 nevertheless takes the full sixteen-argument signature
   and does all of this [verified]:

   o Receives a texture base and three per-vertex UV pairs, and computes
     g_texStepU and g_texStepV.

   o Receives three per-vertex shades and computes maybe_g_shadeStep
     with an IDIV - a division per triangle for a gradient nothing
     reads.

   o Steps maybe_g_edgeU, maybe_g_edgeV and maybe_g_edgeShade along both
     edges, once per scanline, for the whole height of the triangle.

   Screen3D_ClipSpanK3 then copies those into g_spanU, g_spanV and
   maybe_g_spanShade before every call to the nop - the dead stores
   recorded in section 37. The value chain is complete from argument to
   global and is read by nobody.

45.3.  One cause behind three separate observations

   Three findings in this document have looked like isolated oddities.
   They are one thing seen three times:

   +---------+------------------------------------------------------------+
   | Section | Observation                                                |
   +=========+============================================================+
   | 37      | ClipSpanK3 stores u, v and shade before calling a RET      |
   +---------+------------------------------------------------------------+
   | 43      | TriK4 writes seven batch fields for a filler that is a RET |
   +---------+------------------------------------------------------------+
   | 45      | TriK3 computes a shade gradient for a filler that is a RET |
   +---------+------------------------------------------------------------+

   The cause is the template structure of section 44. Each layer is one
   body instantiated per kind, parameterised by which clipper to call,
   which batch kind to stamp, and whether a shade is flat or
   interpolated - but NOT by which interpolants the filler at the end of
   the chain actually reads. A kind whose filler reads nothing still
   gets everything computed for it [inferred, and it explains all
   three].

   This is worth separating from the kind 4 finding of section 43,
   because the two are different in kind. Kind 4 is a DISABLED feature
   and its waste is a leftover. Kind 3 is a WORKING feature - the
   occluder is the point of it - and its waste is structural. It is the
   price of building eight chains from four templates, and it was
   presumably judged worth paying against the alternative of writing and
   maintaining a specialised occluder chain.

45.4.  A free win for the port

   Specialising per kind removes all of it at no behavioural cost. The
   values are provably unread, so dropping them cannot change a pixel
   [verified - the chain ends in a RET].

   o An occluder needs x, y and nothing else. No texture base, no UV
     steps, no shade, no gradient divides, no per-scanline interpolant
     stepping, and no per-span stores.

   o Section 34.3 already had kind 3 becoming a depth-only draw on
     modern hardware, which makes this moot there. It is not moot for a
     faithful software-rasterizer reference build, where the temptation
     is to transcribe the template as-is.

   The general rule the reconstruction should follow: transcribe the
   templates, then specialise the instantiations whose filler ignores an
   interpolant. Keeping the dead computation would be faithful to the
   binary and faithful to nothing that matters.


46.  DrawPrimK3, and the texture lock nobody noticed

   Screen3D_DrawPrimK3 at 0x004a6a50 is the first function of the
   DrawPrim layer read in full. Most of what it does is already
   documented from the Setup side in section 13 - the vertex indices at
   face+0x2c, the quad fan using [0],[1],[2] then [0],[2],[3], the early
   exit when the s16 at face+0x34 is -1, the near-plane clip through
   maybe_Screen3D_ClipEdgeNear, and the per-axis trivial-reject
   counters. None of that is revisited; section 13.1 had it right.

   What the read produced instead was the identity of a function sixteen
   callers use and nobody had opened.

46.1.  FUN_00401050 is a DirectDraw Lock

   Section 4 recorded step 2 of the Setup skeleton as 'fetch the texture
   page with FUN_00401050(1)', which reads like a table lookup. It is
   not. The function, now maybe_Bankw_LockPageBits, locks a surface
   [verified]:

       if (this->surface) {
           if (IsLost() == DDERR_SURFACELOST) Restore();
           if (Lock(0, &desc, 1, 0) == 0) {
               this->bits = desc.lpSurface;
               if (...) Unlock(0);
           }
       }
       return this->bits;

   The COM slots are +0x60 IsLost, +0x6c Restore, +0x64 Lock and +0x80
   Unlock - the same IDirectDrawSurface vtable the dd.cpp family in dd-
   present.txt uses on g_lpDDSMain, applied here to a texture page
   instead of the back buffer.

   So the software rasterizer's texture base is obtained by a surface
   lock PER PRIMITIVE, with lost-surface checking and a conditional
   unlock on every one. Every Screen3D_DrawPrimKn and every
   maybe_Screen3D_SetupPrimN calls it.

46.2.  The literal argument was never real

   WRONG, and corrected in section 47.1. This subsection claimed the
   literal 1 was invented by the decompiler. It is a real argument. What
   the missing calling convention hid was the THIS POINTER, not the
   stack argument - the call site loads ECX with a computed pointer
   [verified]:

       004a6a82  LEA ECX,[EAX*0x8 + 0x4f92f8]   ; EAX = 103 * i
       004a6a89  CALL maybe_Bankw_LockPageBits

   824 bytes per record, which is the bank-record stride confirmed three
   times over in formats/mesh-3df-map.txt and
   subsystems/d3d-textures.txt. Setting the convention in the database
   fixes the decompilation of all sixteen callers at once and is why the
   next finding became visible at all.

   o A function with an unmodelled convention decompiles with a PARTIAL
     argument list, and the part it drops may be either end. See section
     47.1 for what that cost here.

46.3.  face+0x36 is the texture page index

   With the convention fixed the call reads [verified]:

       bits = LockPageBits(&bank[ *(u16 *)(face + 0x36) ]);

   docs/structs/MR_Mesh.txt has face+0x36 as 's16, gates the
   faceKindSelect branch', which was as much as its loader-side evidence
   supported. It is an index into the 824-byte texture bank, and that
   explains the gating: a face with page 0 takes the untextured branch.

   Whether 0 is a reserved sentinel or a real page is not settled here -
   DrawPrimK3 indexes with it unconditionally. Recorded in MR_Mesh.txt
   with that caveat.

46.4.  The occluder locks a texture it never samples

   Kind 3 draws nothing. Section 45 found it computing UV steps and a
   shade gradient for a filler that is a bare RET, and explained that as
   the price of the shared template. This is the same waste one layer up
   and considerably more expensive: before any of that, DrawPrimK3
   performs a DirectDraw surface lock to obtain a texture pointer that
   no code will ever dereference [verified].

   A dead store costs a write. A dead COM call costs an interface
   dispatch, a driver transition, and on a lost surface a full Restore.
   It is the most expensive instance of the template problem found so
   far, and it happens once per occluder primitive per frame.

   o For the port this is another free removal, in the sense of section
     45.4 - the pointer is provably unused. It is worth more than the
     others because it removes a driver call rather than a few
     instructions.

   o It also sharpens what section 38.3 said about surface pointers. The
     frame buffer is locked once per frame; TEXTURE pages are locked
     once per primitive. Those are different lifetimes and a port has to
     model both, not assume one policy.


47.  LockPageBits in full, and a correction to section 46

47.1.  The argument was real; I removed it

   Section 46.2 recorded that the literal 1 in FUN_00401050(1) was a
   decompiler artifact. That is wrong, and the way it went wrong is
   worth keeping.

   Two readings were each half right [verified]:

   +---------------------+--------------------+-------------------------+
   | State               | Decompiled as      | What it omitted         |
   +=====================+====================+=========================+
   | no convention set   | FUN_00401050(1)    | the this pointer in ECX |
   +---------------------+--------------------+-------------------------+
   | __thiscall, 1 param | LockPageBits(page) | the stack argument      |
   +---------------------+--------------------+-------------------------+

   Setting a one-parameter __thiscall fixed the first omission and
   created the second, and because the new output looked cleaner it read
   as confirmation. The stack cleanup settles it without ambiguity: the
   function ends RET 0x4, so exactly one dword of arguments is popped,
   and it is not the this pointer.

   The frame layout confirms it from the other side. The prologue is SUB
   ESP,0x6c - sizeof(DDSURFACEDESC) - and the descriptor base is ESP+8
   after two pushes. The read at [ESP+0x2c] is therefore desc+0x24,
   which is lpSurface. But the gate on the unlock reads [ESP+0x78],
   which is desc+0x70 and lies PAST the 0x6c-byte structure. It can only
   be the stack argument.

   o The rule worth keeping is not 'conventions invent arguments'. It is
     that RET imm and the frame size together pin the argument list, and
     either can be checked in seconds. A prototype that merely looks
     tidier is not evidence.

47.2.  What the function does

       void *Bankw_LockPageBits(this, int releaseImmediately)

           if (!this->surface) return this->bits;
           if (IsLost() == DDERR_SURFACELOST) Restore();
           DAT_004dc14c = 1;
           desc.dwSize = 0x6c;
           if (Lock(NULL, &desc, DDLOCK_WAIT, NULL) == 0) {
               this->bits   = desc.lpSurface;
               this->locked = 1;
               this->+0x334 = 0;
               if (releaseImmediately) {
                   Unlock(NULL);
                   this->locked = 0;
               }
           }
           return this->bits;

   Four fields of the 824-byte bank record are now identified from this
   function alone [verified]:

   +--------+-------------------------------------------------+
   | Offset | Field                                           |
   +========+=================================================+
   | +0x2e0 | IDirectDrawSurface * for the page, NULL if none |
   +--------+-------------------------------------------------+
   | +0x2e4 | locked flag: 1 while held, 0 after release      |
   +--------+-------------------------------------------------+
   | +0x330 | cached bits pointer, and the return value       |
   +--------+-------------------------------------------------+
   | +0x334 | zeroed on every successful lock; unidentified   |
   +--------+-------------------------------------------------+

47.3.  The same policy as the frame buffer, engine-wide

   This is the finding the correction was hiding. releaseImmediately = 1
   means lock the surface, keep the bits pointer, unlock at once, and
   then SAMPLE THE TEXTURE THROUGH AN UNLOCKED POINTER for the rest of
   the primitive.

   That is precisely what g_ddReleaseLockEarly does for the back buffer
   in sections 38.3 and 39.3. The difference is only in how it is
   controlled: a global there, a per-call argument here [verified].

   +-------------------------------------------+--------+--------------------------+
   | Caller                                    | Passes | Meaning                  |
   +===========================================+========+==========================+
   | the eight Screen3D_DrawPrimKn             | 1      | release, sample unlocked |
   +-------------------------------------------+--------+--------------------------+
   | the four maybe_Screen3D_SetupPrimN        | 1      | same                     |
   +-------------------------------------------+--------+--------------------------+
   | Load3dfAndMap, FUN_004216a0, FUN_00462c60 | 1      | same                     |
   +-------------------------------------------+--------+--------------------------+
   | FUN_00479260, menuTools.cpp:68            | 0      | HOLDS the lock           |
   +-------------------------------------------+--------+--------------------------+

   One caller out of fifteen holds the lock, and it is the menuTools
   function the source map places at menuTools.cpp line 68 - not a
   rasterizer path. So every drawing path in the engine reads its
   texture through a released pointer.

   Taken with section 38.3 this stops being a quirk of the frame buffer
   and becomes an engine-wide invariant: DirectDraw surfaces are locked
   to obtain an address and then used without the lock. It works because
   a 1997 driver returns a stable linear address for a system-memory or
   unmoved video-memory surface, and it is undefined behaviour under the
   API contract.

   o A port must not reproduce it. What it must reproduce is the
     assumption: within a primitive, the texture base does not move;
     within a frame, the frame buffer base does not move.

   o The two lifetimes differ and both matter. A modern implementation
     that maps a texture per draw call is doing more work than the
     original, which locks per PRIMITIVE - and one that maps once per
     frame is doing less, which is fine but is not what the original
     assumed.

47.4.  An open global

   DAT_004dc14c is set to 1 here before every lock, and it is not local
   to this function. Twelve functions write it - Cdd_LockMain,
   maybe_Cdd_LoadRawToSurface, maybe_D3D_LoadRawToTexture,
   maybe_D3D_UploadTexture, maybe_Cdd_DrawSurface and others - and every
   one of them is a surface lock, upload or blit. Exactly one function
   reads it, maybe_Game_Tick, which then writes it again [verified].

   That shape - many setters in the graphics paths, one reader in the
   frame loop that clears it - reads as a per-frame 'a surface was
   touched' flag. Not named on that: what maybe_Game_Tick does with it
   has not been read. OPEN.


48.  The DrawPrim layer, and where kind 42 gets its brightness

48.1.  Eight functions, one template, three clusters

   All eight Screen3D_DrawPrimKn take three arguments and end RET 0xc,
   and all eight call exactly the same four functions - their own TriKn,
   __ftol, maybe_Bankw_LockPageBits and maybe_Screen3D_ClipEdgeNear. One
   does more [verified]:

   +--------------------------------+--------------+---------------------------------+
   | Group                          | Instructions | Matches                         |
   +================================+==============+=================================+
   | K1Full, K1Half, K2Full, K2Half | 638 - 641    | 13-argument TriKn               |
   +--------------------------------+--------------+---------------------------------+
   | K3, K4, K9                     | 650 - 652    | 16-argument TriKn               |
   +--------------------------------+--------------+---------------------------------+
   | K42                            | 709          | 13-argument TriKn plus a colour |
   +--------------------------------+--------------+---------------------------------+

   The clusters line up with the argument counts of section 45.1, which
   is a good independent check on both: a DrawPrim that has to marshal
   three per-vertex shades is about ten instructions larger than one
   that does not.

   Screen3D_DrawPrimK42 is the outlier by 58 instructions and the only
   one of the eight that calls Color_Convert555ToSurface. That
   difference is the whole of section 48.2.

48.2.  Kind 42 halves its colour, not its texels

   Section 33.2 observed that kind 42 has no Half variant, inferred that
   it would not need one because its colour is a single per-primitive
   value, and left OPEN whether anything actually darkens it. It does
   [verified]:

       if (bank[face->page] is not loaded) {
           c  = Color_Convert555ToSurface(face->colour);
           c  = (c & 0xffc1) >> 1 | (c & 0x1f);
       }
       if ((v0.shade + v2.shade + v1.shade) / 3 < 0x3e000)
           c = c >> 1 & g_halveMask;
       maybe_g_spanFlatColor = c << 16 | c;

   Same threshold, same mask, same two-level quantisation as the
   Full/Half chains of section 27.2 - applied to the COLOUR at setup
   rather than to the texel at the store. That is why kind 42 needs one
   filler where kinds 1 and 2 need two: there is nothing per-pixel to
   darken, so the darkening moves up to where the colour is computed.

   The dword duplication is here too, c << 16 | c, which is a third
   independent producer of the two-pixels-per-dword convention of
   section 11.7.2.

48.2.1.  The brightness test is not the same test

   The threshold is identical and the SAMPLING is not, which had not
   been noticed [verified]:

   +---------+----------------------------+--------------------------+
   | Kinds   | Decided in                 | Tested value             |
   +=========+============================+==========================+
   | 1 and 2 | Screen3D_DispatchPrimitive | the FIRST vertex's +0x0c |
   +---------+----------------------------+--------------------------+
   | 42      | Screen3D_DrawPrimK42       | the AVERAGE of all three |
   +---------+----------------------------+--------------------------+

   Both compare against 0x3e000, which is 31.0 in the 19.13 fixed point.
   So a primitive straddling the threshold can be bright as a kind 1 and
   dim as a kind 42, or the reverse, depending on which vertex happens
   to be first. That is a real behavioural difference between the chains
   and not an implementation detail a port can normalise away.

   It also explains why section 10.4 could describe the test as 'a
   single vertex's intensity' and be right, while this function
   averages: they are two different decisions that happen to share a
   constant.

48.3.  A discrepancy with section 4, left open

   Section 4 records the flat-colour expression, derived from the Setup
   layer, as a single conversion of a modified input:

       Color_Convert555ToSurface((c & 0xffffffc1) >> 1 | (c & 0x1f))

   Screen3D_DrawPrimK42 computes something different - two conversions
   of the SAME input, with the masking applied to the results
   [verified]:

       (Convert(c) & 0xffc1) >> 1 | (Convert(c) & 0x1f)

   RESOLVED in section 52.2: the layers genuinely differ, and there are
   three distinct expressions rather than two. Section 4's formula is
   correct for the setups it was derived from and does not describe
   Screen3D_DrawPrimK42.

   Worth noting the compiler did NOT common up the two calls, which is
   consistent with the dead store of section 40.3: this toolchain does
   very little redundancy elimination, so repeated calls in the output
   are evidence of repeated calls in the source.

48.4.  Confirmations

   o TriK42 is called with thirteen arguments, from the caller side,
     matching the RET 0x34 measured in section 45.1.

   o The texture page index at face+0x36 is used twice here - once to
     test whether the page is loaded and once to lock it - which
     reinforces the identification in section 46.3.

   o maybe_g_texPalette is assigned from the third argument, as in
     Screen3D_DrawPrimK3. The palette is a DrawPrim-level parameter for
     the whole primitive.


49.  DrawPrimK9 adds nothing, and why that is worth recording

   Screen3D_DrawPrimK9 at 0x004ae730 is a copy. Against
   Screen3D_DrawPrimK4 it shares 579 of 651 instructions and every
   difference is an ESI/EDI swap; against Screen3D_DrawPrimK3 the
   differences are stack-slot assignments and LEA ordering. Neither diff
   shows a semantic difference [verified].

   Longest common subsequence is the wrong instrument for proving that,
   though, because register allocation noise depresses the match and
   cannot be told from real divergence by counting. The conclusive test
   is what the functions TOUCH.

49.1.  The globals settle it

   Every global each of the eight reads or writes, with the four called
   functions already known to be identical [verified]:

   +--------------------------------+---+-------------------------------------------------------+
   | DrawPrim                       | n | Globals                                               |
   +================================+===+=======================================================+
   | K1Full, K1Half, K2Full, K2Half | 6 | the five below + edgeShade                            |
   +--------------------------------+---+-------------------------------------------------------+
   | K3, K4, K9                     | 5 | viewMaxX, viewMaxY, nearPlaneZ, primCount, texPalette |
   +--------------------------------+---+-------------------------------------------------------+
   | K42                            | 9 | the six + bankRecords, halveMask, spanFlatColor       |
   +--------------------------------+---+-------------------------------------------------------+

   K3, K4 and K9 have IDENTICAL global sets - the difference between
   them is empty in both directions. Combined with the same four callees
   and the same RET 0xc, the three are one function with a different
   TriKn call and different register allocation.

49.2.  The shade split, confirmed from above

   The table also closes an inference. Section 45.1 found that the
   thirteen-argument TriKn write maybe_g_edgeShade despite taking no
   shade argument, and reasoned that the value must arrive through a
   global set by the DrawPrim layer. It does, and the split is exactly
   symmetric [verified]:

   +------------------------------+---------------------------+-----------------------------+
   | Shade model                  | DrawPrim writes edgeShade | TriKn arity                 |
   +==============================+===========================+=============================+
   | flat - kinds 1, 2, 42        | yes, once per primitive   | 13                          |
   +------------------------------+---------------------------+-----------------------------+
   | interpolated - kinds 3, 4, 9 | no                        | 16, three per-vertex shades |
   +------------------------------+---------------------------+-----------------------------+

   So a flat-shaded chain resolves its shade at the DrawPrim level and
   the Tri layer merely carries it; a Gouraud chain passes three values
   down and the Tri layer computes the gradient. The two tiers of
   section 8 are visible as a difference in argument count and in which
   layer owns the global.

49.3.  The specialised chain family is finished

   Every function of the switch-path family has now been read or proven

   +-------------+------------+-----------+---------------------+

   +=============+============+===========+=====================+
   | DrawPrimKn  | 8          | 3         | sections 46, 48, 49 |
   +-------------+------------+-----------+---------------------+

   Thirty functions and roughly 45 KB of code, generated from about

   o What remains genuinely unread in the subsystem is the table-path

50.  What the specialised chains actually buy

   Re-reading maybe_Screen3D_EmitTriFlatAffine produced nothing new
   about the function. Section 21 read it, section 19.3 measured its
   arity, and section 14.2 established that it copies maybe_g_primKind
   into the batch record. Every probe run here reproduced one of those.

   Setting it beside the switch-path family, now that all thirty of
   those functions are characterised, does say something neither half
   could say alone. The two dispatch paths make OPPOSITE specialisation
   trades, and the difference is visible in three specific places.

50.1.  One body with runtime branches, against many bodies without

   +----------------+-------------------------------------------+----------------------------+
   |                | table path, the Emit family               | switch path, the Kn chains |
   +================+===========================================+============================+
   | bodies         | one per interpolant set                   | one per kind and policy    |
   +----------------+-------------------------------------------+----------------------------+
   | Now vs Defer   | a runtime branch on maybe_g_spanDeferMode | compiled in; no branch     |
   +----------------+-------------------------------------------+----------------------------+
   | the filler     | indirect, through maybe_g_spanClipper     | a direct CALL              |
   +----------------+-------------------------------------------+----------------------------+
   | the batch kind | loaded from maybe_g_primKind              | an immediate operand       |
   +----------------+-------------------------------------------+----------------------------+

   So a specialised chain removes, per scanline, one indirect call; per
   triangle half, one branch on the defer mode and one global load for
   the kind. Section 27 recorded the indirect call as 'the whole reason
   the specialised chains exist'. It is the largest of the three but not
   the only one [verified].

   The cost is the duplication measured in sections 44.2 and 49.3:
   thirty functions and about 45 KB where eleven bodies would do. Six
   primitive kinds were judged worth that, and the twenty-six others
   were not.

50.2.  Which six, and why those

   The six kinds with hand-written chains are 1, 2, 3, 4, 9 and 42 -
   from the dispatcher jump table of section 35.1. Their identities
   [verified]:

   +------+--------------------------------+------------------------------+
   | Kind | What it is                     | Plausible reason for a chain |
   +======+================================+==============================+
   | 1    | opaque textured, Full and Half | the common case              |
   +------+--------------------------------+------------------------------+
   | 2    | colour-keyed, Full and Half    | the common transparent case  |
   +------+--------------------------------+------------------------------+
   | 3    | occluder                       | cheap and used everywhere    |
   +------+--------------------------------+------------------------------+
   | 4    | inert; a disabled feature      | was presumably common once   |
   +------+--------------------------------+------------------------------+
   | 9    | shaded textured                | the lit case                 |
   +------+--------------------------------+------------------------------+
   | 42   | textured stencil, flat fill    | foliage, signs, shadows      |
   +------+--------------------------------+------------------------------+

   That reads as the hot set of a racing game: road and scenery, cut-
   outs, shadows, and the occluders that hide what is behind the track.
   Kind 4 is the odd one, and section 43 argued it is a complete
   pipeline that was switched off - which fits here, since nobody hand-
   specialises a chain for a mode they never intended to ship.

   o This is the strongest indirect evidence yet that kind 4 was once a
     live mode. It is not merely implemented, it was implemented TWICE -
     once in the table and once as a specialised chain - which is not
     something done for dead code.

50.3.  For the reconstruction

   The specialised chains should not be transcribed as separate
   functions and should not be reproduced as an optimisation either.
   They exist to remove an indirect call and two loads on a 1997 CPU; a
   modern compiler inlining a template over a small closed set of kinds
   gets the same effect from one body.

   o Write the table-path emitter as the general form, since it is the
     one that handles both policies explicitly.

   o Treat the six specialised chains as evidence about which kinds are
     hot, not as code to port. Their existence is a profiling result
     from 1997, and that information is worth more than the duplication.


51.  Walker 7, and a function that cannot be reached

   maybe_Screen3D_EmitTriGouraudPersp was read in section 24, which
   found it to be exactly the union of the two emitters before it, and
   section 24.2 already recorded the striking part: walker 7 serves one
   primitive kind, number 29, whose span filler is a single RET. Nothing
   about the function itself is new here.

   Two things follow from that table which it did not draw out.

51.1.  maybe_Screen3D_Walk7Defer is unreachable

   A walker is selected in two steps: the walker INDEX comes from
   g_spanTable+0x04, and Now against Defer is then chosen by
   maybe_g_spanDeferMode, which is copied from g_spanTable+0x08 for the
   same kind. So a Defer walker runs only if some kind has both that
   walker index and defer = 1.

   Walker 7 has exactly one kind, and it is not deferred [verified]:

       kind 29   walker 7   defer 0   maybe_Screen3D_SpanNopK29

   Every one of the eight walkers is referenced from exactly one place,
   the walker table at 0x004f1ee0, and from nowhere else - the
   specialised chains of section 35 call their clippers directly and
   none of them is a Walk function. So there is no second route in.

   o maybe_Screen3D_Walk7Defer at 0x004a1a30, 636 bytes, cannot be
     executed by the shipped table. It is dead code, and the only Walk
     function of which that is true - walkers 4, 5 and 6 all have
     deferred kinds.

   It was presumably emitted because the walker table is regular: eight
   slots, a Now and a Defer for each of four interpolant sets. Writing
   seven and leaving a hole is more trouble than writing eight.

51.2.  The nop kinds tile the walker space

   Section 24.3 listed the kinds whose filler is a no-op. Setting them
   out by walker and policy shows they are not scattered - they are
   systematic [verified]:

   +------------------------+---------------------+-----------------+
   | Walker                 | Occluder, immediate | Inert, deferred |
   +========================+=====================+=================+
   | 0, no walker           | kind 5              | kind 19         |
   +------------------------+---------------------+-----------------+
   | 4, affine flat         | kind 1              | kind 8          |
   +------------------------+---------------------+-----------------+
   | 5, affine Gouraud      | kinds 3 and 18      | kinds 4 and 9   |
   +------------------------+---------------------+-----------------+
   | 6, perspective flat    | kind 28             | kind 50         |
   +------------------------+---------------------+-----------------+
   | 7, perspective Gouraud | kind 29             | NONE            |
   +------------------------+---------------------+-----------------+

   Every interpolant class has both a coverage-consuming occluder and an
   inert deferred twin - except walker 7, which has only the occluder.
   That single gap is exactly why maybe_Screen3D_Walk7Defer has no
   caller, and the two findings are one fact seen from opposite ends.

   It also says the nop kinds are a designed feature rather than
   leftovers. A renderer accumulating dead modes by accident does not
   accumulate them one per interpolant class in both policies.

51.3.  The most elaborate path in the renderer draws nothing

   Measuring what exists solely to service kind 29 [verified]:

   +------------------------------------+------------------+
   | Function                           | Bytes            |
   +====================================+==================+
   | maybe_Screen3D_SetupPrim4          | 1997             |
   +------------------------------------+------------------+
   | maybe_Screen3D_EmitTriGouraudPersp | 2424             |
   +------------------------------------+------------------+
   | maybe_Screen3D_Walk7Now            | 692              |
   +------------------------------------+------------------+
   | maybe_Screen3D_Walk7Defer          | 636, unreachable |
   +------------------------------------+------------------+
   | maybe_Screen3D_SpanNopK29          | 1                |
   +------------------------------------+------------------+
   | total                              | 5750             |
   +------------------------------------+------------------+

   5,750 bytes - the 19-argument emitter, four interpolants carried
   through near clipping and edge walking, and a perspective divide
   every sixteen pixels - to arrive at a single RET. For comparison the
   perspective fillers that DO draw, maybe_Screen3D_SpanTexHalfPersp and
   maybe_Screen3D_SpanStencilFlatPersp, are 465 and 472 bytes.

   This is the finding of section 45 at its extreme. There the template
   computed a shade gradient for a filler that ignored it; here an
   entire four-interpolant perspective pipeline runs for a filler that
   reads nothing at all. Section 45.3 listed three instances, all on the
   switch path. Kind 29 is the fourth and it is on the table path, which
   means the pattern is a property of the ENGINE and not of one dispatch
   route.

   o For the port: an occluder needs x and y. Whatever kind 29 occludes
     can be drawn by the same depth-only path as kind 3, and walkers 6
     and 7 need no Gouraud variant at all if their only Gouraud kind is
     a nop. That removes SetupPrim4, EmitTriGouraudPersp and both Walk7
     functions - about 5.7 KB of the most intricate code in the
     subsystem - for no visible change.

   o Verify against the shipped data first. If no track or object uses
     kind 29 the whole question is moot, and if something does, the
     occlusion still has to happen. That is the same open question
     section 43.2 raised for kind 4, and one pass over the mesh data
     would answer both.


52.  SetupPrim4, and three ways to make a flat colour

   maybe_Screen3D_SetupPrim4 at 0x004a2630 was read in section 20, which
   established it as the union of the two axes and measured its 19-dword
   emitter call. Nothing about the body is new. Two checks around it
   are.

52.1.  The setup table has one entrance each

   Every one of the five setups is referenced from exactly one address,
   and all five are in the walker table at 0x004f1ee0 [verified]:

   +------------+-------+------------+
   | Setup      | Bytes | Table slot |
   +============+=======+============+
   | SetupPrim0 | 922   | 0x004f1ee4 |
   +------------+-------+------------+
   | SetupPrim1 | 2103  | 0x004f1ef4 |
   +------------+-------+------------+
   | SetupPrim2 | 2127  | 0x004f1f04 |
   +------------+-------+------------+
   | SetupPrim3 | 2009  | 0x004f1f14 |
   +------------+-------+------------+
   | SetupPrim4 | 1997  | 0x004f1f24 |
   +------------+-------+------------+

   Stride 0x10, and the Walk pairs of section 51.1 sit at +0x08 and
   +0x0c of the same records. So a walker-table entry is { ?, setup,
   walkNow, walkDefer } and the whole table path is reached through it.
   There is no other way to call a setup.

   That closes the reachability argument section 51 started. SetupPrim4
   is selected only for walker 7, and walker 7 is selected only by kind
   29, whose filler is a bare RET. So all 1997 bytes of it - including
   four calls to maybe_Screen3D_ClipEdgeNear and the perspective-correct
   near clip that divides 1/z out, interpolates in z and re-multiplies -
   run exclusively in service of a primitive that paints nothing
   [verified].

   Section 20 called SetupPrim4 the fullest variant. It is also the
   least used: the most careful arithmetic in the renderer, reachable by
   one primitive kind, and that kind an occluder.

52.2.  The flat colour has three forms, not one

   Section 48.3 recorded a discrepancy between section 4's flat-colour
   expression and what Screen3D_DrawPrimK42 computes, and offered three
   explanations. The answer is the middle one - the layers really do
   differ - and reading all the producers turns up a third form nobody
   had noticed [verified]:

   +------------------------+---------------------------------------------------------------------+
   | Producer               | Expression                                                          |
   +========================+=====================================================================+
   | SetupPrim1, SetupPrim3 | Convert((c & 0xffc1) >> 1 | (c & 0x1f))                             |
   +------------------------+---------------------------------------------------------------------+
   | Screen3D_DrawPrimK42   | (Convert(c) & 0xffc1) >> 1 | (Convert(c) & 0x1f)                    |
   +------------------------+---------------------------------------------------------------------+
   | SetupPrim0             | (((Convert(c) & 0xffc3) >> 1 | Convert(c) & 0x1e) >> 1) & halveMask |
   +------------------------+---------------------------------------------------------------------+

   So section 4 is CORRECT for the setups it was derived from - the
   masking really is inside the conversion there, and the call site
   pushes an already-masked value. DrawPrimK42 applies the same masks to
   the RESULTS instead, and calls the conversion twice because this
   toolchain does not common up the calls.

   SetupPrim0 is a third thing again: different masks - 0xffc3 and 0x1e
   rather than 0xffc1 and 0x1f - and an extra halve through g_halveMask
   at the end. That is not a variant of the other two but a deliberate
   pre-halving, and it fits its consumer exactly. SetupPrim0 feeds the
   walker-2 blend path, whose filler computes

       *dst = ((*dst >> 1) & g_halveMask) + maybe_g_spanFlatColor;

   A colour added to a halved destination must itself be halved, or the
   sum overflows the channel. So the pre-halve is required by the blend,
   and the mask difference goes with it [inferred, and the arithmetic
   only works this way].

   o Whether the first two forms are equivalent is settled in section
     53: they are NOT. They disagree on exactly half of all possible
     inputs, and the difference is the low bit of green.

   Either way the port needs all three expressions written out
   separately. Collapsing them to one, which the earlier single formula
   invited, would change at least the blend path and possibly the
   stencil.


53.  Convert555ToSurface, and half the colours come out different

   Color_Convert555ToSurface at 0x00402020 is already documented - its
   plate comment gives the formula and docs/subsystems/pixel-format.txt
   covers it. The body [verified]:

       ushort Convert555ToSurface(ushort src)
           return ((src & 0x3e0)  >> 5)  << (bitsG + shlG - 5) & maskG
                | ((src & 0x7c00) >> 10) << (bitsR + shlR - 5) & maskR
                | ( src & 0x1f)          << (bitsB + shlB - 5) & maskB;

   Source is TRUE RGB555 - red at bit 10, green at bit 5 - which is not
   the framebuffer layout. The destination is entirely derived from the
   DirectDraw globals, so the function needs no change for a wider
   format. What it is read for here is the residual left open in section
   52.2.

53.1.  The two flat-colour forms are not equivalent

   Section 52.2 found that the Setup layer masks the SOURCE and
   Screen3D_DrawPrimK42 masks the RESULT, and could not say whether the
   two agree. Evaluating both over every possible input settles it
   [verified]:

       A = Convert((c & 0xffc1) >> 1 | (c & 0x1f))      /* setups */
       B = (Convert(c) & 0xffc1) >> 1 | (Convert(c) & 0x1f)

   +--------+--------+--------+-------+
   | src555 | A      | B      | equal |
   +========+========+========+=======+
   | 0x0020 | 0x0000 | 0x0020 | no    |
   +--------+--------+--------+-------+
   | 0x0400 | 0x0400 | 0x0400 | yes   |
   +--------+--------+--------+-------+
   | 0x03e0 | 0x03c0 | 0x03e0 | no    |
   +--------+--------+--------+-------+
   | 0x7fff | 0x7fdf | 0x7fff | no    |
   +--------+--------+--------+-------+
   | 0x5ad6 | 0x5ad6 | 0x5ad6 | yes   |
   +--------+--------+--------+-------+

   They differ on 16384 of the 32768 possible 555 values - exactly half,
   and exactly those whose green is odd.

53.2.  Why it is green, and why exactly half

   The mask 0xffc1 clears bits 1 to 5. Which bit that destroys depends
   entirely on which layout it is applied to [verified]:

   +------------------------+-----------------+---------------------+
   | Applied to             | Bit 5 is        | Effect              |
   +========================+=================+=====================+
   | the 555 SOURCE, form A | green's low bit | green's LSB is lost |
   +------------------------+-----------------+---------------------+
   | the 565 RESULT, form B | always zero     | nothing is lost     |
   +------------------------+-----------------+---------------------+

   In the destination format green occupies bits 5 to 10, but a five-bit
   source is shifted by bitsG + shlG - 5 = 6, so the converted value
   never sets bit 5 at all. The mask therefore clears a bit that is
   already clear, and form B loses nothing. Form A applies the same mask
   one step earlier, where bit 5 is carrying data.

   So the setups produce a flat colour one green step darker than the
   stencil path produces from the same face colour, for every face whose
   green is odd.

53.3.  What to do with it

   o Neither form is obviously the intended one, and the mask itself is
     odd in both. A halve that avoided channel bleed would clear the low
     bit of EACH field - bits 0, 5 and 10 in 555, or bits 0, 5 and 11 in
     565, which is what maybe_Color_BuildHalveMask actually computes.
     0xffc1 clears a contiguous run instead, halving red and green while
     leaving blue untouched. Deliberate or not, it is not the same
     operation as g_halveMask.

   o The reconstruction must keep all three expressions of section 52.2
     separate and must not normalise them. Two of them are now known to
     disagree on half their inputs, so collapsing them would visibly
     change flat-shaded and stencil geometry against each other.

   o Whether the disagreement is a BUG is not answerable from the
     binary. It would need the original intent, and the difference is
     one step in a five-bit green - small enough to have survived
     unnoticed either way. Recorded, not judged.

   One incidental fact from the plate comment: Menu_Convert555ToSurface
   at 0x0043e1c0 is a second copy of this function in menu\bitmap.cpp -
   the same copy-rather-than-share habit sections 44 and 50 found in the
   rasterizer, here across translation units rather than within one. The
   comment calls it byte-for-byte identical; section 54 checks that and
   it is not.


54.  The menu's copy, and a claim that was not checked

   Color_Convert555ToSurface's plate comment describes
   Menu_Convert555ToSurface at 0x0043e1c0 as a byte-for-byte duplicate.
   Section 53 repeated that. Both are wrong [verified]:

   +-----------------+------------+------------+
   |                 | Color_     | Menu_      |
   +=================+============+============+
   | address         | 0x00402020 | 0x0043e1c0 |
   +-----------------+------------+------------+
   | length          | 131 bytes  | 131 bytes  |
   +-----------------+------------+------------+
   | differing bytes | -          | 51 of 131  |
   +-----------------+------------+------------+

   Same length, and about 40 percent of the bytes differ. The first
   divergence is at +0x23, where one function has opcode 0x81 and the
   other 0x83 - AND with a 32-bit immediate against AND with a sign-
   extended 8-bit one. That changes the instruction length, everything
   after it shifts, and the two happen to end at the same total size.

54.1.  What is actually true

   They are semantically identical and reference exactly the same
   globals - all nine of the DirectDraw-derived format values, with no
   address in one that is not in the other [verified]. The only
   difference in the decompiled form is the order the three terms are
   combined:

       Color_Convert555ToSurface:   green | red   | blue
       Menu_Convert555ToSurface:    green | blue  | red

   OR is commutative, so the result is the same for every input. The
   compiler simply scheduled the three channel computations differently
   in the two translation units, which changed register assignment and
   immediate encodings throughout.

54.2.  The part that matters for the port

   The reason to check at all was not the duplication. It was whether
   menu\bitmap.cpp keeps its own pixel-format state. It does not
   [verified]:

   +---------------------------+----------------+--------------+
   | Global                    | Address        | Used by both |
   +===========================+================+==============+
   | g_bitsR, g_bitsG, g_bitsB | 0x004ee9ac..b4 | yes          |
   +---------------------------+----------------+--------------+
   | g_shlR, g_shlG, g_shlB    | 0x004ee9c4..cc | yes          |
   +---------------------------+----------------+--------------+
   | g_maskR, g_maskG, g_maskB | 0x004ee9d0..d8 | yes          |
   +---------------------------+----------------+--------------+

   So there is one set of format globals for the whole program, written
   once by Cdd_InitCapsVariables and read by the rasterizer and the menu
   alike. A port that widens the destination format has one place to
   change, not two, and the menu bitmap path needs no separate
   treatment.

54.3.  Twice now

   This is the second time a claim has travelled from a plate comment
   into this document without being checked. The first was the literal
   argument in section 4's step 2, which came from a decompilation with
   no calling convention and was corrected in section 47.1. This one
   came from a comment that said byte-for-byte where it meant
   equivalent.

   Neither claim was harmful and both were right in substance. The
   pattern is worth naming anyway, because CLAUDE.md's rule to search
   the Ghidra comments before naming anything makes those comments load-
   bearing, and load-bearing text attracts reuse:

   o A plate comment is a LEAD, at the confidence its own tag claims.
     Comments in this database are not uniformly tagged, and an untagged
     assertion is not evidence. Verifying 'byte-for-byte' took one
     memcmp; verifying the argument took one look at RET imm.

   o Precise-sounding words deserve the most suspicion. 'Byte-for-byte'
     and 'always returns 1' are checkable in seconds and are exactly the
     phrasings that get repeated verbatim.


55.  A caller that forces the immediate clear

   Section 39.2 found that Screen3D_Clear has two implementations and
   picks between them on g_spanBufferEnabled: with the span buffer on it
   records a colour for Screen3D_EndFrame to paint into the uncovered
   remainder, and with it off it performs a full-surface Cdd_Clear
   immediately.

   FUN_004121e0, which maybe_Game_Tick calls once per frame, is the
   first observed caller that deliberately selects the second
   [verified]:

       if (g_ddReleaseLockEarly && !g_frameLockValid) {
           didLock = 1;
           Screen3D_BeginFrame(1, 0);      /* lock only */
       }
       saved = g_spanBufferEnabled;
       g_spanBufferEnabled = 0;            /* force immediate */
       Screen3D_Clear(Color_Pack888ToSurface(r, g, b));
       g_spanBufferEnabled = saved;
       if (didLock) Screen3D_EndFrame(1, 0);

   So g_spanBufferEnabled is not only a mode set at startup. A caller
   can toggle it around a single operation to change which
   implementation that operation uses, and this one does exactly that to
   get a real clear rather than a deferred one.

   It makes sense for the job. The function is painting a background
   before any geometry exists, so there is no free list worth consulting
   and nothing for a deferred fill to be deferred behind. Recording a
   colour and waiting for EndFrame would work, but only if a frame were
   being composed, and this runs outside that.

   o It also reuses the lock-only mode of Screen3D_BeginFrame(1, 0) that
     section 40.1 found in maybe_Screen3D_FadeRect, and for the same
     reason - it needs a surface pointer without disturbing span state.
     Two independent callers now use that parameter split, so it is a
     real interface rather than an accident.

   o For the port: g_spanBufferEnabled has to remain a variable that
     callers may set, not a compile-time choice between two renderers.
     Two functions depend on toggling it mid-frame.

   The colour comes from Color_Pack888ToSurface, a sibling of
   Color_Convert555ToSurface taking three separate byte components. It
   is a second entry point into the same format-agnostic packing
   machinery and has not been read; noted for pixel-format.txt.


50.  Three submitters, not one

   Section 13 and the plate comment on Screen3D_CullAndQueueFaces treat
   that function as THE stage between the transform and the queue. It
   is one of three. All three share a single body - same near-plane
   rejection, same guard-band counters, same choice between a
   camera-space scalar triple product and a screen-space 2D cross
   product, same 1.0f minimum-area test, same hwFlags bits 0 and 1 -
   and differ only in how they compute the depth key and what they do
   to the primitive on the way out [verified]:

   +--------------------------------+---------+------------------------+
   | Function                       | Callers | Depth key              |
   +================================+=========+========================+
   | Screen3D_CullAndQueueFaces     |    6    | farthest camZ; splits  |
   | 0x0049c110                     |         | paletted vs plain      |
   +--------------------------------+---------+------------------------+
   | Screen3D_CullAndQueueFacesEx   |   12    | nearest OR farthest by |
   | 0x0049b7f0                     |         | argument, +1024.0 when |
   |                                |         | flags bit 1 is set;    |
   |                                |         | never paletted         |
   +--------------------------------+---------+------------------------+
   | Screen3D_CullAndQueueTranslu-  |    1    | farthest * 0.2 minus   |
   | cent  0x0049bca0               |         | nearPlaneZ; rewrites   |
   |                                |         | the kind               |
   +--------------------------------+---------+------------------------+

50.1.  Ex owns the depth bias

   Screen3D_CullAndQueueFacesEx is the busier of the two general
   submitters - racers, three animDecor functions, and the boot-region
   drawers. Its fourth argument selects whether the face sorts by its
   NEAREST corner (0) or its FARTHEST (non-zero), and that same vertex
   is the near-plane test subject.

   It is also the ONLY reader of MR_Primitive flags bit 1 anywhere in
   the image:

       depth = (flags & 2) ? chosen->camZ + 1024.0f : chosen->camZ;

   which closes the loop opened in structs/MR_Primitive.txt section 7.1
   and formats/mesh-3df-map.txt: the .map 0x400000 bit sets flags bit
   1, and this is the one function that acts on it.

   Its kind-0x0d skip is unconditional, where Screen3D_CullAndQueue-
   Faces skips 0x0d only when flags bit 0 is also set.

50.2.  Translucent is the first-person cockpit

   Screen3D_CullAndQueueTranslucent rewrites the primitive immediately
   before queueing, which nothing else in the pipeline does:

       if (kind != 0)
           kind = (kind == 1 || kind == 0x10) ? 0x10 : 0x2c;
       depth = farthest->camZ * 0.2f - nearPlaneZ;

   0x10 and 0x2c are both bit-4 blended kinds - detail-levels.txt
   section 2.6 - so whatever the mesh authored, it draws 50/50
   translucent. The depth key at a fifth of true depth, minus the near
   plane, lands it in the lowest sort buckets so it paints in front of
   the world instead of sorting against it.

   Its single caller, FUN_00462110, feeds it exactly two meshes:
   g_meshGuidon and g_meshCockpit. It is the first-person handlebars
   and dashboard.

   o FOR THE PORT: reproduce this as a separate overlay pass with
     blending forced on and depth testing off. A real depth buffer
     cannot express "z times 0.2" as a bias, and the same objection
     applies to the +1024.0 of section 50.1. Both are sort-key tricks

50.3.  The projection, in closed form

   The small screen3d accessors that looked like noise are the
   projection state [verified]:

       g_projScaleX = g_projBaseX * g_projZoom      0x006d20c4
       g_projScaleY = g_projBaseY * g_projZoom      0x006d104c

       Screen3D_SetProjBaseX  0x0049a0e0    g_projBaseX  0x006d20cc
       Screen3D_SetProjBaseY  0x0049a100    g_projBaseY  0x00709360
       Screen3D_SetProjZoom   0x0049a120    g_projZoom   0x006d1f74
       Screen3D_GetProjZoom   0x0049a150

   Only the two products are read by the transform. The bases and the
   zoom exist so either factor can change alone, which is why the zoom
   setter recomputes both axes and each base setter recomputes only its
   own. All three are initialised in Screen3D_Open; g_projZoom is also
   read by FUN_0046e320, which is where a field-of-view or camera
   effect would drive it [inferred - only the read is verified].

   Screen3D_ProjectVertex at 0x0049b230 is the scalar form of the loop
   inside Screen3D_TransformVertsFlat, and the clearest single
   statement of the projection in the binary:

       v->invZ = 1.0f / v->camZ;
       if (v->camZ >= nearPlaneZ) {
           v->screenX = round(centreX + v->camX * g_projScaleX * v->invZ);
           v->screenY = round(centreY - v->camY * g_projScaleY * v->invZ);
       }

   o THE Y AXIS IS NEGATED at projection time.

   o THE SCREEN COORDINATES ARE ROUNDED TO INTEGERS and stored back as
     floats. Sub-pixel position is discarded here, before any
     rasterizer sees it, so BOTH back ends draw on integer vertices.
     A D3D9 rewrite that keeps sub-pixel precision will not match the
     original's pixel coverage. That is probably the right choice, but
     it is a choice.

   o It writes invZ unconditionally and the screen coordinates only for
     a vertex in front of the near plane. A vertex behind the plane
     keeps whatever screen position it had, so the caller must have
     rejected or clipped it - which is exactly what section 50's
     submitters do.

   Screen3D_GetViewportRows at 0x0049a010 is the other accessor worth a
   name: it returns top, centre and bottom rows plus a clip row, adding
   g_viewLetterboxSkip only when the game owns the display mode, is in
   widescreen, and is on an enumerated device. It is the read side of
   section 11.1.
