MotoRacer PC Reverse Engineering                           Analysis Note


                                MR_MENU


Abstract

   Size: 0xd4c [verified] - PUSH 0xd4c into operator new at 0x004730d7,
   immediately before the constructor call and the store to the global.

   Allocated at: 0x004730d7, in FUN_00472c40 (startup). Freed at:
   0x00473661, in FUN_00473540, which then clears the global. Global
   pointer: 0x004dc0c4, zero in the image. Ghidra type applied: yes.
   Belongs to: menu/menu.cpp.

   The one and only menu instance. It holds the current page index, the
   cursor and keyboard state the pages react to, a fixed array of 32
   buttons that each page rebuilds on entry, and the timing for the 1200
   ms page transition. Every one of the 68 page handlers in
   subsystems/menu-pages.txt reaches it through the global.

   needsRedraw is the gate on the whole draw pass: Menu_Draw wraps its
   entire per-button loop in a test of it, so when it is clear the menu
   simply is not repainted. Four methods set it and Menu_Draw is the
   only reader.

2.  Relationships

   o Pointed to by: the global at 0x004dc0c4, and nothing else. There is
     exactly one instance.
   o Contains: MR_MenuButton[32] inline at +0x44. See
     structs/MR_MenuButton.txt.
   o Indexes: g_menuPageTable at 0x004dbb38 through pageIndex. See
     subsystems/menu-pages.txt.
   o Does NOT own the menu sprites. Those live in g_menuObjects at
     0x00504880, indexed by resource id. See subsystems/menu-
     resources.txt.

4.  What bounds the layout

   Three independent facts pin the structure, which is why the size can
   be called verified rather than reconstructed [verified]:

   o The allocation is a literal 0xd4c.
   o The button stride is 0x58, appearing identically in
     Menu_AddTextButton and Menu_AddSpriteButton, and the count is 32
     from both the MAX_BUTTON assert and the constructor's 32-iteration
     loop. 0x44 + 32 * 0x58 = 0xb44.
   o Menu_Tick writes field_b44 and transitionActive at exactly 0xb44
     and 0xd48, the first slot after the array and the last slot before
     the end of the allocation. They agree with the arithmetic without
     being derived from it.

   A census of all seventeen methods found 34 distinct field offsets and
   no access that falls outside the layout above, so the structure is
   complete in the sense that nothing observed contradicts it.

5.  Open questions

   o The 512 bytes at 0xb48 are the largest gap. A scan of all 198860
     game-code instructions found no constant displacement in
     0xb48..0xd47 on any register. The three candidates that first
     appeared were false positives: 0xbb8 is the immediate value 3000
     stored to unrelated globals, and 0xc6c and 0xc84 belong to a
     different object in FUN_00405bc0. So the region is either dead
     space or is reached through a pointer computed elsewhere.

   o field_38 is never touched at all. Together with the 512-byte gap
     that is 516 of 3404 bytes, about 15 percent, with no observed use.

   o field_28 and field_b44 are both cleared by Menu_Tick on page entry
     and never read by any of the seventeen methods. Their readers, if
     any, are elsewhere.

   o field_28 and field_b44 remain the only header fields that are
     written and never read. Both are cleared by Menu_Tick on page
     entry.

   o ANSWERED. Menu_OnKey's eleven switch cases and the nine constant
     keyCode values buttons register are all Windows virtual-key codes,
     now the MR_MenuKey enum. See structs/MR_MenuButton.txt sections 3
     and 4.
