MotoRacer PC Reverse Engineering                           Analysis Note


                  THE RACER DRAW PARITY AUDIT


Abstract

   Every function behind "racer draw + shadow + LOD + segment list",
   what it was imported from, and whether it can be VERIFIED rather
   than argued about.

   THE CALL GRAPH MATCHES RETAIL AND THE GEOMETRY DOES NOT. Those are
   different claims and this project has conflated them: the wheels
   and the rider are visibly mispositioned while every function sits
   where the original puts it. Structure was the last job; values are
   this one.

   WHAT MAKES THIS DIFFERENT FROM EVERY EARLIER ATTEMPT is that a
   function can now be answered instead of eyeballed. MR_Racer carries
   the original layout for its whole 0x3209 prefix, and HOOK_FUNC runs
   our C inside MOTO in place of theirs, so the question is "given
   these bytes in, do we produce the same bytes out" - settled by a
   diff. See whole-function-import.txt 6.1.

1.  The split that decides the method

   A function can be hooked only if the original has its own ENTRY
   POINT. Most of racerdraw.c does not: it is maybe_Racer_Draw cut on
   its own seams, and a seam has no address to jump to.

   +----------------------------+-------+---------------------------+
   | kind                       | count | how it gets verified      |
   +============================+=======+===========================+
   | standalone original        |     9 | HOOK_FUNC, byte-diff      |
   +----------------------------+-------+---------------------------+
   | block inside another       |    22 | trace hook on the block,  |
   | function                   |       | feed ours the same inputs |
   +----------------------------+-------+---------------------------+
   | ours, no original          |     3 | by the callers only       |
   +----------------------------+-------+---------------------------+

3.  Blocks inside maybe_Racer_Draw - no entry point of their own

   Twenty-two functions, every one tagged "@ 0x0045f290, at ...". They
   cannot be hooked because the address in the tag is a SEAM, not a
   call target. They are verified by hooking the enclosing function
   and comparing what it produces, or by a trace hook on the block
   that captures the stack slots either side of it.

   Grouped by what they position, because that is how the symptom
   presents:

   THE BIKE BODY   build_matrices, rebuild_contacts, offsets,
                   draw_position, view_matrix
   THE FORK        fork_solve, fork_scale, fork_tip,
                   fork_part_matrix, front_wheel_offset, steer_pose
   THE SWINGARM    rear_frame, arm_angle, arm_matrix,
                   rear_wheel_offset
   THE RIDER       place_rider, part_is_rider, part_matrix
   THE FAR LOD     far_lod, far_shade
   THE QUEUE       queue_parts (uncalled), shading_enabled (uncalled)

4.  Ours, with no original at all

   racerdraw_bind_skeleton   the MR_Skeleton to MR_RacerPart bridge.
                             The original needs none: it keeps the
                             pose in the racer and fills it in the

   racerdraw_part_walks      SEE SECTION 5. This one is the problem.

5.  The gap that explains the symptom

   Skl_BuildPartMatrices (0x00463d90) WAS NEVER IMPORTED.

   It is a standalone function - 261 instructions, five basic blocks,
   thirteen parameters because the 3x4 matrix goes BY VALUE, calling
   Matrix34_Copy, maybe_Mat34_FromEuler, Vec3_Set,
   Vec3_TransformByMatrix34, Matrix34_Identity and FUN_00464190. It is
   what walks the part tree and writes every part matrix.

   WE WROTE rd_walk INSTEAD. Its ORIGIN tag names
   "maybe_Racer_Draw @ 0x0045f290, at 0x00460f00..0x00460f70", which
   is the CALL SITE - the two lines that invoke the walk, not the walk.
   racerdraw_part_walks, the function that drives it, carries NO ORIGIN
   TAG AT ALL. The composition rule came from skl.c, chosen because it
   reproduced the game stored matrices to 0.0004 in a capture.

   THE FILE ALREADY NAMES THE DOUBT, in racerdraw.c above rd_walk:

       "The decompilation of Skl_BuildPartMatrices appears to INVERT
        the incoming matrix before composing - the transpose and
        -R^T t are both visible ... IF A CAPTURE EVER DISAGREES, the
        inverse is the first thing to try."  [open]

   THAT OPEN QUESTION POSITIONS THE RIDER AND EVERY BIKE PART, and the
   rider and the wheels are exactly what is mispositioned. It is not
   proof, but it is the first place to look and it is now answerable
   rather than arguable.

6.  Order of work

   STATUS, and section 12.1 is the evidence: step 1 is DONE and
   verified - parts 0..3 and 15 are exact. Steps 2..4 are IMPORTED
   but NOT YET DIFFED against MOTO. Step 5 has a floor that has
   stopped moving for the frame, fork and swingarm, so it can start.

   1  IMPORT Skl_BuildPartMatrices WHOLE, hook it at 0x00463d90 and
      diff the twenty part matrices at racer+0x63c+(slot*20+part)*100
      +0x18, forty-eight bytes each. It is standalone, it writes into
      the byte-exact pose array, and it decides the thing that looks
      wrong. Everything else in section 3 reads what it produces, so
      auditing them first would be measuring against a moving floor.

   2  maybe_Inst_DrawWithMatrix (0x0048c6d0) - the wheels, and the
      other half of the visible symptom.

   3  maybe_Racer_BuildShadow (0x00461aa0) - six vertices into the
      racer, the cleanest byte-diff of the set.

   4  maybe_Racer_SelectLod, then the cull - both small, both write
      one or two fields.

   5  Only then the blocks in section 3, top down, each against a
      floor that has stopped moving.

   DO NOT AUDIT IN FILE ORDER. The blocks consume each other: offsets
   feeds draw_position feeds view_matrix feeds the part loop. Verify
   producers before consumers or every reading is contaminated by the
   one above it - which is the mistake that made the piecemeal import
   unfalsifiable in the first place.

7.  First measurement - the pose array, MOTO against ours

   Both games placed at (-128, 0, 2058) yaw 0 with mr_place --to both,
   stepped two frames, then all seventeen 100-byte part records read
   from each and compared field by field. THE POINT IS TO SEPARATE
   INPUTS FROM OUTPUTS: comparing a matrix means nothing if the angles
   feeding it already differ.

   +--------------------------+------------------------------------+
   | field                    | result                             |
   +==========================+====================================+
   | tree: next/parent/child  | IDENTICAL, all 17, including part  |
   |                          | 3 severed as its own root          |
   +--------------------------+------------------------------------+
   | pivot, firstVertex,      | IDENTICAL, all 17                  |
   | vertexCount              |                                    |
   +--------------------------+------------------------------------+
   | angle, BIKE parts        | IDENTICAL - 0, 1, 2, 15, 16        |
   +--------------------------+------------------------------------+
   | angle, RIDER parts       | DIFFER - 4..14, by up to 1.5 rad   |
   +--------------------------+------------------------------------+

   So racerdraw_bind_skeleton is CORRECT: the tree it builds, the
   pivots it copies and the severing of part 3 all match the original
   exactly.

   MAX ABSOLUTE MATRIX ELEMENT DIFFERENCE, by part:

       0, 1, 2      0.010 .. 0.018      the walk, inputs identical
       15           0.896               the fork override
       16           10.58               the rear wheel
       4 .. 14      21 .. 77            rider, fed wrong angles

   THE INVERSE FIX WORKED. Parts 0, 1 and 2 are pure output of
   skl_build_part_matrices with identical inputs and an identical
   tree, and they now agree to about 0.018 on elements of order 5.
   That residue is most likely the cosine table index: a turn is
   0x4000 entries, so one step is 3.8e-4 rad, and against a pivot of
   27 units that is about 0.01 - the magnitude observed. [inferred]

   THE RIDER IS NOT A WALK PROBLEM. Twelve of seventeen parts are fed
   angles that differ before the walk runs, so their matrices cannot
   agree whatever the composition rule is. That is racer_build_pose
   and the .ROT blend, upstream of everything audited here.

   NEXT, in producer-before-consumer order:

     1  the rider pose angles - 12 of 17 parts, and the largest
        single source of wrong geometry
     2  part 16, the rear wheel - 10.58 with correct inputs
     3  part 15, the fork override - 0.896
     4  the cosine table residue, once the rest is exact

8.  The rider angles are not a pose bug

   THE BLENDER IS CORRECT. anim_blend_angle_frames matches
   Anim_BlendAngleFrames (0x0045b4e0) in every respect: the
   shortest-arc wrap, the [0, 2pi] normalisation, min(count), and both
   self-copy guards. The only difference is that ours works in double
   where the original works in float. [verified]

   ITS INPUTS DIFFER INSTEAD. Same placement, same input, two frames:

       speed        MOTO 0.989   ours 1.898
       engineSpeed  MOTO 0.3     ours 0.0
       suspAngle    MOTO -0.0112 ours 0.0423
       lean         both -0.0000

   AND SPEED PICKS THE POSE WEIGHT DIRECTLY. Below the 20/3.6 gate the
   base stance blends staticPied to staticHaut with w = speed * 0.18:

       w(MOTO 0.989) = 0.178
       w(ours 1.898) = 0.342

   Nearly double, on a blend between feet-down and feet-up - a large
   postural change that moves every rider joint. So the rider is
   posed correctly from the wrong number.

   THE WORK IS IN THE DRIVETRAIN, NOT THE DRAW. Auditing the pose
   sequence now would measure it against a moving floor, which is the
   mistake section 6 exists to prevent.

   NOT ESTABLISHED: whether speed accounts for ALL of the angle
   difference. The 1.5 rad deltas in section 7 were measured at a
   different spot from these numbers, so the two are not directly
   comparable. Re-measure the pose once speed agrees. [open]

9.  The speed divergence - a launch hold we do not have

   tools/check_physics.py passes with 0 failures, so the individual
   formulas are right. The divergence is in SEQUENCING.

   Placed identically, stepped one frame at a time:

   +-------+---------------------+---------------------+
   | frame | MOTO speed / engine | ours speed / engine |
   +=======+=====================+=====================+
   | 0     | 0.000  /  0.3       | 0.000  /  0.0       |
   +-------+---------------------+---------------------+
   | 1     | 0.000  /  0.6       | 0.990  /  0.0       |
   +-------+---------------------+---------------------+
   | 2     | 0.000  /  0.9       | 1.898  /  0.0       |
   +-------+---------------------+---------------------+
   | 3     | 0.000  /  1.2       | 2.392  /  0.0       |
   +-------+---------------------+---------------------+
   | 4     | 0.000  /  0.0       | 2.909  /  0.0       |
   +-------+---------------------+---------------------+
   | 5     | 1.898  /  0.7       | 3.453  /  0.0       |
   +-------+---------------------+---------------------+

   THAT FOUR-FRAME HOLD DID NOT REPRODUCE and the reading above is
   retracted. A second run from a fresh reset had MOTO moving on frame
   1 like ours. The hold was leftover state from the experiment before
   it - MOTO had been left mid-shift - not a systematic difference.

   THE LESSON IS THE MEASUREMENT, NOT THE ENGINE. A single run off an
   unknown starting state is an anecdote. Reset both sides and repeat
   before recording anything as a property of the game; this section
   nearly sent the next session after a launch limiter that was never
   missing.

   THE REAL DIVERGENCE, from the repeated run, is the ENGINE:

   +-------+---------------------+---------------------+
   | frame | MOTO speed / engine | ours speed / engine |
   +=======+=====================+=====================+
   | 0     | 0.000  /  0.7       | 0.000  /  0.0       |
   +-------+---------------------+---------------------+
   | 1     | 1.898  /  0.7       | 0.990  /  0.4       |
   +-------+---------------------+---------------------+
   | 3     | 4.022  /  1.5       | 2.391  /  0.9       |
   +-------+---------------------+---------------------+
   | 5     | 6.591  /  2.5       | 3.452  /  1.3       |
   +-------+---------------------+---------------------+

   MOTO SITS AT 0.7 FROM FRAME 0 AND WE START AT ZERO. 0.7 is exactly
   the idle floor 9.32.1 documents - moteurVitesseMax / regimeMax *
   1200 for the road bike - so the original has the engine idling
   before the throttle does anything, and we do not.

   OUR ENGINE THEN STAYS ABOUT HALF THEIRS all the way out, and road
   speed follows it: our per-frame gain settles near 0.5 where theirs
   climbs 1.0 to 1.35. Torque is a function of engine speed, so one
   explains the other.

   THE FLOOR IS INSIDE physics_tick_drivetrain, which race.c calls
   ONLY on the throttle branch (dm.num > 0). Whatever keeps MOTO at
   0.7 with the bike stationary is therefore somewhere we do not run.
   That is the next thing to read. [open]

9.1.  And racer+0x00ec was never written

   engineSpeed lived only in s_race_drive; the racer field stayed 0
   for the entire race. FIXED - race.c now mirrors it beside r->speed.

   THE BYTE-EXACT STRUCT IS ONLY WORTH ANYTHING IF IT IS CURRENT. A
   field kept in a static instead reads 0 to every comparison and to
   every imported function that expects it at its offset. Here it
   looked like a dead engine next to MOTO 0.7 idle - a false lead
   manufactured by the very struct meant to prevent them. Check for
   others before trusting a zero.

10.  The speed divergence was the harness, not the physics

   Measured from a genuine standing start, both bikes aligned down the
   track, reading the port real state rather than its mirrors:

   +-------+---------------------+---------------------+
   | frame | MOTO speed / engine | ours speed / engine |
   +=======+=====================+=====================+
   | 1     | 1.8976 / 0.73       | 0.9897 / 0.38       |
   +-------+---------------------+---------------------+
   | 2     | 2.9092 / 1.11       | 1.8977 / 0.73       |
   +-------+---------------------+---------------------+
   | 3     | 4.0218 / 1.54       | 2.3915 / 0.91       |
   +-------+---------------------+---------------------+
   | 4     | 5.2454 / 2.01       | 2.9094 / 1.11       |
   +-------+---------------------+---------------------+
   | 6     | 8.0695 / 3.09       | 4.0221 / 1.54       |
   +-------+---------------------+---------------------+

   OURS AT FRAME 2N IS MOTO AT FRAME N, to about 1e-4, on speed AND
   engine. The gains sum too: MOTO frame-2 gain 1.0116 against our
   frames 3 and 4, 0.4938 + 0.5179 = 1.0117.

   SO THE DRIVETRAIN IS RIGHT. One SEND_INPUT frame is not the same
   quantity of simulation on the two sides - mr_ab.py header says so
   outright - and every "half acceleration" reading in this
   investigation was that, not physics.

10.1.  Four harness faults that produced false readings

   Each of these produced a confident, wrong conclusion first.

   o mr_ab DEFAULT SPOT POINTS BOTH BIKES ACROSS THE TRACK. It is
     built on mr_place, which is documented as "place the bike for a
     repeatable impact test". Every speed number taken through it is a
     wall-scrape measurement.

   o mr_place --to both DOES NOT RELIABLY PLACE THE PORT. Observed 675
     units out in one run and 97 in another, while reporting success.
     Direct SET_MEM works; verify the two positions before believing
     any comparison.

   o PLACING STRAIGHT AFTER mr_reset IS CLOBBERED. The restart
     re-places racers on a later tick.

   o THE PORT DRIVETRAIN STATE IS NOT IN THE RACER. speed,
     gearboxRoadSpeed and engineSpeed live in the static s_race_drive
     (0x00643270); the racer fields are mirrors written at the END of
     the tick. READS are a frame stale at worst; WRITES ARE SILENTLY
     DISCARDED. Zeroing racer+0x124 to get a standing start does
     nothing - the port kept 18 m/s and looked like it was jumping to
     the gear top in one frame.

   THE BYTE-EXACT STRUCT IS ONLY AS GOOD AS WHAT ACTUALLY LIVES IN IT.
   Three of the fields an A/B most wants to set are copies. Fixing that
   - making s_race_drive the mirror and the racer the state - would
   remove a whole class of false reading. [open]

11.  The geometry divergence is suspensionAngle

   Measured with both games at a VERIFIED identical standing start -
   same position, same orientation, same speed, confirmed before
   reading anything.

   CLEARED, all with identical values:

       racerdraw_bind_skeleton    tree, pivots, severing
       anim_blend_angle_frames    matches 0x0045b4e0 in every respect
       racer_build_pose           angles agree, modulo 2pi
       mat34_from_euler           reproduces the original truncation
       racerdraw_build_matrices   every input matches

   THE ONE INPUT THAT DIFFERS:

       suspensionAngle   racer+0x2e8d   MOTO 0.0000   ours -0.0809

   AND 0.0809 IS THE WHOLE GEOMETRY ERROR. bodyMat is matBikeRoot with
   the suspension pitch folded in; the walk takes bodyMat as its root;
   every part inherits it. Parts 0 to 4 are out by 0.08 - the pitch -
   and the rider chain amplifies that to 20..79 five levels down.

   MOTO READS EXACTLY ZERO with the bike stationary on flat ground,
   which is what a suspension at rest should be. Ours does not.

   NEXT: whatever writes racer+0x2e8d. It is upstream of the draw
   entirely, so nothing in section 3 can be judged until it agrees.
   [open]

11.1.  On the 2pi angles, which are NOT the cause

   Our pose angles land on 2pi where MOTO lands on 0. Tested directly:

       0     -> raw 0.0        -> index 0
       2pi   -> raw 16383.9999 -> index 16383
       pi/2  -> raw  4095.9999 -> index 4095

   So 2pi is NOT equivalent to 0 - it is one table step short. But
   MOTO truncates identically with its own constant at 0x004d0ed0, so
   this is faithful, and one step is 0.000383 rad - three orders below
   the observed error. Ruled out, and written down so it is not
   re-investigated.

12.  suspensionAngle was a startup transient, and what it was hiding

   THE CHAIN, traced end to end: geometry error <- bodyMat <-
   suspensionAngle -0.0809 <- headingSmoothed 6.2023 where MOTO has 0.

   6.2023 IS 2pi - 0.0809, so ours is genuinely 0.0809 behind the

13.1.  The residual is a 2pi that costs one table index

   OUR ANGLES ARE MOTO PLUS EXACTLY 2PI on parts 2, 3, 4, 6, 7, 8, 9,
   11, 12 and 13 - the angle column reads 6.28319, not a fraction of
   it. That is normally harmless, because

       index = (int)(a * 2607.5945876) & 0x3fff

   shifts by exactly 0x4000 and masks back. IT IS NOT HARMLESS FOR A
   NEGATIVE ANGLE. (int) truncates toward zero, so a*K rounds UP while
   (a + 2pi)*K rounds DOWN, and the two land one index apart:

   +------+-----------+--------+------------+----------+
   | part |  MOTO deg | idx(a) | idx(a+2pi) |   d cos  |
   +======+===========+========+============+==========+

   +------+-----------+--------+------------+----------+

   +------+-----------+--------+------------+----------+

21.1.  What the rear-wheel block actually computes

   0x004604c0..0x00460da0 is not one output but at least two, and the
   second is a 3x4 BY 3x4 MATRIX MULTIPLY written out inline - eight
   FLD/FMUL/FADDP groups of the same shape, one per output element:

       004605b6  FLD [ESI+0x6c] / FMUL [ESP+0x58]
       004605bd  FLD [ESI+0x84] / FMUL [ESP+0x60]
       004605c7  FLD [ESI+0x78] / FMUL [ESP+0x5c]
       004605d4  FSTP [ESP+0x2c]

   so  [ESP+0x10 .. 0x3c]  =  [ESP+0x58]  x  [ESI+0x68]

   with the translation rows added separately - FADD [ESI+0x8c] at
   0x00460618 and FADD [ESI+0x94] at 0x00460668.

   ESI IS THE CAMERA AND IT IS A PARAMETER. MOV ESI,[ESP+0x42c] at
   0x0045f9cb, held across the whole block. The struct carries a 3x4
   at +0x68 with its translation at +0x8c..+0x94, so the original
   passes ONE camera object where the port passes camEye and camView
   separately.

   The result is copied ESP+0x10 -> ESP+0xac -> ESP+0x238, and
   ESP+0x238 is what member 3 reads. See 20.2.

21.2.  Why this is not a one-sitting import

   The block is 2272 bytes of x87 with no calls to lean on - the
   matrix products are inlined rather than going through
   Matrix34_Multiply, so there is no call graph to read the structure
   off. It needs the stack slots tracked by hand, and the second
   operand at [ESP+0x58] is set further back still.

   THE CHECK IS ALREADY BUILT, which is the reason to do it properly
   rather than approximately: hook 0x0046197a for member 3 and
   0x004614b7 for member 0, and the target is member3 = A x member0
   with A a 1.914-degree Y rotation and translation (-4.0791,
   -6.1705, 2.7412). Any transcription can be scored against that
   before it is believed.

22.1.  What merging actually means here

   racerdraw.c IS ALREADY THE DEDICATED FILE - its header says the
   function was "brought over whole", which is not true and should be
   corrected. 28 of the 31 tags are already in it. The other three
   are helpers with a defensible home:

     mat34_invert_rigid   model.c   general 3x4 maths, also used by
                                    the skeleton walk
     the vertex/face loop model.c   shared with other draws
     the contact rebuild  racer.c   writes racer fields

   So the file merge is nearly a no-op. THE REAL WORK IS THE 28
   FUNCTIONS BECOMING ONE, in the original order, with the six gaps
   filled from the disassembly.

22.2.  The order to do it in

   1  Fill the six gaps first, as marked stubs inside the existing
      slices. They are the only part where behaviour is definitely
      absent, and they are small - four of the six are under 250
      bytes.

   2  Re-derive the span table after each gap lands. A gap that
      shrinks means the transcription is real; one that does not
      means the address range was mis-attributed.

   3  Only then inline the 28 into one function, bottom up, keeping
      the leaf formulas as named statics the way racer_update_pose
      did. That import is the model: control flow whole, formulas
      named, ORIGIN on each.

   4  Score every step against the hooks that already exist -
      0x004614b7 for member 0, 0x0046197a for member 3 and the part
      loop, 0x0045fd0d and 0x00460d3e for the two wheel offsets. Four
      attachment points cover most of what the function produces.

23.  The 464-byte gap, 0x0045fa30..0x0045fc00

   It sits between racerdraw_view_matrix, which ends at 0x0045fa30,
   and racerdraw_fork_solve, which starts at 0x0045fc00. It is not
   x87 soup - it is a chain of named helpers, which makes it the
   cheapest of the six gaps to transcribe:

       0x004039c0  Matrix34_Copy
       0x00403710  Matrix34_Identity
       0x0040fc90  Vec3_Set
       0x00410010  Vec3_TransformByMatrix34
       0x0040ffc0  Vec3_Add

23.1.  MEMBER 3 DEFAULTS TO AN IDENTITY, and that resolves 20.2

       0045fa3d  LEA ECX,[ESP+0x3f4] / CALL Matrix34_Identity
       0045fa49  LEA ECX,[ESP+0x238] / CALL Matrix34_Identity

   ESP+0x238 IS THE MEMBER-3 SLOT - the same one written at 0x00460707
   and read at 0x00461525. So it is identity-initialised here and
   only later overwritten by the rear-wheel block.

   THAT IS WHERE THE "MEMBER 3 GETS AN IDENTITY" NOTE CAME FROM. The
   claim was not invented; it was read off this instruction and then
   stated as though it were the whole story. It is the DEFAULT, not
   the value - if the block at 0x004604c0 runs, it is replaced.

23.2.  The first computation in the gap

       C   = g_bikeCarac[bikeIndex] float at 0x005092b8, which is
             carac 16 - two past RoueAxeDistance at 0x005092b0, so
             the REAR wheel radius

       lift = C * 48 + C * 12 * springBounce        racer+0x2e91
       Vec3_Set(v, 0, lift, 0)

   with 48 at 0x004d0e98, 96 at 0x004d102c and 0.125 at 0x004d1050 -
   the 12 is 0.125 * 96. A purely vertical offset driven by the
   spring, then taken through a matrix by Vec3_TransformByMatrix34
   and accumulated with Vec3_Add.

   The same shape repeats for a second value read from [ESP+0x160],
   so the gap builds TWO offsets and adds them - front and rear.

   IT IS NOT racerdraw_offsets. That is transcribed from
   0x0045f7a0..0x0045f830, a different range. This is a second,
   later offset pass that the port does not have at all. [open -
   what consumes its result]

26.  The slot trace resolves one level and opens another

   The calling convention settles the first slot. Vec3_Set is
   __thiscall with three stack args, so the PUSH EDX at 0x0045fa84 is
   NOT its argument - it survives the purge and belongs to the call
   after it:

       0045fa84  PUSH EDX             &[ESP+0x298]
       0045fa9f  CALL Vec3_Set        this=&[ESP+0x84], (0, lift, 0)
       0045faab  PUSH EAX             the vector Vec3_Set returned
       0045faac  PUSH ECX             &[ESP+0xe0]
       0045faad  CALL Vec3_TransformByMatrix34

   giving  [ESP+0xe0] = (0, lift, 0) through the matrix [ESP+0x298].

   AND [ESP+0x298] IS BUILT IN ANOTHER GAP. Its five references are
   0x0045f5b9, 0x0045f8ea, 0x0045fa65, 0x0045fb06 and 0x0045ff2e, and
   the first is inside 0x0045f5a0..0x0045f6a0 - the 256-byte gap.

26.1.  Piecemeal tracing has reached its limit

   Three slots traced, three levels deep, and each landed in another
   untagged region: [ESP+0x58] -> [ESP+0x40] -> [ESP+0x12c];
   [ESP+0x1c0] -> rear_frame span; [ESP+0xe0] -> [ESP+0x298] ->
   the 0x0045f5a0 gap.

   THAT IS NOT BAD LUCK, IT IS THE SHAPE OF THE PROBLEM. The function
   keeps about forty live matrices and vectors in one stack frame and
   threads them through 200-odd calls. A slot only means anything in
   the context of the frame, so tracing one at a time re-derives the
   same frame repeatedly and gets slower the deeper it goes.

   READ IT FRONT TO BACK IN ADDRESS ORDER INSTEAD, building the frame
   map once - offset, what lives there, where it is written, where it
   is read. Every slot then costs a lookup rather than a search, and
   the transcription falls out in the original order, which is what
   the merge wants anyway.

   The four hooks already in place score it as it goes: 0x004614b7,
   0x0046197a, 0x0045fd0d, 0x00460d3e.

31.1.  The hook was reading the wrong slot

   The part-loop transform at 0x0046197a takes its matrix as a
   PUSHED POINTER, and the two paths push different ones:

       general path   00461979  PUSH EDX   EDX = &+0x12c
       i == 3 path    00461531  PUSH ECX   ECX = &+0x238

   Both arrive at 0x0046197a with four pushes pending, so
   ESP+0x13c is the matrix FOR THE GENERAL PATH ONLY. Every
   "member 3" capture in this document was reading +0x12c.

   IT LOOKED CREDIBLE BECAUSE IT WAS SELF-CONSISTENT. +0x12c held a
   stable value across headings, so the readings repeated exactly and
   the 6.17 difference reproduced every time. A stable wrong number
   is not evidence of anything.

   THE LESSON IS ABOUT THE CAPTURE, NOT THE ANALYSIS. Six sections of
   reasoning were built on it and every one of them was wrong,
   including three that were retracted for other reasons along the
   way. When a hook captures a stack slot at a MERGE POINT, the slot
   only means one thing per incoming path - resolve which path the
   hit came from before believing the bytes.

   EDI DISTINGUISHES THEM and was in the register dump the whole
   time: it is the member index, 3 on the branch in question. The
   information needed to catch this was captured and not used.

   angle, view_matrix, place_rider, the frame map itself. Those were
   read from racer fields or from unambiguous single-path sites.

   THE SWINGARM WAS ALREADY FIXED IN SECTION 14 - the w x d cross
   product - and that fix was verified against 0x00580a70, a global
   with a single writer. It is not affected by this.

40.  The shade flag is segment +0xe0, and it arrives late

   racerdraw_shade_level was a stub because the per-segment shade flag
   was not parsed.  It is now found and implemented.

   maybe_Racer_ShadeLevel (0x00465d60) is two lines:

       if (g_nTrkSegmentCount == 0) return 0x1f;
       return (-(seg[racer->segmentStart].nShaded == 0) & 0xf) + 0x10;

   so 0x10 on a shaded segment and 0x1f otherwise.  It indexes by
   racer+0x31c1, segmentStart - the segment the race assigned, NOT a
   per-frame current segment.  That is the original's choice and it is
   transcribed rather than corrected.

   THE FLAG IS NOT IN THE SEGMENT RECORD, which is why it stayed lost.
   The 132-byte record has no room for it and the in-memory segment is
   252.  It is written by a SECOND per-segment pass, the section
   formats/trk.txt calls the link table: Trk_Load's loop at 0x0040df49
   indexes g_pTrkSegments by the segment stride i*0xfc and stores three
   u16 into +0xd8, +0xda, +0xde and then, for version > 3, four dwords
   into +0xec, +0xe8, +0xe4, +0xe0.

   THE FOUR DWORDS ARE READ IN DESCENDING OFFSET ORDER.  Reading them
   in the order they appear in the struct swaps the shade flag with the
   two surface ids.

   OUR LOADER WAS PUTTING THEM IN A LINK ARRAY NOTHING READ.  src/trk.c
   parsed the section into MR_TrkLink, which was allocated, filled and
   freed with no consumer anywhere in the port - so the bytes were
   consumed, the file stayed aligned, and the data went nowhere.  That
   is why the omission never showed up as a parse failure.  The fields
   now land on MR_TrkSegment and MR_TrkLink is gone.

41.  Two shading mechanisms, and the tunnel is the other one

   Section 40 ended by naming maybe_Racer_ShadeParts as what stood
   between the shade flag and a visible tunnel.  THAT WAS WRONG, and
   the correction matters because the two are unrelated.

   +----------------------+------------------------------------------+
   | The shade LEVEL      | maybe_Racer_ShadeLevel returns 0x10 or   |
   |                      | 0x1f from the segment flag.  The         |
   |                      | original keeps it in one frame slot      |
   |                      | (+0x128) and PUSHES IT INTO EVERY        |

   |                      | is the tunnel darkening.                 |

41.1.  maybe_Racer_ShadeParts, imported whole

   482 bytes, 142 instructions, __ftol its only callee.  The
   decompiler renders the whole body as one bare __ftol() because the
   arithmetic is FPU-only, so it was read from the disassembly.

   THE SIGNATURE IS 18 STACK DWORDS AND IT USES FOUR.  The caller at
   0x004619e8 pushes one dword, the light direction, the camera 3x4 BY
   VALUE (48 bytes copied onto the stack at 0x004619c5), the constant
   1.0f, and the destination vertex array.  The body reads only
   [ESP+0x30], [ESP+0x34], [ESP+0x38] and [ESP+0x70] - the light and
   the destination.  THE MATRIX AND THE 1.0f ARE PASSED AND IGNORED.
   The port takes the three that matter.

   What it computes, per part, per vertex:

       L      = normalise(light), only if |light| != 0.0
       a,b,c  = M^T * L          the light in the part's local frame
       d      = dot(normal, -(a,b,c))
       v      = (int)(20.0 - d * 32/3)
       if (v >= 0x20) v = 0x1f
       vertex.shade = v << 13

   o 20.0 is 0x004d0f98 and 32/3 is 0x004d109c.  The length is
     compared against 0x004d0e54, which is 0.0f.
   o THERE IS NO LOWER CLAMP.  Only the top is clamped; a negative
     intensity is shifted left 13 as a negative int.  Transcribed as
     it stands.
   o MR_Vertex is already 0x1c with shade at +0x0c, so the store
     needed no layout work.

   ITS INPUT DOES NOT EXIST YET.  The normals come from
   racer+0x2d60[slot], a per-LOD array allocated and computed by
   FUN_00462580 (1187 bytes).  The port has no equivalent, so
   racerdraw_slot_normals returns NULL and the function returns
   without writing.  The function is whole and correct; what feeds it
   is missing.  [open - FUN_00462580]

41.2.  g_flLightDir is a constant, not data

   0x0052c228 reads all zeroes in .data and -0.5, -1.0, 0.0 in the
   running game, which looked like loaded content.  It is not:
   FUN_00410120 writes the immediates 0xbf000000 and 0xbf800000 at
   0x0041014e and 0x00410158, and EBX - zero at that point - to the
   third.  So it is a compile-time constant and transcribing it is
   reading the binary, not hardcoding what looks right.

   It is passed UNNORMALISED; maybe_Racer_ShadeParts normalises its
   own copy.  MenuPage10_BikeSelect and MenuPage24_Podium overwrite
   it, so the turntable and the podium light from somewhere else.

43.  maybe_Mesh_SetPrimVariant, done - and inert on measured data

   Imported whole.  121 bytes, and the entire body is a kind swap over
   a prim array:

       shaded ? (0x10 -> 0x15, 0x26 -> 0x27)
              : (0x15 -> 0x10, 0x27 -> 0x26)

   for i < primCount, stride 0x40.  MR_Primitive is already 0x40 with
   kind at +0x00, so the walk is the same one.

   TWO CALL SITES, ONE PER WHEEL, AND THEY TAKE DIFFERENT MESHES.
   Front is racer+0x1dc at 0x0045fcd6, rear is racer+0x360 at
   0x00460ce6.  Both are assigned together at 0x0045f544 when
   skeletonSlot <= 1, from two per-slot global arrays of stride 0x70:

       racer+0x1dc = 0x0051ac58 + slot * 0x70      front
       racer+0x360 = 0x0052c240 + slot * 0x70      rear

   Both arguments are SETNZ on (shadeLevel != 0x1f), so the parameter
   is simply "on a shaded segment".

   THE MESHES ARE PER-SLOT GLOBALS, so this is SHARED state: every
   racer in a LOD slot points at one prim array, and the last writer
   before the draw wins.  That is the original's design, not an

   | front wheel |    48 | 1 x36, 2 x12     | 0           |
   | rear wheel  |    48 | 1 x36, 2 x12     | 0           |
   | bike body   |   340 | 1                | 0           |
   +-------------+-------+------------------+-------------+

   MOTO and the port agree exactly, which is itself worth having - the
   wheel prim arrays are the same size and carry the same kinds on
   both sides.  But none of 0x10, 0x15, 0x26 or 0x27 appears, so the
   loop runs and swaps zero primitives.

   THE FUNCTION IS RIGHT AND THE EFFECT IS ABSENT.  Those are separate
   facts and conflating them is how a correct import gets reverted by
   somebody who sees no change.  The call sits where the original's
   sits and will fire the first time a wheel mesh carries a blended
   kind.  Which bike, track or texture setting produces one is not
   established.  [open]

   So the shade level remains the whole of the visible tunnel effect;
   this is a second mechanism that is present in the code and dormant
   in the data.

44.  Racer_BuildVertexNormals - shade_parts has its input

   FUN_00462580, now Racer_BuildVertexNormals, imported whole.  It
   builds smooth per-vertex normals for one LOD slot, and Racer_Create
   runs it twice - once per articulated slot, ONCE PER RACER.  It
   depends only on the bind pose, which is why the port calls it at
   race setup rather than next to racerdraw_bind_skeleton, which runs
   every frame.

   Accumulate a normalised face normal onto each of its three
   vertices, count the contributions, then divide and renormalise.
   Standard smooth-normal construction, with three things that are
   not standard:

   o THE CROSS PRODUCT IS REVERSED.  Read literally it is
     cross(e2,e1), the negation of the usual order.
     maybe_Racer_ShadeParts negates again before dotting, so the two
     agree; flipping either alone inverts the lighting.

   o 0x004d0ec8 IS A DOUBLE 1.0, not a float.  Its bytes are
     00 00 00 00 00 00 f0 3f, so reading four bytes there returns
     zero and makes the whole function look like it zeroes its own
     output.  That reading is wrong and it is an easy one to make.

   o DIVISION BY THE COUNT IS UNGUARDED.  A vertex in no face has
     count 0 and produces inf or nan, which the following length test
     does not rescue.  OURS SKIPS THOSE VERTICES - a deliberate
     divergence, because the alternative is nan reaching the
     rasterizer through the shade.

44.1.  What had to be wired first

   The builder walks each part's face list at +0x698/+0x69c.  Those
   are written by Skl_Load (0x0046327d, 0x004637e6), not by
   Racer_Create - the skeleton loader partitions the mesh's faces per
   member.

   The port's skeleton had the vertex range per member but not the
   face range, even though skl_load already appends faces in member
   order, so the slice existed implicitly.  MR_SklMember now records
   firstFace and faceCount as the loader goes.

   THE FACES ARE NOT COPIED ONTO MR_RacerPart, and that is deliberate.
   part->faces is MR_Primitive * - the 0x40-stride render form with
   u16 indices - while the skeleton's own faces are MESH_FACE, the
   loader form with int indices.  They are different arrays, and
   assigning one to the other would type-confuse
   racerdraw_queue_parts, which reads part->faces.  The builder reads
   the skeleton's slice directly instead.

   So racerdraw_queue_parts is still unfed: it needs the
   MR_Primitive-form per-part slice, which is a mapping from member to
   a range of s_race_bikePrims rather than of mesh.faces.  [open]

46.  VOID (see 52) - the wheels DO spin

46.1.  Where the rotation that DOES exist is applied

   Every joint angle becomes a matrix in one place: the pose loop at
   0x00460f70, which is inside the audited range and is ours as
   skl_part_local via racerdraw_part_walks.  It reads the three angles
   at record +0x0c and runs each through the 14-bit table -
   FMUL 0x004d0ed0, __ftol, then g_cosTable[i & 0x3fff] for cos and
   [(i - 0x1000) & 0x3fff] for sin.

   So a wheel is just a joint.  Had the original spun them, this loop
   is where it would have shown up, and it is already transcribed.

47.  The rider residual IS the 2 pi wrap, and section 39 was wrong

   Section 39 concluded the wrap was free because parts 2 and 3 carry
   it with a matrix dmax of 0.00000.  That generalised from two
   samples and is false.

   THE WRAP COSTS ONE TRIG INDEX, because the index cast truncates
   TOWARD ZERO and the two representatives straddle the wrap:

       MOTO  angle = -0.3344078   ->  (int)(-871.9956)  = -871
                                      -871 & 0x3fff     = 15513
       ours  angle = +5.9487777   ->  (int)(15512.0044) = 15512

   One index apart, so cos comes out 0.94473 against 0.94460 and sin
   0.32785 against 0.32821.  Parts 2 and 3 happened to truncate the
   same way; nothing about them was general.

47.1.  Everything else about the rider is already identical

   Ruled out by measurement, in this order:

   +--------------------------+---------------------------------+
   | joint angles mod 2 pi    | identical to 6 decimals, all 17 |
   | pivots                   | identical, all 17               |
   | matRiderRoot             | identical                       |
   | matBikeRoot              | identical                       |
   | matOrientation           | identical                       |
   | the part tree            | identical - every parent, next  |
   |                          | and child pointer decoded and   |
   |                          | compared on both sides          |
   +--------------------------+---------------------------------+

   So the inputs, the roots and the topology all agree.  Only the
   angle REPRESENTATIVE differs, and only where the angle is negative.

   +------+-------------+------------+
   | part | MOTO        | ours       |
   +======+=============+============+
   | 2    | -0.19175    | +6.09144   |
   | 4    | -0.33441    | +5.94878   |
   | 6    | -1.46495    | +4.81823   |
   | 8    | -0.11351    | +6.16967   |
   | 9    | -0.71637    | +5.56682   |
   | 5,10 | all positive| identical  |
   | 14   | all positive| identical  |
   +------+-------------+------------+

   EVERY NEGATIVE ANGLE IS WRAPPED IN OURS AND NONE IN MOTO, and ours
   is MOTO plus exactly 2 pi - so the lerp changed nothing and only
   the wrap fired.

47.2.  Where the wrap comes from, and what is left to find

   anim_blend_angle_frames wraps into [0, 2pi] on its BLEND path only.
   Both copy paths - t <= 0 and t >= 1 - return without wrapping, and
   the t <= 0 path skips even the copy when out == a.

   The original has the identical wrap; this was read off the
   disassembly at 0x0045b4e0 rather than assumed.  So MOTO keeping a
   negative angle means EVERY ONE of its fifteen blend call sites in
   maybe_Racer_UpdatePose took a copy path in this state, while at
   least one of ours blended.

   Confirmed from the other end with a hardware watchpoint on part 4's
   angle: the only writer is 0x0045e355, the write-back loop at the
   end of maybe_Racer_UpdatePose, storing EAX = 0xbeab3780 - the
   negative value - straight from its stack frame.

   WHAT IS NOT YET KNOWN is which of our passes blends where MOTO
   copies.  A pass with a == b still wraps, so it need not be one that
   changes anything.  [open - instrument the t of each pass]

   One divergence was found and fixed on the way: our blender computed
   in DOUBLE where the original keeps the whole lerp in one FPU float
   slot and compares against float 0.0 at 0x004d0e54.  Widening the
   intermediate moves the sign test and so moves the wrap.

   IT CUT THE RESIDUAL BY MORE THAN HALF - worst matrix dmax 0.05467
   to 0.01926, part 13 0.04825 to 0.01911, part 8 0.03308 to 0.01670.
   Parts 4, 5, 9, 10 and 12 did not move.  This was predicted NOT to
   help; the prediction was wrong and the double was doing real damage
   on the parts whose blends actually changed a value.

47.3.  What the number means, and why it is invisible

   matrix dmax is the largest difference in ANY of the 12 elements,
   and it is dominated by the TRANSLATION, not the rotation.  Part 4
   is the clean example:

       rotation   MOTO 0.94473 / -0.32785   ours 0.94460 / -0.32821
       translation MOTO (0.000, 12.547, 1.396)
                   ours (0.000, 12.561, 1.395)

   The rotation elements differ by 0.0004, which is exactly one trig
   index - 2 pi / 16384 = 0.000383 rad.  The translation differs by
   0.014, fifty times more, because the pivot arm is long: part 4's
   pivot is (0.278, 10.413, -36.514), about 38 units, and
   0.0004 x 38 = 0.015.

   SO THE WHOLE RESIDUAL IS ONE TRIG INDEX ACTING ON A 38-UNIT ARM.
   0.015 units on a bike roughly 100 units across is under two
   hundredths of a per cent.  IT IS NOT VISIBLE AND IT IS NOT MEANT TO
   BE LOOKED FOR - this is a numeric check, not a visual one.  Any
   visible rider difference is a different bug and should be chased
   separately rather than attributed here.

48.  Found: race_ang_cos called libm where the original reads the table

   The pass that blends where MOTO copies is the PITCH, and the reason
   is four levels upstream of the pose.

   Traced by hooking our own anim_blend_angle_frames.  Exactly two
   call sites run per frame at rest:

       racer_update_pose+0x5FA   t = 0                  copies
       racer_update_pose+0x718   t = 1.46958e-15        BLENDS

   The second is the pitch.  Hooking racer_pose_pitch gave its inputs:

       front[1] = +1.54305e-14      rear[1] = -1.54305e-14

   so the ground contacts are equal and opposite instead of zero, and
   poseBlend converges to 1.47e-15 rather than decaying to it.  Those
   come from racer_wheel_ground, which is m[6+i] * along + m[9+i] +
   position[i]; with along = +-84 that needs m[7] = 1.8369e-16.

   IT DOES.  Read bit for bit:

   +--------+---------------------+----------------------+
   | slot   | MOTO                | ours                 |
   +========+=====================+======================+
   | m[1]   | 0        00000000   | -1.83697e-16 a553c9ca|
   | m[2]   | -0       80000000   | +1.83697e-16 2553c9ca|
   | m[3]   | 0        00000000   | +1.83697e-16 2553c9ca|
   | m[5]   | 0        00000000   | -1.83697e-16 a553c9ca|
   | m[6]   | 0        00000000   | -1.83697e-16 a553c9ca|
   | m[7]   | -0       80000000   | +1.83697e-16 2553c9ca|
   +--------+---------------------+----------------------+

   matBikeRoot is exact on both sides; only matOrientation carries it.

   1.83697e-16 IS cos(3pi/2) IN DOUBLE.  race_ang_cos was

       return (float)cos((double)(a & 0x3fff) * RACE_RAD_PER_ANG);

   with the comment immediately below it stating that the original
   rebuilds the 3x3 from g_cosTable[i & 0x3fff].  The code and the
   note describing it disagreed, and the note was right.

   THE TABLE IS BIT-IDENTICAL BETWEEN THE TWO GAMES - checked at all
   four quadrant entries, including g_cosTable[0x3000] =
   -1.190342746e-12 - so switching to it is exact, not merely closer.

48.1.  The chain, because it is worth seeing whole

       race_ang_cos uses libm            cos(3pi/2) = -1.83697e-16
         -> matOrientation off-diagonals +-1.83697e-16, not 0
         -> wheel ground contacts        +-1.54305e-14, not 0
         -> pitch weight                 1.46958e-15, not 0
         -> the pitch pose pass BLENDS   where the original COPIES
         -> anim_blend_angle_frames wraps every negative angle by 2pi
         -> the trig index truncates one step differently
         -> every rider joint is one index out

   A 1e-16 error in a cosine became a visible-in-the-numbers pose
   difference eleven orders of magnitude larger, because a boolean -
   blend or copy - sat in the middle of it.  THAT is why the residual
   did not shrink when the inputs looked identical to six decimals:
   the comparison that mattered was against exact zero.

   THIS IS THE THIRD libm-FOR-TABLE DEFECT, after racer_compose_yaw
   and racerdraw_arm_matrix.  Any remaining cos/sin call on a path
   that feeds a matrix should be treated as suspect until checked.

49.  The table fix was real but was NOT the cause

   Section 48 predicted that using g_cosTable in race_ang_cos would
   close the rider residual.  IT DID NOT.  The pose comparison after
   the change is identical digit for digit - worst matrix dmax still
   0.01926, angle deltas still 6.28319.

   The change did take effect and is worth keeping: matOrientation's
   off-diagonals went from 2553c9ca (cos(3pi/2) in double,
   1.83697e-16) to 2ba7869e (the table's -1.190342746e-12).  It is now
   doing what the original's comment describes.  BUT NEITHER VALUE IS
   ZERO, and MOTO's are exact zero, so the residue survived at a
   different magnitude.

   TWO PREDICTIONS IN A ROW WERE WRONG HERE.  The first said the 2 pi
   wrap was harmless; the second said the table fix would close it.
   Both were reasoned from a mechanism that was real but not the
   binding constraint.  The lesson is the same one twice: verify the
   OUTPUT against MOTO, not the mechanism against a story.

50.  Found: the quantise ran after the ground fit instead of before

   A hardware watchpoint on MOTO's matOrientation[6] settles it.
   Three writes per frame, in this order:

   +-----------+------------------------------+---------------+
   | eip       | what                         | value written |
   +===========+==============================+===============+
   | 0045cb58  | the Matrix34_Multiply copy   | -1.19e-12     |
   | 0045cca6  | the quantise rebuild store   | -1.19e-12     |
   | 00469738  | inside UpdateGroundContact,  | 0.0           |
   |           | the terrain re-fit           |               |
   +-----------+------------------------------+---------------+

   SO MOTO PRODUCES THE SAME RESIDUE WE DO AND THEN THROWS IT AWAY.
   The rebuild is not a cleaner formula; it is the same formula, and
   the exact zeros come from the ground fit that runs after it.

   The port called race_orient_quantise at the END of the tick, after
   racer_update_ground_contact, so the rebuild had the last word and
   the residue survived.  The original quantises inside
   maybe_Racer_ApplySteering (0x0046664a), BEFORE the ground fit.
   Moved to match.

   THIS IS THE SAME MISTAKE THE COMMENT AT THAT SITE ALREADY WARNS
   ABOUT, in a subtler form.  It says what used to be there "overwrote
   matOrientation with the SEGMENT matrix ... so the terrain fit
   racer_update_ground_contact had just built was thrown away every
   single frame".  The segment matrix went; the overwrite stayed, now
   carrying only 1e-12 instead of a whole wrong attitude, and that was
   small enough to look like nothing.

50.1.  The rebuild is verified, and 49.1 was wrong about it

   Traced instruction by instruction through the x87 stack,
   0x0045cc36 to 0x0045ccd2.  All nine elements match ours exactly:

       m[0] = cB*cC              m[1] = sC*cA + sB*cC*sA
       m[2] = sC*sA - sB*cC*cA   m[3] = -(sC*cB)
       m[4] = cC*cA - sC*sB*sA   m[5] = cC*sA + sC*sB*cA
       m[6] = sB                 m[7] = -(cB*sA)
       m[8] = cB*cA

   A is roll, B pitch, C yaw; the sines and cosines come from
   g_cosTable at i & 0x3fff and (i - 0x1000) & 0x3fff, and the
   translation row is zeroed at +0xe0 and +0xe4.

   Section 49.1 claimed m[6] came from an FSUBP of two products.  IT
   DOES NOT - it is a bare sB.  The FSUBP two instructions earlier
   produces m[4], and an FXCH ST2 moves sB to the top before the
   store; reading the store without following the exchange gives the
   wrong operand.  x87 traces have to be followed through the
   exchanges or not attempted.

51.1.  What the whole thing turned out to be

   One line in the wrong place.  race_orient_quantise ran after
   racer_update_ground_contact instead of before it, so a rebuild
   carrying the angle table's -1.19e-12 at the quarter turns
   overwrote a terrain fit that was exactly zero.

   Nothing else was wrong.  The rebuild formula was right, the trig
   table was right, the blender was right, the pose passes were right,
   the normals were right, the tree was right.  A 1e-12 in one matrix
   slot became a 2 pi wrap on every rider joint because a boolean -
   blend or copy - sat between them.

   TWO REAL DEFECTS WERE FIXED ON THE WAY and neither was the cause:
   race_ang_cos called libm where the original reads the table (48),
   and anim_blend_angle_frames computed in double where the original
   keeps floats (47.2).  Both are worth keeping; the second more than
   halved the residual before the actual fix removed it.

52.  The wheels DO spin - Racer_SpinWheels, and 46 was wrong

   Section 46 concluded there was no wheel rotation to implement.  It
   is visibly wrong in retail, and the reason the probes missed it is
   worth stating: they looked for spin STATE in the wheel instances
   and for a cycling PART matrix, and the spin is neither.  It is a
   plain accumulating angle in the racer that only the draw consumes.

   Found by hooking maybe_Inst_DrawWithMatrix at 0x0048c70e and
   capturing the matrix it is handed (EBX) with EBP naming the
   instance.  Both wheels get a PURE X-AXIS ROTATION that changes
   every frame:

   +------+--------+-------------------+-----------+
   | hit  | wheel  | m[4] / m[5]       | angle rad |
   +======+========+===================+===========+
   | 1    | front  | 0.97329 / -0.22957|   0.2318  |
   | 3    | front  | 0.99685 / -0.07930|   0.0794  |
   | 2    | rear   | 0.68926 / -0.72451|   0.8112  |
   | 4    | rear   | 0.78145 / -0.62396|   0.6743  |
   +------+--------+-------------------+-----------+

   The angles are EXACT TABLE INDICES - -181.0 and 1404.0 - which is
   what said the matrix is built from g_cosTable and the angle is
   stored, not computed from a matrix.

52.1.  The state, and the function that advances it

   racer+0x2e3d and racer+0x2e49, the two euler triples the frame doc
   already called "unnamed next to forkDive".  Only X is ever set, and
   both accumulate with distance - measured creeping on MOTO:

       speed    rear (+0x2e3d)   front (+0x2e49)
        8.52          7.89087          8.70716
       10.19          8.70443          9.60489
       12.02          9.66738         10.66745
       13.98         10.79187         11.90827
       15.94         12.07923         13.32880

   The front runs faster because its radius is smaller.

   A watchpoint on +0x2e3d names the single writer: 0x00466a42, in
   FUN_00466940, now Racer_SpinWheels.  It is called once per racer
   per tick from all three tick variants and is short enough to quote:

       if (humanPlayer ? (inputWord & 2) : (tickInputWord & 2)) return;
       axis   = matOrientation row3 + row2
       rear  += dot(rearContact  - rearContactPrev,  axis)
                / (rayonAr * g_frameDelta * 96)
       front += dot(frontContact - frontContactPrev, axis)
                / (rayonAv * g_frameDelta * 96)

   o 96.0 is 0x004d102c.
   o BRAKING LOCKS THE WHEELS.  Bit 1 returns early, so a braking bike
     slides with its wheels stopped.
   o THE AXIS IS ROW3 PLUS ROW2, which is not obviously a direction.
     Transcribed as it stands.
   o It never wraps.  The angle grows without bound and only ever
     reaches mat34_from_euler, which masks the index.

52.2.  Everything downstream was already built

   racerdraw_build_matrices has read rearWheelSpin and
   frontWheelSpin since it was written - racerdraw.c calls
   mat34_from_euler on both, the rear
   chain at one and the front at the other.  MR_Racer has carried the
   fields all along.  The ONLY missing piece was the accumulator, so
   the wheels were being drawn with a spin of exactly zero every
   frame.

   THAT IS WHY "ALL THE MATRICES MATCH" WAS TRUE AND USELESS.  The
   pose A/B compares pose[] parts; the wheels are drawn as INSTANCES
   with a matrix built outside that array, so a comparison that reads
   zero on both sides passes while both are wrong in the same way -
   ours because nothing writes the angle, MOTO's only when the bike
   happens to be stopped.  A comparison taken at rest cannot see a
   term that is zero at rest.

53.  The spin belongs to the wheel MESH only

   With Racer_SpinWheels landed the wheels turned, and so did the
   swingarm, the rear frame and the fork pivot - both wheels orbiting
   a point that was not their axle.

   THE SPIN WAS IN A MATRIX FOUR THINGS SHARE.  Our rearMat was
   FromEuler(rearWheelSpin) x roll x root and fed all of:

       racerdraw_rear_frame  -> rearFrameW, the world rear frame
       racerdraw_arm_angle   -> the swingarm angle
       racerdraw_rear_frame  -> rearFrameC -> armC -> viewPart3
       the rear wheel draw

   Only the last of those wants it.  MOTO keeps the two apart:

       +0x298   roll x root                    the general rear matrix
       +0x268   FromEuler(rearWheelSpin) x +0x298     the wheel's attitude
       +0x334   a copy of +0x268, and the ONLY thing that reaches
                maybe_Inst_DrawWithMatrix

   The front is the same shape: the bars on the body place the fork
   and build the front frame, and frontWheelSpin goes on top for the mesh
   alone.  Ours folded it into frontMat, which
   racerdraw_fork_solve transforms the pivot through - so the fork
   pivot orbited and carried the wheel with it.

   Fixed by giving build_matrices a fifth output.  rollOut and
   frontOut are spin-free and feed the frames, the pivot, the arm and
   the swingarm; rearOut and frontWheelOut carry the spin and go only
   to the two wheel draws.

55.1.  Where the second rotation came from

   maybe_Racer_Draw builds the fork frame at 0x0045fb0f from body
   +0x298 - roll x root, NO STEER - and transforms the fork pivot
   through it at 0x0045fb49.  So in the original the pivot stays put
   when the bars turn and only the fork AXIS rotates, through the
   steer matrix built separately at 0x0045fb6d.

   The port passed frontFrame, built from frontMat, and frontMat is
   steer x body.  So the pivot turned as well as the axis: two
   rotations, hence 1.91x.  The Y drift follows from the same cause -
   a pivot that swings changes reach, and reach scales an axis that
   points down the fork.

   Fixed by building the fork frame from rollMat.

   ONE THING THIS RULED OUT ALONG THE WAY: MOTO reads the fork tip's
   part index from a per-slot table at racer+0x2d74 rather than
   hardcoding it - EDI = [ptr+8] at 0x0045fb5b.  Read live it is 15,
   which is what the port hardcodes, so it is not a divergence.  The
   table itself is worth knowing: it reads 0, 1, 15, 2, 16, 3, 4, 5.
   [open - what that ordering is]

59.1.  Two details that had to be measured, not assumed

   o THE UV SCALE IS A FLOAT RECIPROCAL.  pixel * (1.0f/255.0f)
     reproduces the original's bits at every corner; a correctly
     rounded pixel/255.0 comes out ONE ULP HIGH at 56, 58 and 113 and
     exact at 2 and 34.  Seven candidate formulas were tried against
     the five observed bit patterns and only the reciprocal matches
     all five.

   o +0x3f IS THE ALPHA BYTE and ours was zero.  The prim constructor
     at 0x00422de0 derives flatColor from colorIndex by the 5-6-5
     expansion, which for colour 0 gives 0 - so the 0xff in the top
     byte is set somewhere else and is not a consequence of the
     colour.  A zero there is what a fully transparent primitive
     looks like.

   THE TAIL SLOT IS NOT A WRAP UV.  The constructor copies the first
   (u,v) into slot 4 for ordinary faces; the shadow instead holds
   114.0 and 57.0, each one past its own quad's u0.  114.0 appears as
   the immediate 0x42e40000 at 0x0045bfce, so it is authored, not
   derived.  [open - what reads it]

60.  The shadow's bank is bike-relative and was not rebased

   With the primitives byte-identical to MOTO (59.2) the shadow still
   drew as a rectangle.  The material was right; the PAGE it names was
   not loaded.

   MOTO's bank numbering and ours are different, and the shadow is the
   one primitive that carries the original's index literally:

   +----------------------------+----------+----------+
   | file                       | MOTO     | ours     |
   +============================+==========+==========+
   | data\speed\bnk00_00.raw    | bank  0  | bank 28  |
   | data\speed\bnk00_01.raw    | bank  1  | bank 29  |
   | data\ile01\...\bnk00_02    | bank  2  | bank  9  |
   +----------------------------+----------+----------+

   MOTO runs the two bike pages first and the track from 2; the port
   puts the track at 8 and the bike at RACE_BIKE_BANK.  So the shadow's
   bankIndex of 1 means "the bike's second page" and resolves to 29
   here, not 1.

   BANK 1 IS EMPTY IN THE PORT - read live, s_banks[0] and s_banks[1]
   are entirely zero - so prim_is_textured returned 0 and both quads
   fell through to their flatColor.  That is 0xff000000: a solid black
   rectangle, which is exactly what was on screen.

   Fixed by rebasing the shadow prims with prim_rebase_banks and
   RACE_BIKE_BANK, the same call the bike's own prims already get.

60.1.  Why 59.2's "byte-identical" was true and not enough

   The primitives ARE identical to MOTO's, field for field, and that
   was verified honestly.  It just does not settle the question,
   because a bankIndex is only meaningful against a bank TABLE, and
   the two programs number their tables differently.  Copying the
   original's index verbatim is correct for every field except this
   one, where it is the one field that must NOT be copied verbatim.

   The tell was available and was not read: prim.h already says a face
   pointing at a bank nobody loaded "draws as its flatColor", and the
   flatColor here is opaque black.  A black rectangle was the
   documented symptom of exactly this.

62.1.  Two ways this was got wrong first

   o READING THE CODE WAS NOT ENOUGH.  Both implementations read
     frontWheelContact and rearWheelContact and project to the
     ground; comparing the two functions says they must agree, and
     they do not, because the ORDER around them differs.  A function
     can be transcribed perfectly and still be wrong at the point it
     is called.

   o THE FIRST WHEELIE TEST NEVER WHEELIED.  Holding accelerate never
     raises the nose, and forcing wheelieAngle moves neither game's
     contacts - both sat at front.y 0.00 and a 248-unit shadow at
     every forced angle, which reads exactly like agreement.  THE
     STUNT BUTTON IS BIT 6 AND IS NOT PART OF THE INPUT WORD:
     mrhook routes 0x40 to stuntHeld and stuntPressed directly, and
     the port takes keys=c.  A test that cannot produce the state it
     is testing will report that everything matches.

63.  Why the shadow ordering was missed - the order was written down
     and not followed

   Verified after the move: our shadow holds 248.0 through a wheelie
   with the front contact at y 118.79, against MOTO's 251.4 at the
   same lift.  MOTO's few units of variation are terrain, since each
   vertex is dropped onto the ground independently; ours is on flat
   road.  The divergence is closed.

   THE ORDER WAS ALREADY IN THE TREE.  racer.c carries s_tickOrder,
   tagged "ORIGIN maybe_Racer_Tick @ 0x0045d580, its call list - DATA,
   not code", and it lists in sequence:

       maybe_Racer_BuildShadow       0x00461aa0
       maybe_Racer_UpdateLean        0x00469c60

   BuildShadow before UpdateLean, correctly recorded.  Nothing reads
   that table.  racer_tick_order() has exactly one reference in the
   whole tree - its own declaration in racer.h - so the sequence was
   transcribed as documentation and the scaffolding in race.c then
   called things in a different order with nothing to object.

63.1.  Three reasons it survived, and only one is about the shadow

   o IT WAS NEVER IN THE maybe_Racer_Draw AUDIT.  BuildShadow is
     called from the TICK by all three tick variants and never from
     the draw, so the whole audit that verified racerdraw.c function
     by function could not have covered where it is called from.

   o THE FUNCTION WAS VERIFIED, THE CALL SITE WAS NOT.
     racerdraw_build_shadow is byte-exact - section 12 checked all six
     vertices and they still agree.  A function can be transcribed
     perfectly and be wrong at the point it is invoked, and nothing in
     the harness looks at invocation order.

   o maybe_Racer_Tick WAS NEVER IMPORTED WHOLE.  It exists here as
     slices - racer.c carries five separate "at 0x0045d..." tags - plus
     the s_tickOrder table.  CLAUDE.md 15 says a slice "silently drops
     every branch nobody knew to look for"; what it dropped here was
     not a branch but the ORDER, which is the one thing a call list is.

   AND THE VERIFICATION COULD NOT HAVE CAUGHT IT.  The shadow was
   compared at rest, where the front contact is flat and both orders
   give the same six vertices.  That is the third time this session a
   term that is zero in the measured state hid a real divergence - the
   wheel spin and the fork steer were the others.

63.2.  What this implies beyond the shadow

   Sixteen other steps sit in s_tickOrder and none of them is checked
   against what race.c actually does.  Any one of them could be in the
   wrong place for the same reason, and the symptom would again only
   appear in a state the comparison does not visit.

   THE TABLE IS THE FIX THAT IS ALREADY HALF-WRITTEN.  It names the
   function, the address and the guard for every step; comparing it
   against the real call sequence is a mechanical check nobody has
   run.  [open - audit race.c's tick against s_tickOrder]
